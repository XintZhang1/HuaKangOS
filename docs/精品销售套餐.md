# 精品销售套餐

本模块对应原表 HK-068“精品销售套餐设置”，并接通 HK-069／HK-070 已有的精品销售、安装、退货与收退款。精品套餐是门店商品和安装项目的销售组合，集团会员服务套餐仍使用独立权益账本，二者不混用。

原表没有定义套餐拆退价格算法。本批按明确的固定规则交付：在发布前配置每套组成、参考金额、成交价、销售期间和退货补充条款；按原分摊逐组件退货，不因部分退货重新定价剩余商品。该软件规则已经实现和自动验证，不能据此宣称公司已批准条款或全系统已验收。

## 发布与开单

店长或管理员在“精品套餐配置”选择本店启用商品和可选安装项目。每个版本包括套餐代码与名称、整数分成交价、起止日期、明确退款条款和有序组成。默认不启用；发布新版本时须明确勾选启用。停用通过发布未启用的新版本完成，历史规则不覆盖。

每项组成分别填写“每套此商品数量”“每套此商品参考金额”“每套此安装参考金额”。数量为整数千分位，金额为整数分。参考金额是每套内该组件的总参考金额，不是商品单价。重复 SKU 在发布时拒绝；无安装项目不能填安装金额；每套成交价须为正数且不超过参考合计。

系统按商品、安装参考金额的占比对每套成交价使用最大余数法分摊。同余数时按配置组成顺序、商品在安装之前分配。先冻结每套金额，再乘购买整套数，因此买两套与两次各买一套的分摊一致。例如一套商品参考 10.00 元、安装 1.00 元、另一商品 0.01 元，成交 10.00 元，冻结分摊为 9.08、0.91、0.01 元；第二商品可为 0.333 件，不要求从金额反算整分单价。

销售或服务顾问选择本人有权办理的本店客户、套餐和整数套数。页面先展示本次组成、数量、分摊与条款，再提交开单。后台重新检查当前启用版本、有效期、客户归属、每个商品与安装项目以及全部可用库存。开单在一个事务中创建原精品订单、冻结金额分摊、商品占用、主管待办、来源日志和幂等回执，任何组件失败全部回滚。可选维修关联仅允许同店同客户的可读维修单。

## 岗位办理与异常出口

| 经办岗位 | 必要事实与入口 | 结果与下一责任人 |
|---|---|---|
| 销售／服务顾问 | 选择当前套餐并确认已说明冻结退货条款 | 仅占库存，交店长复核价格 |
| 店长 | 原冻结明细、明确最低总额；低价例外需理由 | 批准原报价后由原经办记录客户实际授权 |
| 原经办 | 本单客户授权类别文件，当前冻结报价版本 | 交库管实际出库，不把生成报价当客户签字 |
| 库管 | 原单已批准且客户已授权，本人实际出库凭据 | 每商品产生原库存流水，交技师／客户接收 |
| 技师 | 实際安装结果及凭据，无未处理退货冲突 | 原经办记录客户实际接收 |
| 财务 | 本店账户、真实流水与收退款凭据 | 分笔实收或原款退款，不重复生成套餐现金 |
| 退货经办与店长 | 原出库行及未退数量、理由、独立岗位复核 | 占用原可退数量后交库管可售检查 |
| 库管／技师 | 不合格先整改复检；拒收须实物交回客户 | 只有验收通过才入库、减少应收或增加退款额度 |

未出库可由主管取消，释放所有原占用；已有实际收款形成原账户退款待办。已出库必须走原单部分退货。批准后尚未验收的退货可以撤销并释放原可退数量；不合格的整改、复检、拒收及交回沿既有精品流程。到期未办使用原待办与逾期提示，不自动移动库存、退款或替员工确认。交接由既有待办指派办理，系统保留已明确的当前责任人。

实际部分退货按原行剩余数量分摊原商品金额、安装金额和库存成本，最后一次取尽余分。已经履约的对应安装金额保留；未安装的对应费用随验收退货减免。其他商品的原分摊金额不变。未收款部分只减应收，不能伪造现金退款。预收抵用、客户月结分配、实际收款和原款更正继续使用原精品结算入口。

## 冻结数据与权限

追加迁移 `d430_retail_bundles`，依赖 `c329_vehicle_imports`，静态建立五张表：规则、组成、原精品套餐销售、原行分摊、规则发布回执。新业务仍为 `retail / flow_version=2`，以是否存在不可变套餐来源分派金额校验，普通精品单的既有单价算法保持原有语义。

套餐行的独立单价内部字段为 0，表示不单独按单价计价。API 对此类行不返回该字段，显式给出 `pricing_mode=frozen_bundle`，UI 和文件只展示冻结套餐分摊金额。该内部值不能被员工理解为免费商品，也不能用于重新计算原单。通用改状态／改价接口不能办理该精品原单，ORM 与恢复校验均拒绝覆盖冻结来源、组件或分摊。

所有业务与规则本店隔离。库管、技师只能查看履约所需组成，不能查询规则价格、原单金额、补充财务条款或价格文件。集团汇总只读。两连接同时占同一库存使用同一 Item 版本与数据库锁，冲突返回中文错误；客户端须刷新核对，保留原请求编号。

API 前缀 `/api/retail-bundles`：

- `GET /rules`：本店规则及历史版本，当前版本单独标记。
- `POST /rules`：`request_id/base_version/values`。版本必须等于当前最新版本；首次为 0。明确配置每套组成与金额后追加版本。
- `GET /rules/{id}/preview?sets=N`：当前有效版本、本次数量及金额、当前可用整套数提示。
- `POST /sales`：`request_id/rule_id/rule_version/sets/customer_id/related_repair_id/terms_accepted=true`。返回原精品业务详情，后续沿 `/api/retail/orders/{id}/actions/{action}` 办理。

## 报价文件、报表与恢复

本单可生成 `retail_quote` 精品套餐报价确认单，记录原套餐版本、套数、每项商品和安装分摊、合计、固定退货规则及发行前补充条款。模板默认草稿，需门店确认后启用。生成不等于客户授权；文件按原机制冻结字节、模板版本与快照，进入附件检查，技术与仓库岗位无权读取价格件。配置后续版本不重写历史文件。

专用排版将元信息、明细表和条款分别呈现，明细表逐项独立行且跨页重复表头。真实接口生成的短单与 24 项长单经过官方 LibreOffice 临时解包版本渲染，逐页检查分页、数量、金额、条款和签名区；普通通用模板未因本模块改变。

`retail_bundle_settlements` 是原 `retail_settlements` 的套餐来源子集，图表、明细、CSV 保持同源；不作为额外营业收入或第二份现金来源。按原报价、验收退货、安装保留费、实际净收以及库存成本追溯原精品单。月结定义 5 记录冻结套餐来源，旧定义继续按原范围核对。

`retail_bundle_integrity.frozen_pricing_sqlite` 和 `validate_retail_bundles_sqlite` 离线核对规则组成、门店、逐套最大余数分摊、乘套数、原行数量及金额、发布回执、开单来源事件和原客户业务。原精品恢复校验继续核对所有占用、出入库数量与成本、可退上限和唯一现金。删除套餐来源、额外加商品或重定价原分摊会被拒绝。

## 验证与边界

`tests/test_retail_bundles.py` 有 10 项专项，覆盖分数数量及金额余分、安装后多次部分退货与原成本恢复、未安装减免、取消释放、默认关闭与新旧版本、重复 SKU、过期／越权／跨店／幂等、两连接竞争、最后一步失败全部回滚、恢复篡改拒绝、价格文件权限与不可变字节、24 项长单生成。与原精品、业务预收／客户月结、门店对账组合运行 63 项通过；套餐经营图表与 CSV 的独立整合用例也通过。全量回归与 PostgreSQL 最新结果由总验收记录统一列明。

`tests/browser_retail_bundles.py` 在独立合成新库、真实本地 HTTP Chrome、390×844 窄屏中使用店长、销售、库管、技师、财务五个实际员工账号，4 场景通过且无 JavaScript 错误。覆盖配置与冻结、0.666 件商品的套餐报价、低价例外、实际授权、分笔收款、安装关口、退货不合格整改复检、原退款和保留安装费；新页面及收退款截图已目检。本地 HTTP 演练不是正式 HTTPS 与公司业务验收。

本批一张精品单选择一个套餐版本并购买整数套，组件数量允许千分位，原商品退货允许合法部分数量。未做一单混搭多个套餐、临时替换组件、任意促销叠加、退部分后重估剩余商品价格或额外赠品追价；这些不是本批固定规则的默认行为。门店若需要不同退货政策，应先明确业务规则另行增加有版本的流程，不可修改已冻结原单。
