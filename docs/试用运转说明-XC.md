# XC 试用运转说明

本轮试用的做法：**按需求表里每一个带冒号的大功能走一整轮**，过程中我会提供虚拟需求、虚拟数据和步骤；你以“刚用这个系统的人”的视角跑，遇到不好用的地方直接告诉我，我做最小微调，然后以 commit + PR 的形式交给你审核。

已有材料的分工：

| 材料 | 用途 |
|---|---|
| `docs/试用脚本/总表.md` | 41 轮清单、虚拟世界设定、累计数据索引 |
| `docs/试用脚本/Rxx-*.md` | 单轮脚本：数据、步骤、分支、观察点、核对、记录表 |
| `docs/试用操作手册-XC.html` | 上面两份的单文件版，可离线打开、可打印 |

《从零试用操作手册》是入门串烧；本轮是按 41 组逐个深挖，两套可以并存，不互相替代。

## 一、环境：全新独立预览

本轮用**全新空库**，和旧目录 `E:\proj\...\dealer_desk` 的那份预览互不影响（旧库保持原样、不再启动）。

1. 双击仓库根目录 `start-preview.cmd`（或在仓库目录执行 `.\start-preview.ps1`）。
2. 首次会打开“设置本地预览管理员”页面：填管理员账号 `admin`、密码（12–128 位）、再次输入密码，点“设置管理员并进入”。设置链接 15 分钟有效，失效就再运行一次启动器。
3. 默认地址 `http://127.0.0.1:8000/`；端口被占时启动器会自动顺延并显示实际地址。
4. 数据、日志、预览状态在 `%LOCALAPPDATA%\huakangos\preview-4d3404510ceec7f779b8`（这个编号由源码目录路径算出），与仓库 `data` 目录和公司库无关。

**请不要再移动仓库目录**：预览数据是按目录路径绑定的，移动后系统会认为换了另一份源码。确实要移动时，把 `preview-4d3404510ceec7f779b8` 整个目录复制成新路径对应的 `preview-<新编号>`，并把里面的 `preview.json` 的 `repository_id` 改成新编号；或干脆用新目录重新开始（旧库保留）。

### 员工账号一次建好（R01 用）

R01 要建 9 个员工账号，一个个填太费事。**先手动建 1 个**体验一遍表单，其余的在“员工账号”页面点 **批量新增员工**：

1. 每行粘贴一条：`员工姓名｜登录账号｜岗位`（竖线、中文竖线、逗号、制表符或两个以上空格都行；账号写在姓名前面也能认出来）。
2. 岗位写中文即可：销售、店长、库管、服务顾问、前台接待、维修技师、财务、审计、客服。
3. 下面的**核对名单**逐行检查：账号格式、是否重复、是否已存在、岗位是否认识；系统管理员账号会被拦下（那类账号用“新增员工”单独建）。有问题的行会说明原因，全部合格才允许提交。
4. 选本次分配门店，填一个 12 位以上的**初始密码**（本批共用），提交后每个账号首次登录都必须自己改密。

**这个按钮只有系统管理员能看到**：店长及其他岗位在侧栏看不到“员工账号”，即使直接调用接口也会被服务端拒绝（按账号岗位判定，不是只隐藏按钮）。集团汇总视图是只读的，同样不能建账号。

备用命令行工具（先看会建哪些、不写入时方便）：

```powershell
.\scripts\create-xc-staff.cmd
```

（也可以直接跑 `.\\.venv\\Scripts\\python.exe scripts\\create_xc_staff.py`；它只连本机预览、跳过已存在的账号、不保存密码。）

前台使用顺序仍是：门店设置（改名 + 建城西店）→ 建账号 → 员工首次登录改密。

## 二、一轮怎么跑

1. 打开 `docs/试用脚本/R01-系统管理.md`（或 HTML 单文件版），先看“本轮虚拟需求”“本轮数据”。
2. 按“操作步骤”一节做。每步有四种信息：**谁**（哪个账号、哪个岗位）、**手动**（侧栏或页面路径）、**搜索**（搜索框输入什么词）、**助手**（对业务助手说什么）。三种通道随你混用，同一件事不要重复提交。
3. 每步先看右上角：当前门店、姓名、岗位是否正确；需要换岗位时按“岗位切换”约定换浏览器个人资料或退出重登。
4. 有“分支与找坑”时，至少挑一条跑（拒绝、重复、过期版本、跨店、边界）。
5. 做完按“结束核对”和“报表核对”收口；把单号填进“记录表”。

节奏建议：R01–R07 是开门和基础资料，可以连着做；之后每轮 20–40 分钟（含分支 45–70 分钟），不必一次做完。

## 三、反馈怎么写

沿用你熟悉的格式，一句到几句就够：

```
门店／岗位：星驰汽车城东店 / 销售
轮次步号：R01-07
单号／条目：xc-sales
我点了：新增员工 → 保存
我原本希望：……
实际出现：……
截图：（可附）
```

也可以直接用页内 **业务助手 → 问题清单** 记录并导出，把文件或文字发我；页内记录会区分资料不足、业务规则、模型填错、服务错误和未支持事项。

金额、数量、时间有问题时把**你预期的数值**一起写上。不要发送密码、密钥或真实客户资料。

## 四、我拿到反馈后怎么处理

每条反馈进《试用问题台账》，给编号 `XC-ISSUE-0NN`，并按六类判定：

| 判定 | 意思 | 我通常怎么做 |
|---|---|---|
| ①文案提示 | 话说得不清、按钮名误导、错误提示看不懂 | 直接改文案，不动判断逻辑 |
| ②校验默认值预填 | 该拦的没拦、能带出的信息要重填 | 前端加提示/预填，必要时后端二次校验 |
| ③入口搜索词指引 | 找不到入口、搜索词搜不到、指引与页面不一致 | 改 `docs/workflow-source/*.json` 后重建手册与搜索索引 |
| ④交互布局 | 点击路径长、窄屏难用、顺序别扭 | 最小前端改动，桌面与 390px 各看一遍 |
| ⑤业务规则 | 涉及金额、库存、审批、权限、版本口径 | **先给方案等你确认**，再实现并补齐拒绝/跨店/重复/过期版本/守恒验证 |
| ⑥缺陷 | 明确的错值、报错、卡死、重复提交 | 先复现再修，附复现步骤 |

不会做：放宽审批或权限、绕过原接口、把准备当成实物/现金、堆砌必填、监控员工、新增需求表以外的范围、改历史迁移、把演示数据写进正式库、动你现在的预览库。

## 五、提交与 PR

- 每轮改动放一个分支 `trial/rNN-<说明>`，一个或多个 commit，然后提一个 PR 到 `main`，由你审核合并。**我不会直接推 main，也不会自动合并。**
- PR 正文固定六段：反馈 → 判定 → 改动（是否触碰业务规则）→ 验证（命令、结果、源码摘要）→ 需要你复验的步骤 → 风险与回滚。
- PR 里会明确写“**需要重启预览**”还是“**只要刷新页面**”。
- 每轮 PR 同时附上**下一轮的脚本**，保证你手上总有一轮能跑。

## 六、重启与刷新

| 我改了什么 | 你要做什么 |
|---|---|
| 只改 `web/*.js`（文案、布局、提示） | 页面 Ctrl+F5 刷新即可 |
| 改了 `app/*.py`、迁移或生成物 | 需要重启预览（见下） |
| 只改文档、脚本、试用材料 | 不需要重启，也不用刷新 |

安全重启（不要按端口杀进程）：

```powershell
$root = Join-Path $env:LOCALAPPDATA 'huakangos\preview-4d3404510ceec7f779b8'
Get-Content (Join-Path $root 'process.json') -Raw      # 看 pid / port
Get-CimInstance Win32_Process -Filter "ProcessId = <上面的pid>" | Select-Object ProcessId, CommandLine
Stop-Process -Id <上面的pid>                            # 确认是本目录 app.local_preview serve 才结束
.\start-preview.cmd                                     # 重新启动，账号和数据保留
```

源码变了以后启动器会拒绝复用旧进程并提示你关闭原预览，这是有意设计，不是故障。

## 七、数据与安全

- 只用虚拟客户、虚拟 VIN、虚拟金额；不真转账、不发消息、不开票；上传文件一律标注“试用”。
- 业务助手使用本机私有配置 `%LOCALAPPDATA%\huakangos\business-assistant.json`（当前为 DeepSeek，`synthetic: true`）。密钥不写进文档、对话或截图。
- 不同岗位用不同账号办理；不用管理员账号代替所有岗位，也不自己申请自己批准。
- 提交结果不确定（超时、断线、页面卡住）时，先刷新并打开原单确认，再决定下一步，不要换新请求号盲目重试。
