# 业务助手权限范围与“向上级评审”设计 · 2026-09-24

你的原话：“我们能不能允许 deepseek 完成已有指引或者已有评审名单之外的工作？就是需要他按照员工的职责范围和可使用模块来判定这个任务能否完成，如果需要更高权限，允许向相关上级提交评审。”

一句话结论：**“能不能办”由系统回答，“怎么办”由助手准备，“要不要办”由员工确认，“批不批”由上级在原页面自己办。** 指南与评审名单不再是助手能力的唯一来源，但也不会变成“助手替人审批”。

## 一、你的四个决定（已记录）

| 议题 | 你的选择 |
|---|---|
| 读取范围 | 业务数据 **+ 管理资料**（员工账号、门店、参数、操作记录等）——都按该员工的岗位权限 |
| 准备动作边界 | 审批/作废/冲红/封存/收付款确认这类**只指路，不准备确认卡** |
| 评审适用范围 | **只解决权限与额度不足**；业务规则明确禁止的不评审 |
| 相关上级 | **本店店长**；申请人是店长本人时转**集团管理员**（由服务端规则判定，模型不能自己选人） |

## 二、三层边界（不随“放开”而改变）

1. **权限判定在接口，不在模型**：助手的每次写入都走“待确认卡片 → 员工确认 → 原接口”，确认后由原接口用该员工的会话、CSRF、门店、版本号和幂等键执行。岗位/门店/状态检查依旧是权威。
2. **审批不由模型产生**：助手不生成审批结论、不代表任何人批准、不改变权限；审批类动作只在原业务页面由有权限的岗位本人办理。
3. **凭据与文件永不进入模型**：登录会话、密码、密钥、品牌图片、部署配置、原始附件、导出文件、期初导入一律不可见；`DENIED` 与 `SECRET_KEYS` 清洗保持不变。

## 三、P0（本轮已实现）：读取按岗位放开 + 权限可回答

- 查询不再受“评审名单”限制：员工岗位能读到的页面，助手都能查（含 `员工账号`、`操作记录`、`门店资料`、`参数与个人密码`、`经营主体与账户归属`、`数据复核`、`每日汇总`、`原有单据`、`整车请款与批量导入`）。可见操作从 285 项增至 303 项。
- **写入仍严格按评审名单**：`POST /api/users`、`POST /api/stores`、`PUT /api/stores/{id}` 等一律不可准备；`POST /api/flow/cases` 这类已评审业务写入保持可用。
- 新增权限提示字段：`list_operations` 返回 `role_may_read`（该岗位能否读，静态规则可直接判定时给出）与 `role_note`（“这个入口只对系统管理员开放”这类说明）。业务领域不给该字段，表示**由接口按岗位与门店判定**，助手应调用一次、用真实的 403/409 回答。
- 系统提示同步：先看 `role_may_read`，不要再回“我这边没有入口”；审批类只说明入口与所需资料。
- 仍然关闭的领域：`auth`、`local-preview`、`branding`、`settings`、`business-assistant`、`export`、`health`、`workflow-guides`、`opening-import`（另有文件/下载/导出/`.csv|.docx|.pdf` 正则拦截）。

## 四、P1（下一步，已定规则）：写入按风险分类放开

- 员工岗位能写的模块，助手都可以**准备确认卡**；但永远不准备：
  1. 审批、驳回、作废、冲红、封存、收付款确认、实际收货/质检结论等**判断类**动作；
  2. 账号、权限、参数、模板的变更；
  3. 文件、导出、期初导入。
- 风险分类写成**代码里的可评审表**，并加测试：**新出现的路由默认按“人工原页面办理”**（fail-closed），并能在一次巡检里列出“尚未分类的新路由”。
- 确认卡继续显示字段级取值与原页面入口；原接口的岗位、状态、版本、幂等检查不变。

## 五、P2（再下一步，需单独一轮）：权限不足时的“向上级评审”

- 助手只能**准备**一张“评审申请”；员工确认后由原接口创建一条任务（新任务类型，含：想办的操作、业务对象与原单链接、当前被拒的服务端原话、申请人、申请时间）。
- 收件人由**服务端规则**决定：本店店长；申请人是店长本人 → 集团管理员；店长缺该模块权限时继续向上。模型不能指定收件人。
- 上级侧：在“待我评审”里打开**原业务页面**，用自己的岗位办理或驳回并写理由；全过程不可改写、不可删除。
- **硬性限制**：评审只解决“权限/额度不足”。业务规则明确禁止的（质检不合格不得出库、未收款不得出库、未授权增项、未到货不得结算等），助手必须回答“这条规则不能通过评审绕过”，不得生成申请。否则就是把“找领导绕过规则”做成了流程，等同模型自造审批。
- 需要的配套：新任务类型与迁移、上级待办页面、通知与超时（到期未处理如何处理）、审计与导出、以及拒绝/重复申请/跨店/过期版本的测试。

## 六、仍然不做的事

- 助手不自动提交、不代替员工确认、不代替上级审批、不改变权限、不执行命令或代码、不访问任意网址、不读写服务器文件。
- 不因为“放开了名单”就放宽：门店范围、角色校验、版本校验、幂等、附件安全、现金与库存事实的确认边界全部照旧。
- 不用助手做员工监控或绩效排名；不把“助手建议”当成任何业务事实。
