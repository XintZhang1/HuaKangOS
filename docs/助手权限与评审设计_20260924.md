# 业务助手权限范围与“向上级评审”设计 · 2026-09-24

> 实现状态（2026-09-24 首版；2026-09-25 按你的两条限制重做）：**P0 读取按岗位放开**；**P1 写入不再有白名单**——助手以员工本人身份调用接口，能不能办由接口判定，被拒时提示并引导提交评审申请；**P2 评审申请**只接受系统自己记下的被挡记录，类别与收件人由服务端判定。唯一保留的边界是非业务面（凭据/部署/附件/导出/旧单据 CRUD/多部分上传/办理评审申请本身）。逐条证据见 [验证报告](verification/assistant-write-scope-and-escalations-20260924/测试报告.md)。

你的原话：“我们能不能允许 deepseek 完成已有指引或者已有评审名单之外的工作？就是需要他按照员工的职责范围和可使用模块来判定这个任务能否完成，如果需要更高权限，允许向相关上级提交评审。”

一句话结论：**“能不能办”由系统回答，“怎么办”由助手准备，“要不要办”由员工确认，“批不批”由上级在原页面自己办。** 指南与评审名单不再是助手能力的唯一来源，但也不会变成“助手替人审批”。

## 一、你的四个决定（已记录）

| 议题 | 你的选择 |
|---|---|
| 读取范围 | 业务数据 **+ 管理资料**（员工账号、门店、参数、操作记录等）——都按该员工的岗位权限 |
| 准备动作边界 | 审批/作废/冲红/封存/收付款确认这类**只指路，不准备确认卡** |
| 评审适用范围 | **只解决权限与额度不足**；业务规则明确禁止的不评审 |
| 相关上级 | **本店店长**；申请人是店长本人时转**集团管理员**（由服务端规则判定，模型不能自己选人） |

## 二、三层边界（不随“放开”而改变）

1. **权限判定在接口，不在模型**：助手的每次写入都走“待确认卡片 → 员工确认 → 原接口”，确认后由原接口用该员工的会话、CSRF、门店、版本号和幂等键执行。岗位/门店/状态检查依旧是权威。
2. **审批不由模型产生**：助手不生成审批结论、不代表任何人批准、不改变权限；审批类动作只在原业务页面由有权限的岗位本人办理。
3. **凭据与文件永不进入模型**：登录会话、密码、密钥、品牌图片、部署配置、原始附件、导出文件、期初导入一律不可见；`DENIED` 与 `SECRET_KEYS` 清洗保持不变。

## 三、P0（本轮已实现）：读取按岗位放开 + 权限可回答

- 查询不再受“评审名单”限制：员工岗位能读到的页面，助手都能查（含 `员工账号`、`操作记录`、`门店资料`、`参数与个人密码`、`经营主体与账户归属`、`数据复核`、`每日汇总`、`原有单据`、`整车请款与批量导入`）。可见操作从 285 项增至 303 项。
- **写入仍严格按评审名单**：`POST /api/users`、`POST /api/stores`、`PUT /api/stores/{id}` 等一律不可准备；`POST /api/flow/cases` 这类已评审业务写入保持可用。
- 新增权限提示字段：`list_operations` 返回 `role_may_read`（该岗位能否读，静态规则可直接判定时给出）与 `role_note`（“这个入口只对系统管理员开放”这类说明）。业务领域不给该字段，表示**由接口按岗位与门店判定**，助手应调用一次、用真实的 403/409 回答。
- 系统提示同步：先看 `role_may_read`，不要再回“我这边没有入口”；审批类只说明入口与所需资料。
- 仍然关闭的领域：`auth`、`local-preview`、`branding`、`settings`、`business-assistant`、`export`、`health`、`workflow-guides`、`opening-import`（另有文件/下载/导出/`.csv|.docx|.pdf` 正则拦截）。

## 四、P1（2026-09-25 按你的裁定重做）：助手以员工本人身份调用，只有两条限制

你的原话：“deepseek 是天然可以把好几个步骤结合起来一起做的……你就让它以当前员工身份去调用 api，如果调用到了被权限拒绝的 api，你就让它提示用户哪些是需要向上申请的，问他要不要申请。如果没有这种，你就让他自由调用就好了。再就是创建一个中间流程（比如创建订单），那它的前序流程都需要 ai 询问完成……只有这两个限制，其他的限制都应该去掉吧。”

实现：

- **去掉按动作名/路由的白名单与禁用词闸门**。助手就以员工本人的会话、门店、岗位调用已评审的业务接口：能办的就准备、该连着做的就连着准备（读原单 → 读目录/可办事项 → 准备这一步 → 继续下一步），不再由助手替接口判断“这一步能不能准备”。
- **限制一：权限由接口判定，被拒就提示走评审**。原接口返回 403（岗位/门店/权限）时，助手拿到系统原话，告诉员工“这一步需要更高岗位权限”，并读 `GET /api/escalations/refusals` 里那条被挡记录，问要不要提交评审申请（类别由服务端判定，`rule` 类不能提交）。接口因业务规则拒绝（409/422）时说明规则，不改权限、不绕流程。
- **限制二：中间单据必须先补前序**。准备新建订单/工单/开票申请这类流程中间的单据时，助手会拿到该业务自己声明的前序字段（`prerequisites`：相关业务、客户、车辆、原单等），必须先逐项向员工确认前序事实是否已完成或选定，缺哪一项先补哪一项，不能凭空新建。
- **仍然不放开的只有“非业务面”**：登录与凭据、部署与品牌设置、原始附件与下载导出、期初导入、任意旧单据 CRUD、多部分文件上传，以及**办理评审申请本身**（`POST /api/escalations/{id}/actions/{action}`）——这些不是流程步骤，是安全边界；凭据/文件/导出从不进入模型。
- 确认卡机制不变：每一步仍各自生成一张卡，员工逐张核对点击；点击前助手不得声称已办理；原接口的岗位、门店、状态、版本、证据与幂等依旧是权威。

## 五、P2（已实现 2026-09-24）：权限不足时的“向上级评审”

- 助手可以**准备**一张“评审申请”；员工确认后由原接口创建一条申请。申请必须引用**系统自己记下的被挡记录**（`escalation_refusals`：接口返回 403 时由服务端写入，含操作、状态码、系统原话和按原话判定的类别）。
- 类别由服务端从记录判定，申请人选不了：`rule`（业务规则）在提交时被 422 拒绝，只有 `authority` / `amount` 能提交。“业务规则不允许”因此不可能被改写成“权限不足”绕过规则——这是“找领导绕过规则”与“岗位不够请上级定”的分界。
- 一条被挡记录只能用一次、只能本人用、只在本店有效、超过 24 小时失效。
- 收件人由**服务端规则**决定：本店店长；申请人是店长本人 → 集团管理员；集团管理员只看发给自己的申请，不会抢店长的队列。岗位判定一律用**当前门店的实际岗位**，不是账号级岗位。
- 上级侧：在“待我评审”里打开**原业务页面**，用自己的岗位办理或驳回并写理由；全过程不可改写、不可删除；不能自己批准自己提交的申请。
- **硬性限制**：评审只解决“权限/额度不足”。业务规则明确禁止的（质检不合格不得出库、未收款不得出库、未授权增项、未到货不得结算等），系统自己的拒绝记录就是 `rule` 类，提交时直接被拒；助手也不得声称这类事可以走评审。
- 需要的配套（均已落地）：新表与迁移（`h47e_escalations` + `h48f_escalation_refusals`）、上级待办页面、审计，以及拒绝/重复/跨店/记录归属/过期/门店岗位判定/管理员队列范围的测试。

## 六、仍然不做的事

- 助手不自动提交、不代替员工确认、不代替上级审批、不改变权限、不执行命令或代码、不访问任意网址、不读写服务器文件。
- 不因为“放开了名单”就放宽：门店范围、角色校验、版本校验、幂等、附件安全、现金与库存事实的确认边界全部照旧。
- 不用助手做员工监控或绩效排名；不把“助手建议”当成任何业务事实。
