# 业务助手交接给 GPT‑6 Pro

整理日期：2026-09-26。以提交 `1f884fb` 的实际代码及本地 `web/businessassistant.js` 输入光标修复为基线。此次只清理交付目录和整理文档，未修改助手业务实现。数据库迁移头为 `h51i_proposal_questions`，月结定义 21、现金定义 7。

## 1. 先理解这个系统

huakangos 是多门店经销业务系统。业务助手是员工操作入口：模型查询员工可见资料、准备确认卡；员工点击后，服务器才调用原业务接口。它不是编码代理，也不拥有独立的业务权限。

业主 2026-09-25 的决定覆盖早期“审批类动作只指路”和动作名白名单设计：在已评审业务接口范围内，用员工本人身份准备操作，让原接口判断权限。业务层额外要求是：403 后解释可申请向上评审；创建中间单据前核对原单、客户、车辆等前序事实。岗位、门店、状态、版本、幂等、凭据及人工点击确认始终保留。

**“无动作白名单”不等于“任意 API 可调用”。** `business_assistant_capabilities.json` 仍是写入路由的已评审边界。新 API 不会自动获得助手写入能力。登录凭据、系统配置、原始附件/导出、期初导入、旧版任意 CRUD、办理评审申请仍封闭；具体以 gateway 中的规则为准。

模型说“已办好”不是业务事实，只有卡片原接口成功才是。钱是整数分、数量是整数千分之一；不得伪造收款、收货、审批、客户同意或关联编号。

## 3. 一条消息如何走完

1. 员工选择单店，创建本人会话。会话冻结 `owner_id/store_id/owner_role/access_version`；读会话时还连接 User 检查账号有效及权限版本，权限变化不会继承旧会话权限。
2. 消息携带 `request_id/content/thinking`。同编号同内容同思考设置返回原会话，不重复调用；同编号不同输入返回 409。
3. `_conversation` 取得有版本锁的 `busy_token/busy_until`，保存用户消息。租约为本轮时长上限加 60 秒，每个模型轮次续租。
4. 组装系统提示、系统日期、岗位/门店、待办与最近结果、已查询的操作字段和历史消息。历史最多最近 30 条、24,000 字符。工具结果会脱敏及截断，不是全量原始记录。
5. 调用固定服务商地址。模型可连续读取目录、查询数据、准备多张卡；每次工具返回后继续模型轮次。准备工具只写助手提案，不写业务事实。
6. 每轮向模型更新数据库实际新生成卡片数；对“没有生成卡却声称已经准备好”的答复做一次纠正。这是有限启发式检查，不是完整事实验证器。
7. 正常结束写助手文字消息并释放租约；异常/超时记录问题、保留已经准备的卡。流被取消时释放自己的租约并保存停止提示。

TOOLS 共 10 个：`list_operations`、`inspect_operation`、`read_data`、`find_cases`、`get_case`、`prepare_case_action`、`prepare_customer_contact`、`prepare_operation`、`record_issue`、`find_workflows`。**没有 confirm、执行代码、SQL、文件路径或任意 URL 工具。**

`find_cases` 先按原 API 分页，再过滤本人负责的单据；本页无结果不代表全库无结果，要检查 `has_more`。`get_case` 返回原单 actions 和 assistant_guidance；模型应选择真实动作，不能拼动作名。两个专用准备工具会读最新记录/版本。

## 4. 网关与身份边界

`_operations()` 从 FastAPI 路由读取真实 schema。GET 在允许的业务/管理域内发现；POST/PUT 必须在已评审 JSON 中。随后 `_operation`、`_parameters`、`_declared_dispatch` 等检查封闭路由、参数和实际匹配对象，避免通配路径落入另一个新增静态接口。

`invoke()` 使用进程内 `httpx.ASGITransport` 重新请求原 API。Cookie、CSRF、X-Store-ID 来自当前 HTTP 请求/主体，不来自模型。原 API 再鉴权、再验证门店、版本、状态、证据，业务事务也由原 API 提交。助手 DB 事务在嵌套请求前结束。

注意 `CLASSIFIED_BLOCKED_WRITES` 当前主要是一份分类清单，网关执行代码未直接引用它做拒绝；这些写路由实际由“不在 reviewed JSON 中”、域过滤等机制排除。维护 capability JSON 时不能以为这份常量会提供第二层兜底。

`role_may_read/role_note` 是部分管理入口的说明性投影，原接口才是最终权限边界。响应过滤密码、令牌、原始文件等字段，但允许的客户业务资料可能进入模型上下文；不能宣称这套助手只外发匿名汇总。日报 AI 与此模块的配置和数据合同不同。

## 5. 确认卡：准备和执行是两个阶段

`prepare_proposal` 先校验操作和字段，生成规范化 payload。原接口支持 request_id 时，由网关生成。相同会话、操作和业务内容（忽略 request_id）的活跃卡去重；executing/uncertain 的重复意图拒绝重新准备。

卡保存 owner/store/role/access_version、operation_id、payload、digest、过期时间，以及本轮 request_id、step_order/step_label、questions。digest 是上述身份/操作/payload 的 SHA-256，不是可替代登录鉴权的签名。questions 和分组信息不在该 digest 中；只有服务器能写提案这些字段。

前序提示同时进入工具结果的 `prerequisites` 和卡片 `result.prerequisites`，页面显示“办理前请先确认”。它是提示及原接口守卫的配合，目前没有独立的前序事实确认账本，也没有可自动绑定尚未生成 ID 的依赖图。

员工点击 confirm 后，`decide_proposal` 检查会话归属、digest、pending、过期、岗位和授权版本、必填答案；合入员工答案后重新按原 schema 校验。先把卡持久化为 executing，才调用原接口。2xx→succeeded，4xx→failed，5xx/异常/超时→uncertain。**不自动重放业务写入**，不确定时先核对原记录。

这不是横跨“提案表 + 原业务表”的单个事务：存在原业务已提交但卡片结果尚未保存的窗口，uncertain 就是必须保留的状态。重复点非 pending 卡不会再执行；原 API 的幂等也继续生效。

批量接口按请求数组顺序逐张调用同一个决定函数，各自事务。某张失败仍继续其他张，**不是整批原子操作，也不是依赖失败即停止的工作流引擎**。前端“按顺序全部确认”只是按展示分组组装数组。需要上一张成功生成 ID 的后续卡，应在成功后重新读取再准备。

## 6. 必填项、前端行为与 SSE

`questions` 每卡最多 12 项，每项 key/label，最多 20 个字符串 options，默认 required。无 options 用文本框，有 options 用下拉。准备时若缺字段，代码尝试用类型占位值做 schema 探测，探测值不存卡也不提交。

确认带 `answers: {key: string}`。仅合入卡声明的键；`values.x` 放入 body.values，其他键精确命中优先，否则带点键回退末段。不是通用深层 JSON 路径编辑器。员工答案仅用于这次 execution，当前代码没有另存完整最终 execution/answers 快照，审计原业务事实需结合原接口记录。

前端按轮次和步骤分组、翻页、展开收起。未填必填项禁止确认及向后翻页；一组有未填项则不能批量确认。已存在的未提交光标修复会在 input 时只更新按钮，不重建输入框；change 时再重画卡栏。此次保留了这份修改。

确认后自动继续是前端逻辑：无待确认/执行中/不确定卡、无错误且服务 ready，再通过最近助手文本中的“下一步/确认后/继续”等词判断是否再发送一条“继续处理下一步”。这是启发式续聊，不是服务端持久化任务调度。离开助手页会继续收流；换店、退出登录会中止并清除旧上下文。

下游 SSE 事件：`status`（thinking/responding/tool）、`delta`、`error`、`done`（最终会话）。上游必须收齐合法结束标志和完整工具 JSON 才执行工具。原始 reasoning 仅在当前内存工具链携带，不展示、不写消息表。普通正文流增量先经过敏感内容处理。

## 7. 文件资料与帮助搜索

文件预览支持 CSV/TSV/XLSX/DOCX/TXT；单文件 5 MiB、20 文件、总文件 20 MiB，multipart 请求上限 21 MiB。每文件最多 1,000 行、50 列，另有 ZIP 展开体积、压缩比和文本体积保护。解析在内存内，不保存原件、不执行公式、宏或外部链接。

员工选行/段落，审阅发送文本并显式发送后才进入模型。解析结果是不可信业务资料，不是凭据事实；附件上传/病毒扫描/签回要求仍通过原页面处理。虽然业主取消了业务按行限额，解析和上下文仍有资源截断边界，不能把截断后的文件称为已完整导入。

帮助内容来自 `web/workflow-guides.json`。全局帮助搜索不应为了查操作说明而查客户记录；AI 推荐只能返回现有指引 ID。跳转助手入口只填未发送草稿，不应自动发送。构建源在 `docs/workflow-source/`；用 `scripts/build_workflow_guides.py` 生成并 `--check`，禁止手改生成文件或用 draft 作为发布结果。

## 8. 评审申请

原 API 的真实 403，或带权限/额度语义的 422，由异常处理器记录 `escalation_refusals`。类别由服务器按原提示关键词判定，无法识别归为 rule；不是模型自述。记录失败会写日志并保持原拒绝，因而存在“被拒但没有凭据”的可能。

助手先读 `/api/escalations/refusals`，再准备 `/api/escalations` 申请卡。创建时要求凭据属于本人、本店、未使用、24 小时内，rule 一律拒绝，类别不能重标。收件人按当前门店岗位确定：普通员工→本店店长，店长/管理员→集团管理员。管理员只看到 admin 队列，自批禁止。

评审只记请求与轨迹，不改角色、不产生业务事实。上级在原业务页面办理，再到评审页 claim/done/reject；申请人可按原规则 cancel。助手不能准备评审处理动作。

网关目前仅为 403 附上升级提示；409/422 没有提示，即使其中某个 422 被 refusal 服务认定为权限/额度不足。请勿将所有失败一概解释为缺权限。

## 10. 建议接手后优先处理的具体问题

以下是此次静态阅读发现，**未在本次修改或做专项复现**，不要当作已修复：

1. **统一提示词和网关合同。** SYSTEM_PROMPT 后半段仍有“审批、驳回、作废、收付款确认只在原页面”的旧句，与业主决定和当前网关冲突；`_operations` docstring 也过时。不能误把旧句恢复成动作白名单。
2. **统一流式/非流式资源限制。** stream.py 的 30 工具限制和正文限制仍在，所谓“删除回复上限”只删除了向服务商发送的 token 参数。优先复现 31/60 张同回复准备在两条通道的差异，再设计统一保护。
3. **100 vs 200 张。** 后端最多挂 200 张，批量最多 100，前端不会分块；超过 100 的“全部确认”预计被 schema 拒绝。要显式分组或分批，并保留每张原校验及失败结果。
4. **补齐 questions 的严格数据合同。** 服务器检查非空及字段 schema，没有单独强制 answers 属于 options，也没有严格拒绝多余答案键（目前忽略）；候选值/名称映射和深层字段支持有限。不要把下拉框当权限保证。审视最终执行内容是否需要独立不可变快照。
5. **前序链不是依赖引擎。** step_order 只影响展示/请求顺序，批量失败不停后续；没有 future-ID 绑定。确认后的自动续聊靠文本正则。设计更稳的依赖表达前，保留原接口和每步人工确认。
6. **活跃卡窗口并非真正无限。** session_view 对数据库仍是 pending 的过期卡也纳入 open 查询，再以 220 截断；大量旧过期卡、executing/uncertain 累积的情况需要覆盖。显示为 expired/uncertain 不代表一定已写回状态。
7. **修正错误文案。** `_conversation` 仍有“10轮上限”、上下文“最近80项”旧文案；前端缺必填项提示使用了 Python 风格 `%` 表达式，会导致错误提示值，应专项验证。
8. **拒绝类别与提示。** 403 并不必然是可升级的权限不足；目前 hint 对 403 一概给出，申请阶段才由真实 receipt 拦截 rule。422 权限/额度凭据又没有网关 hint。可改进解释的一致性，绝不允许模型指定类别绕规则。

建议按“确认安全与幂等 → 流式批量一致性 → 必填答案 → 依赖与续聊 → 飞书入口”拆分评审。不要把这次清理误认为上述问题均已解决。

## 11. 飞书：只有需求，没有实现

业主希望以后通过企业自建应用、私聊或 @机器人使用同一助手。网页业务入口仍保留；不用旧 maintenance 的飞书代码审批工具（已随废弃工具删除）。

必须绑定飞书员工到真实系统账号，按当前门店岗位执行；不能使用共享机器人管理员身份。推荐默认私聊，群里只提示去私聊，不能泄露客户/金额。绑定方式（网页一次性码或管理员维护）、默认门店与切店、卡片是否在飞书确认、通知范围仍需具体产品决定。

设计事件 event_id 去重、回调验签/防重放、提案归属/digest/过期检查，按渠道留审计。飞书确认也必须进入原业务 API，不能直接写业务表。现网关依赖浏览器 Cookie/CSRF，接渠道时需认真设计受信主体适配，不能伪造用户会话或新增权限旁路。确认卡 digest 本身不是可公开使用的授权票据。
