# 核销后找到原物资

本文件对应建设计划阶段三的异常出口，承接第三版物资调拨已经确认的运输损失。领域模型、接口和员工页面已正式注册到本轮 `n46a_operations_extensions`，原 `m359` 历史迁移及第二版调拨语义保持不变。真实浏览器通过正式 CLI 在新临时库执行当前 Alembic head 后启动，未额外挂载临时路由或补建草稿表。实际清算、报表及联合验收由总接线完成，下文分别记录领域行为与验证状态。

## 不变的原账和新的事实

- 找回记录引用原 `TransferLossPosting`，沿用原调出/调入两张 Case。双方共享窄范围的实物协调记录；原损失、原 movement、原现金和原店间结算均保留。
- 每份找到数量必须可辨认且有本店实际原件。已完成找回的合格件加实际处置坏件，累计不超过该原损失数量。不同复验结果按可辨认的份分别办理；当前一份只记录一个复验结果，不在同一份内假定平均合格率。
- 仅原调出店实际收到、复验合格、双方独立批准后，才能登记原物资入库。调入店找到的合格件须先由其库管实际发回，再由原店库管登记实际接收及复验；发回或接收证明本身不产生可用库存。
- 当前保管店复验不合格的物资，由其库管在批准后确认实际处置。原店财务核对处置后结束该份实物；不产生库存、不恢复原成本、不冲回承担。零成本物资同样有真实数量、核对、复验和入库。
- 一笔在办找回锁整笔调拨。专用找回命令始终可办理获授权的核对、处理、赔付条件和原退款，避免“要求先退款但又锁死退款入口”的循环。原已付款清算的到账确认、未执行清算的取消/拒绝仍保留事实出口。

恢复原成本按原损失累计合格数量计算：`原损失成本 × 累计已恢复合格量 // 原损失数量`。本次取累计差额，最后合格份额保留原尾差；实际处置坏件仍归原损失。承担冲回再按原恢复成本累计分摊调入方原承担，调出方取剩余差额，两方之和恰好等于本次恢复成本，不按当前平均进价重估。

例如原损失3件、100分、双方各承担50分，依次恢复0.333、0.667、2件，原成本分别11、22、67分，累计100分；两店承担冲回累计各50分。若先找到并实际处置0.5件坏件，再恢复2.5件合格件，只恢复83分，剩余17分仍为原损失。

## 岗位与动作

| 动作 | 经办与前置 | 原子事实及下一责任 |
| --- | --- | --- |
| 登记找到 | 本店库管；明确原第三版损失与可处理余量 | 本店找到原件、暂时保管事实；另一店库管核对原关联 |
| 核对原关联 | 另一门店另一位库管 | 只证明本人核对原发出、拒收或损失关联，不代找货人作证 |
| 复验 | 当前实际保管店库管 | 明确合格/不合格及原件；追加本人检查，不改旧检查 |
| 实际发回 | 调入店找到且双方已核对、本店复验合格 | 只记录实际运输；原店待收到，不造接收或库存 |
| 实际收到与复验 | 原店库管；对方已有实际发回 | 记录整份实际收到和质量；仍不自动变成可用库存 |
| 原成本方案 | 原调出店财务；两方核对、最终实际复验齐全 | 冻结原复验、恢复量价与承担；两店主管分别复核 |
| 批准/拒绝 | 两位不同主管，均未参与本次找到、实物或方案；管理员无例外 | 独立原件；拒绝返回核对，下一版追加，不覆写 |
| 合格件实际入库 | 原店当前库管；当前方案批准 | `StockMove(purpose=transfer_found)`、原成本恢复和承担反向记录一次提交 |
| 坏件实际处置 | 当前保管店当前库管；当前方案批准 | 真实处置原件；原店财务随后核对，价值仍为原损失 |
| 撤回误关联 | 原申报人或本店主管；尚未实际发回、接收、处置或入库 | 保留原找到观察，追加误关联理由与原件，释放本次锁；不能把真实运输或入库抹掉 |

任务使用原 Case 的 `transfer_found_{id}_...` 前缀、当前门店岗位分派、约定核对日期。经办人只证明自己的事实；可引用本店其他获授权员工上传的原件，不要求凭据上传者和动作经办人必须相同。系统生成草稿、未过文件检查及另一店的附件均不可借用。

找到物资后仍在重新运输中的未到货部分保留真实在途及待办，不假定已到。目前不提供对该次找回运输再失联后自动结案、重复核销或清空在途的动作。

## 承担冲回与真实清算

本次恢复产生独立 `GoodsSettlement` 两条反向记录，每条精确引用同店原损失承担条目。原调出方负、原调入方正，金额等于本次调入方承担冲回。原损失已清算时，此新记录成为反向应付/应收；原损失尚未清算时，与原往来合看为净未结金额。旧清算金额、现金和核销记录不修改。

实际清算以新来源 `material_found` 配对 `transfer_id/posting_id/recovery_id/original_id`，由双方财务按真实付款/到账分别确认。不能因两条往来相反就伪造两笔银行现金。若要抵销尚未结清的原应付，须另行保存双方确认的抵销分配及额度守恒，不得悄悄改原清算总额。领域测试验证已结清的原往来恢复后追加反向记录，原清算和现金完全保留；实际清算接线及专项结果由本轮总验收记录补充。

## 找到后的外部赔付条件与原款退款

系统不判断法律赔付责任，不能仅凭找到物资自动宣布应退赔款。实物和原成本可以先据实处理；已有外部赔付时状态保留为“实物已处理，原赔付仍需核对”。

1. 本店财务引用同一原承运人/保险公司已经实际确认的处理条件和原件，明确**新累计赔付目标**，可以确认仍维持原目标。目标不得超过原已批准目标或找到后本店剩余承担。
2. 新条件追加到原 `TransferRecoveryPlan`，由另一名本店主管独立复核；`GoodsTerms` 记录本次找到与新旧目标关系。拒绝或撤回保留历史，允许重新提交明确条件。
3. 原目标仍在审的，可从专用 `pending_cancel` 撤回未生效目标，再处理原有效条件；不是从旧入口绕开暂停。
4. 已实收超过新批准目标才形成原款应退。专用 `refund` 仍核对原入款、未退上限、原账户、银行流水、实际日期和财务凭据，追加原 `TransferRecoveryPayment` 与唯一 `CashEntry`；`GoodsRefund` 追溯本次找到及原条件。
5. 等待真实原款退回期间，未退现金继续占用原承担。不得新建收款或以另一条追偿重新占用同一损失。所有相关本店原条目完成条件确认且超收退清后释放找回锁；仍未收齐的新目标保持原追偿财务待办，不将找回结案等同于赔款到账。

往来方若主张维持的赔偿超过剩余原成本，需要经确认的新业务规则，系统不会假定保留、强制退款或追加额外收入。

## 接口及跨域约束

Router：`app.transfer_goods_recovery_api.router`，前缀 `/api/transfer-goods-recoveries`。

- `GET /origins/{transfer_id}`：本店第三版已损失批次、尚可找到数量、原单及版本。库管无成本字段。
- `GET /`：本店列表，可用 `transfer_id` 查询原调拨；超过500条明确拒绝，不展示被截断的结果。
- `GET /{id}`：本店可见协调事实、当前版本、本店原件；管理岗位才有成本及本店原追偿。
- `POST /`：`request_id, transfer_id, loss_id, version, case_version, quantity_milli, result, evidence_id, due_date, confirmed`。
- `POST /{id}/actions/{action}`：`request_id, version`（找回）, `transfer_version, case_version, values`。
- 实物与方案动作：`match, inspect, ship, receive, plan, approve, reject, dispose, restore, finish_bad, cancel`。复验含严格布尔 `passed`；实际动作含严格布尔 `confirmed`，假值不接受。
- 原赔付动作：`terms, terms_approve, terms_reject, terms_cancel, pending_cancel, refund`；携带当前原 `claim_id, claim_version`，复核带 `plan_id`，退款带 `original_id`（原实际入款）。

所有写操作同一事务提交，先共享 `MaterialTransfer` 版本锁、再本店 Case，再本次找回/原追偿，最后本店 Item 或 Account。冲突要求刷新、保留原请求编号；幂等收据只保存结果标识，重放重新按当前权限裁剪。集团多店办理拒绝。
