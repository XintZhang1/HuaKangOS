# 客户识别与人工确认

新建 v2 业务不再把同名同电话视为同一客户。电话仅提供匹配提示；员工明确选择当前获权的 `customer_id` 才复用档案。未选择客户时须填写姓名，电话可不填。输入电话匹配到当前可见档案时，须选择复用或明确确认另建独立档案；两者互斥。

业务新建表单在姓名和电话旁显示候选，不要求没有匹配的客户额外填确认字段。选择已有客户后，表单显示已选姓名和电话，相关输入锁定，本次业务不修改原客户身份、负责人、联系偏好或备注。如果 API 同时提交与已选档案冲突的姓名或电话，后端拒绝，而不猜测员工想选谁或想改哪项资料。

匹配和明确选择都使用当前单店 SQL 查询。销售、接待只能选择本人负责的客户；管理员、主管、服务顾问、客服按既有本店客户读写岗位访问。仅仅知道他人的客户 ID 或相同电话不会获得访问权限。另一负责人同电话而当前员工无权查看时，不返回其存在性提示；当前员工可以为自己核对的客户建立独立档案。集团汇总不能读取匹配明细。

接口 `GET /api/customer-choice/matches?phone=...` 返回精确电话匹配，`q=...` 用于员工主动查找获权姓名/电话。结果仅含 id、姓名和电话，最多 20 条并明确标记是否还有更多，不返回备注、客户价值、业务历史或集团身份资料。此功能不会创建或合并 GroupIdentity，不授权别店业务历史或附件。

v2 新建字段增加可选 `customer_id` 和 `confirm_new_customer`。新建原始业务的 request_id 幂等约定保持不变，失败匹配确认不提交客户、Case、待办或请求回执。历史 v1 调用显式传递 `flow_version=1` 并保留原有识别语义；不会重新关联既有 Case.customer_id，也不会推断历史身份合并。

客户主档的「新增」也只能建立新档案。同电话候选可以核对，但新增接口不会悄悄复用旧行再覆盖备注或允许联系设置；明确确认另建才产生新的客户记录。修改客户资料仍从原档案的版本化编辑入口完成，重新允许联系沿用主管权限，确认另建字段不会成为客户模型列。

自动验证见 `tests/test_customer_choice.py`，覆盖同名同电话拒绝、明确复用、明确另建、姓名/电话冲突、无电话、原联系偏好保留、负责人隐私、跨店、只读汇总、非客户岗位、业务请求幂等和 v1 保持。`tests/browser_customer_choice.py` 使用真实 Chrome、随机销售账号及隔离合成数据库验证 390px 表单、中文拒绝、选择后输入锁定、另建主档以及他人档案不可见。测试辅助函数只为指定合成数据显式选择唯一获权档案，不改变生产规则。

本次不提供自动去重、同电话归户、电话格式归一化合并、客户主档合并或负责人自动转移。多个独立客户共用电话是允许存在的业务事实；需要共享身份或负责人交接时，另走已有明确授权入口。
