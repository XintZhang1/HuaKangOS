# 日期、里程纠正与有效提醒来源

本模块沿用既有客户车辆、原观察和保险原单，已接入 `n46a_operations_extensions`。原 `m359` 检查点未包含本域；正式集成的专项、浏览器和整库恢复结果分开记录，自动验证不等于公司业务验收或正式启用。

## 业务边界

`VehicleObservation` 原观察始终保留。员工指向同店、同客户车辆、同种类的具体原观察，提交正确数值和依据；另一位本店主管复核后追加有效版本。管理员也不得批准自己申请的纠正。更正错误的原实际日期或公里数不会新建一次保养，不改变观察种类，也不修改车辆 VIN、客户身份、库存或现金。

人工登记的保险、保修截止日可以有据缩短；不再只能把错误期限继续延长。撤销误登记必须指向仍有效的原观察。已生效纠正不能删除或直接撤回；需另建指向当前有效版本的申请，形成连续的纠正链。仪表更换、里程重置、原保险批改重签不在此版范围内，不能用纠正入口伪装这些业务事实。

实际保险业务生成的观察只贡献原保单日期，不把当时程序带入的历史最大公里数或零当成实测里程；原字段不改写，没有实际读数时界面明确显示未知。人工纠正入口拒绝编辑此类观察。

保险观察失效须有同原报价的实际出保结果、终止方案、独立批准、匹配摘要的客户同意、已执行终止和各自原单附件。只提出申请、部分退款、外部拒绝、补件或未出保终止均不会被推断成已生效保单失效。附件证明的是本次原件关联及扫描可用，不代表系统认证外部结果真实性。

## 办理和异常出口

| 动作／经办岗位 | 入口与必要事实 | 原子效果、下一责任人 | 文件与超时／撤销 |
|---|---|---|---|
| 建立申请：服务顾问、客服、本人客户销售／接待、主管 | 同店已启用客户车辆、具体原观察、车辆版本、有效观察摘要；原种类不变 | 建立专用 `observation_correction/v2` 申请及申请人提交待办；有效观察尚不变化 | 原件可随后上传；到期日为当日，逾期仍待人工办理，不自动批准 |
| 提交：申请人或主管 | 本申请内获权可读、扫描通过的非生成原件；邻近有效实际观察不矛盾；无同原观察待复核申请 | 冻结方案进入复核；选择本店另一位主管；相关提醒暂挂外联／结案 | 主管可复用本单原件，不强制重复上传；提交后仍可明确撤回 |
| 批准／拒绝：另一位主管 | 当前申请版本、本次核对原因、原件；批准再验有效摘要、前后实际日期／里程 | 批准追加生效版本并失效有关旧提醒；拒绝只关闭申请；所有事实、任务和请求回执一次提交 | 不能自批，不能批准过期方案；拒绝或撤回解除待复核挂起，旧提醒可恢复正常办理 |
| 撤回：申请人或主管 | 申请尚未生效、当前版本、原因 | 追加撤回事件，关闭本申请任务；不修改原观察 | 已生效／已拒绝申请不得撤销，需新建纠正 |
| 检查提醒：主管、服务顾问、客服；独立定时进程 | 有效规则、现任经办／批准岗位、有效基准、独立实际里程来源 | 只新增内部待办，冻结基准和当前观察 ID／纠正版本、规则参数；旧任务与新任务分别保存并链接 | 不发送客户消息；当前周期已完成或人工取消不会因同日公里数更正重发 |
| 原保险失效同步：原保险实际终止事务；受权岗位显式复核 | 完整已执行原终止链，经办读取权限、原客户 VIN 和报价一致 | 追加保险基准失效，关闭有关仍开放的旧提醒；不动原保险观察、收退款和库存 | 无自动延保；来源缺失或摘要不符则拒绝推断，不以退款代替终止 |

待复核提醒允许接手、内部核对、转交和取消；拒绝客户外联以及按原基准结案。生效后，开放的受影响原提醒关闭并保留全部记录；已完成、已人工取消的历史状态不改。新任务不会假装是旧任务继续办理。

新提醒冻结准确依赖；纠正不相关的更早观察不会关闭已冻结的另一周期提醒。较早版本任务未保存“当时最近里程来源”，无法重建完整依赖，处理时保守标记为来源已变、保留历史，不反推旧里程。更正后的来源仍达到规则门槛且原周期仅因基准失效关闭，才建立有前后链接的替代任务。

## 数据与接口契约

八张追加表：`observation_corrections`（申请）、`observation_correction_events`（提交／独立复核／撤回）、`observation_correction_effects`（单链有效版本）、`observation_insurance_invalidations`（原保险已执行失效）、`observation_reminder_bases`（本次规则与实际来源快照）、`observation_reminder_invalidations`（旧任务失效原因及原状态）、`observation_reminder_replacements`（前后任务关系）、`observation_correction_receipts`（请求回执）。本域禁止应用内覆盖或删除，恢复还要核对配对流程事件摘要。数据库管理员仍有技术修改能力，这不是密码学防篡改承诺。

| 接口 | 返回／请求 |
|---|---|
| `GET /api/observation-corrections/catalog` | 当前单店获权车辆及岗位能力；销售／接待按现客户归属限制；多店汇总拒绝 |
| `GET /vehicles/{id}` | 原观察的有效投影、原记录 ID、纠正版本、业务来源、是否实测，以及本车申请 |
| `POST /cases` | `request_id, vehicle_id, vehicle_version, observation_id, base_digest, operation, proposed, reason`；替代值仅四字段 `observed_date, odometer_km, valid_until, source_reference` |
| `GET /cases/{id}` | 冻结申请、目前有效值、事件、获权附件与可办理动作 |
| `POST /cases/{id}/actions/{submit,approve,reject,cancel}` | 请求编号和申请版本；提交需原件，复核需原件及原因，撤回需原因 |
| `POST /reminders/generate` | 按当前有效来源生成、跳过规则的说明；同请求精确重放，不自动重试冲突 |
| `POST /insurance/{case_id}/sync` | 原保险版本和请求编号；仅检查真实已执行来源，不制造终止事实 |
| 既有 `/api/flow/cases/{id}/files` | 沿用上传、扫描、隔离、私有字节与本单下载权限；不增加另一个文件存储入口 |

旧 `/api/customer-service/reminders/generate` 继续验证并精确返回原 `CareReceipt` 的经办、摘要和响应；旧请求不会升级为一次新周期检查。新生成器使用自己的不可变回执，既有旧生成结果不会重写。

所有写入都先选单店。独立 API 的重复请求比较经办人及精确内容；旧版本、不同请求复用标识、竞争操作均返回中文 409 并整单回滚。原观察事实与修正净投影分开，领域没有金额／数量过账。

## 集成与事务契约

| 位置 | 必要 hook 与顺序 |
|---|---|
| `models.py`、迁移 | 注册八表；由统一迁移 `n46a_operations_extensions` 冻结静态 DDL；不得改 m359 或更早迁移 |
| `main.py`、`flow_specs.py`、`flow_engine.py` | include 新 router；仅注册 `observation_correction/v2` 元数据 `SPEC`，无通用创建／状态动作；`can_read` 转专用 `can_read_case(db,user,row)`；Case 查询同样限制本客户销售／接待和单店明细，不能只加宽 READ_KINDS |
| 前端 | 加 `/static/observationcorrections.js`；路由 `observation-corrections/{vehicles,cases}/{id}` 调 `observationCorrectionsPage(section,id)`；客户菜单入口；session 清理调 `clearObservationCorrectionsSession()`；点击和表单自监听。可从具体客户车辆链接本页 |
| `customer_service.observe` | 在原观察插入事务中，先 `control_vehicle(db,user,vehicle_id,expected_version,active=True)`，不要在触碰版本之后再比较旧版本；用 `guard_observation_append(db,user,vehicle,values)` 替换原 raw-history 日期／里程／期限比较。原 schema、附件权限、确认、不可变插入及审计仍保留 |
| `customer_service._vehicle_info` | 当前实际里程改用 `effective_vehicle_values(db,vehicle)`；历史原观察列表保留；有效值与历史不能混称 |
| 原客户提醒动作 | 在既有 `_execute` 内、`_care` 的 Case 锁之前，先 `lock_reminder_vehicle(db,user,case_id)`；取得原 Case 后 `guard_reminder_action(db,user,row,action,values)`。生产入口仍是 `case_action`，不存在另一套临时适配动作 |
| 原提醒生成和 `customer_service.tick_reminders` | 统一委托 `generate_reminders(db,user,key,automatic=...)`，不能保留旧 raw-history 生成器绕过新来源。worker 同日任务指纹加入 `reminder_epoch(db)`；它包含提交、批准、拒绝、撤回、保险失效及原保险实际终止应用。旧 `CareReceipt` 查重须换为 `generation_receipt_exists(db,tick_key)`（本域回执），避免每轮取回同一批“已创建”响应重复报告；改变同日记录可再检查但不增加实际周期 |
| 保险实际出保 | 原保险 Case 锁后，更新 `CustomerVehicle` 前调 `control_vehicle`；继续保留原 `InsuranceResult.observation_id` 来源链接。本模块只把该观察投影为非实测，不反写旧公里数 |
| 保险已执行终止 | 原 `termination_apply` 和其原件已 flush 后、同一次 commit 前调 `sync_insurance_basis(db,user,source_case)`；这个函数不 commit，不回锁原保险 Case，源链完整才追加失效 |
| 保险由续保待办创建／关闭 | 同样先客户车辆控制锁再相关 Care Case 锁，并检验有效提醒来源，不能从被纠正／终止的旧提醒绕开挂起。已有保险创建流程的锁顺序须统一后才正式启用 |
| 已有历史实际终止 | 在车辆控制锁内按 `sync_vehicle_insurance_bases` 逐源校验并追加失效，生成器、worker 和原续保办理都经过该入口。客服只得到本人获权车辆的有效来源判断，不因此获得保险金额、文件或原单办理权；缺少完整出保／终止链则拒绝推断 |
| 备份／恢复 | 在原附件字节、扫描和保险／客户来源校验后调用 `observation_corrections_integrity.validate(connection)`；无本域表可兼容旧备份，部分缺表拒绝。有表时逐原观察／原文件／前后链核对，不能只验证空表或登录 |

锁协议：先 `CustomerVehicle` NOWAIT 并触碰乐观版本，再按 ID 升序 NOWAIT 锁本申请和有关提醒 Case。原保险可以持有自身 Case 后进入车辆控制；本模块只读取保险不可变事实，不反向获取保险 Case 锁。预约／维修里程如后续也写入本表，须加入同一协调入口。任何数据库锁冲突或乐观版本冲突整体 409，不自动换请求编号盲重试。

## 验证与实际限制

集成测试直接调用真实注册 API，已经删除临时 router、kind 与权限注入。原 `/api/customer-service` 日期里程写入、外联跟进／结案和提醒生成均走同一有效投影；`app.reminder_worker.run(once=True)` 调用生产 tick，检查同日提交、撤回和生效后的正确唤醒与去重。保险从续保任务建立、核价、授权和提交时再次验证原基准；已合法提交后才发生的外部实际结果仍可据实记录，不因客服复核而抹掉事实。

保存原款、库存和里程观察数的守恒断言；并发客户端验证单一有效链与单周期任务。每项后复制非空 SQLite 并跑领域恢复校验，原观察、申请方案、效力链、提醒基准和保险源链篡改必须拒绝。共同车辆控制会改变当前资料版本；提交前应刷新原页，过期表单仍返回冲突而不是自动覆盖。
