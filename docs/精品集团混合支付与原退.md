# 精品集团混合支付与原退

2026-09-22，实际检查点 `n46b-native-retail` 已完成原会员发行、精品原单收退款/实际退货、发票、积分、经营/物资统计与月结定义10的接线；公开动作仍需相应岗位、当前待办、原件、版本及独立规则批准。已移除 n46a-fix1 的临时只读隔离，但没有宣布公司验收或正式上线。最新实测及环境缺口以根目录交接和 CHECKPOINT_STATUS.json 为准。

以下保留详细业务约定；文末 n46a-fix1 隔离记录是历史。集团会员只做内部记账，不建设集团中心实际资金清算；公司规则和本机验收单独记录。

## 本版业务范围

本版只为客户已经实际接收、无待处理退货、且尚无实际收款、预收抵用或其它支付的精品单建立新集团混合付款方案。方案可以包括集团本金、集团赠金、消费券、次数套餐及随后分笔登记的现金。已有支付的原单不按新计划重分；集团混合预付款仍待单独建设。

每个方案冻结原商品行、商品与安装的分项金额、客户明确选择的原权益批次及每个券/套餐原整数单位的分摊。授权、占额、实际核销、实际现金及实际退货各有独立动作。没有任何动作可把保险代收款算作精品消费。

实际退回商品仍由原精品退货流程办理。检查不合格不能增加可售库存或退款额度，已完成安装的原保留费仍保留。本扩展读取新的 `RetailReturnPosting`；它不会自行确认商品已经退回。

## 公司必须明确批准的规则

集团 `BenefitRule` 原有 `service_code` 不证明商品适用。每个新商品用途必须先建立不可变附则，指向一个明确的原集团规则版本，并列出具体门店、物资及商品/指定安装范围。申请和批准须由两名不同主管办理；两人在每家选定门店均须有实际管理岗位。集团汇总权限不能代替这些岗位。

当前实现只有以下明确模式，没有默认选择：

| 配置 | 当前唯一支持值 | 业务含义 |
|---|---|---|
| `partial_return_mode` | `accumulate_original_unit` | 原实退按分累积到原券或套餐单位，凑齐才能恢复整份 |
| `expiry_mode` | `original_expiry` | 恢复仍保留原钱包到期日，不自动延期 |
| `pending_claim_expiry` | `none` | 待恢复非现金负债不自动清零 |

公司未明确接受这些约定，商品用途附则不能提交生效。已经发行的钱包不能补授新商品范围。正式发行时必须保存 `RetailGroupWallet`，同时绑定批准决定、附则及真实原发行流水；仅凭“当前规则已批准”不能认领旧批次。

尚不支持退货自动延长有效期、零头转通用余额、零头提前退发行现金或不同券/套餐单位相互凑整。这些是待公司确定的后续规则，不是当前功能。已过期的整份恢复必须显示原到期日及不可直接消费状态。

## 员工完整办理顺序

1. 主管建立未发行的新集团赠金、券或套餐规则，再从“精品权益商品规则”明确申请商品范围和原退约定。另一名获权主管亲自核对本单来源原件并批准。新批次发行时冻结此附则。
2. 销售或服务顾问完成精品实际接收后，核对本单客户付款授权原件并冻结原付款方案。这一步不占额、不扣款。
3. 当前财务待办经办人分别占额、核销每个原本金或权益批次；每步都核对原单、会员、钱包和占额版本。需要换人时由主管明确交接负责人和期限。
4. 现金从原精品单分笔登记。可收金额仅来自冻结现金份额以及已明确释放的未核销份额。释放占额不会制造收款或退款。
5. 库管完成实际原单退货后，同一事务记录原资金份额减少和非现金待恢复负债。未核销占额不能阻挡实际退货；已退部分也不能再核销，财务应明确释放剩余方案。
6. 财务分别办理原现金退款、本金/赠金恢复和已凑整的原券/套餐恢复。未凑整的券/套餐额度保持不可消费的原权益负债，不被当作现金可退。

本金、赠金逐分恢复；券/套餐按原核销的每个整数单位管理。不同单位之间不挪用退货份额。原现金退款指向真实 `PaymentLink` 与其原行分摊，不能把集团抵扣额度当成本店现金原款。

本店可查看本店实际核销和原退。A 店发行、B 店履约时，B 店可以恢复原钱包和形成内部往来，但不会获得 A 店原业务或附件权限。已恢复购买券的原发行退款仍须由原发行店按原发行现金、原账户和原规则独立办理；本扩展不增加履约店代退发行款的捷径。

## 原批次分摊与账目守恒

三个值分别保存，不用一个“支付金额”替代：

- `C`：本次抵扣面额；本金和赠金以分为单位，券/套餐为整份冻结面额。
- `P`：原批次真实发行实款的分摊。赠送和积分兑换来源的 `P=0`。
- `S`：冻结的集团与履约店内部结算额。

付款计划按明确选择顺序，针对各批次的允许商品/安装剩余金额分摊。每个原券或套餐单位分别冻结 `C/P/S` 到各行，剩余部分成为现金份额。每次实际退货仅消耗各原分摊的剩余值；最后一次收尽余分，不用重新计算累计最大余数而减少之前已确认的退款份额。

实际退回立即减少对应履约 `C/P/S`，并形成本金、赠金或券套餐的原权益待恢复额。例如原券 `C=1000、P=801、S=903`，本次分摊退回 `C=250、P=200、S=226`：净履约相应减少，250 分列为不可消费待恢复负债，原钱包仍不增加 0.25 张券。

凑齐原完整单位后，实际恢复继续写原 `BenefitEntry.reverse`，不改变其整数语义。标准逆转产生的整份 `C/P/S` 减少，通过 `RetailGroupRestore` 与配对内部结算对冲。由此，原实退只减少一次履约收入与内部结算；恢复时只是把待恢复负债转换回原钱包。

报表适配集合为“标准集团原账 + 负的实际退回分摊 + 正的恢复对冲”。精品本单的集团净支付直接取“原实际核销 − 原实际退回份额”，不再重复加上标准逆转。现金仍只有 `CashEntry` 一次；所有本扩展现金记录只是原行分摊，不是另一套收款账。

当前形成的是集团中心与履约门店的**内部结算记录**。原系统实际双店资金清算只支持物资、损失和整车调拨。集团已有独立财务系统处理实际资金，本项目不建立中心账户、实付/到账审批或支付接口；内部会员记账不能当成已付款，也无需等待这些被排除的模块。

## 数据与接口集成约定

本域文件为 `app/retail_group_*.py`、`web/retailgroup.js` 及独立测试。16 张追加表包括规则附则/范围/批准/发行关联、支付方案/批次/单位/原行分摊、占额关联/核销关联/释放、实退/实退分摊/恢复/内部结算及现金原行分摊。已由上传源码的 n46a 静态迁移建立；表存在不代表生产业务 hooks 已接通。

所有窄接口均不自行提交，除带 request_id 的专用 `command/create` 外由调用者一次提交：

| 接口 | 调用位置与作用 |
|---|---|
| `rules.guard_issuance(db,user,rule)` | 原 `benefits._issue` 创建钱包前；没有商品附则返回 None，保持旧服务规则 |
| `rules.attach_issuance(db,user,wallet,origin,permit)` | 同事务新钱包和原发行流水 flush 后；只接受本次许可之后新建的真实记录 |
| `service.guard_legacy_wallet_action(db,row)` | `group._case`；有精品方案时禁止旧维修 release 等入口，专用 authority 内允许正常协调 |
| `service.guard_cash_receive/attach_cash` | 原精品实际收款前/原 `PaymentLink` flush 后，限制并冻结原行现金份额 |
| `service.guard_cash_refund/attach_cash_refund` | 原现金退款前/原退款链接 flush 后，绑定原现金而非权益额度 |
| `service.record_actual_return(db,user,row,posting)` | 新实际 `RetailReturnPosting` flush 后，同事务写原退分摊和内部结算 |
| `service.guard_external_settlement(db,row,action)` | 预收抵用、月结代收及通用收款更正等额外结算入口；已有本方案则明确拒绝 |
| `service.totals_adjustment(db,row)` | 原精品 totals；集团净抵扣、实际优惠、现金可收/可退、分类待恢复 |
| `reporting.report_data(db,user)` | 原商业/物资/集团统计同源适配，与标准 Group/Benefit 原账一同统计，避免整份逆转时再次减少履约 |
| `integrity.validate_retail_group(connection)` | 总恢复校验，核对发行、原单位、原行、现金与内部往来来源 |

`retail_group_rule/v2` 是规则申请专用 Case，仅管理、财务和审计可读，集团汇总不开放原配置详情。付款计划继续绑定原 `retail/v2` Case，不引入可任意修改状态的新入口。普通 Case 事件只记录计划、原批次及凭据标识，不嵌入新支付价格清单。

新 API 前缀 `/api/retail-group`，包含订单 catalog/detail/actions 和规则申请；网页函数 `retailGroupPage(id)`、`retailGroupRulesPage()`、`retailGroupRulePage(id)` 与 `clearRetailGroupSession()`。已注册 `retail-group/{id}`、`retail-group-rules`、`retail-group-rule/{id}`，当前根据真实岗位/待办返回可操作集合，不再统一隐藏全部写入。

当前原报表、发票、积分与恢复校验已接线，月结定义10增加明确来源；旧定义1—9不扩大。完整版本回归和现场验收仍须执行；动作可用不能代替最终验收。

原支付只匹配成交行与发行范围两个冻结快照的物资编号、单位及安装作业编号/编码，不按当前主档重标历史。发行时检查发行本店批准的商品/作业是否仍启用且身份未变；发行权限不开放他店主档。公共物资单位变更守卫仍需接入已批准商品范围的引用检查。

## 历史 n46a-fix1 公开边界与当时的接线门槛

`retail_group_readiness.require_write_ready` 在实际生产注册路由拒绝规则创建/批准及付款计划全部写动作，`read_only` 返回 `write_enabled=false` 和中文说明。不能通过环境变量或请求字段解除。普通原精品不含混合方案时不受影响。

已有混合方案不能从原精品 `receive/refund/return_receive`、发票来源、外部预收/月结代收、旧维修权益等入口写出未分摊的结果；有冻结消费积分规则时也拒绝使用旧金额口径同步。原发行如已有商品用途附则、却没有专用同事务绑定，必须拒绝，不能制造一个后来被补授范围的钱包。源域 helper 仅供隔离集成测试，不能作为 HTTP 绕过标记。

解除隔离之前至少完成原发行 guard/attach、原收退 guard/attach、实退分摊、原净价与现金应收、发票上限、消费积分、原全局统计及新冻结月结定义，并验证公司规则、跨店来源/附件、幂等、并发和非空恢复。必须用原注册的生产入口测试，禁止通过 monkeypatch 或手工补 hooks 宣称接线完成。

本次注册路由的写拒绝、零现金/库存副作用及普通流程兼容验证见根目录续开发交接。上文34项/23项及 Windows 浏览器计划是历史独立开发记录，不是本轮正式生产集成通过数。
