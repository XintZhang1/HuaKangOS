# 客户车辆、客户服务与提醒

本轮是阶段五的一条可实际办理的纵向链：独立客户车辆主档、事实来源、内部服务任务、日期里程提醒、续保跟进以及可撤销的跨店服务摘要授权。它不等于完整 CRM、任意问卷设计器、道路救援调度平台或保险直连系统。

## 入口与适用岗位

“客户管理”下提供“客户车辆档案”“客户服务任务”“保养与续保提醒”“服务历史授权”。员工电脑、手机共用网页。管理员、店长、服务顾问、客服可按岗位办理；销售和前台只可查看自己负责或明确指派的客户服务。审计可读本店，不能办理；财务、库管、技师不因其其他业务权限获得这些客户服务详情。集团汇总不开放客户明细，通用 Case 详情也遵循同一边界。

客户车辆是 `CustomerVehicle` 与现有本店 `Customer` 的关系，共享 `GroupIdentity(kind=vehicle)` 的 VIN。与整车库存 `Vehicle`、车辆占用、库存调拨分开：登记客户车辆不会入库、转店或改变可售状态。客户电话为空或相同都不会自动合并；创建新的客户身份使用随机标识。选择既有身份必须人工确认同人并记录来源，姓名或已有电话不一致时拒绝。已有身份关联不允许覆盖修改。

车型、车牌和关系启用状态可版本化维护。更改 VIN、客户归属或原始身份关系须另行核对建立关系；不提供覆盖字段接口。停用前必须办完或明确取消、转交本车未结服务。

## 日期与里程来源

按实际事实追加交付、里程、保养完成、首保完成、保险期限或保修期限记录。每条必须包含实际日期、当时整数公里数、来源凭据编号及经办人确认；可引用同一客户本店业务中获权且扫描可用的附件。附件编号不代替纸质或外部凭据真实性核验。未来实际发生日期、少于本店已登记里程或早于最近登记日期拒绝；原记录不覆盖、不删除。同一来源和数值重复登记拒绝。

保险和保修另记截止日期，不能倒退覆盖；首保完成和交付基准各只登记一次。日期及里程是本店关系下的事实，系统不会从别店未授权数据推断数值，也不预测客户每天行驶里程。若原始记录错误，当前版本要求主管核对并按后续经审核的纠错流程处理，没有自动改写旧事实的入口。

## 服务办理契约

服务使用 `Case.kind=customer_care`、`flow_version=2` 的专用服务接口；通用流程目录只注册显示元数据，不能通过通用动作任意改状态。保留原有 callback、complaint 等历史流程，不改其版本含义。对应本店 `Task` 进入现有待办；员工可从普通原单页进入专用办理页，并按原附件权限上传凭据。

| 分支 | 经办与入口 | 必要事实及守卫 | 同事务结果与下一步 |
|---|---|---|---|
| 问卷、咨询 | 客户业务岗位；选择本店客户，可关联其车辆 | 主题、诉求、期限、匹配岗位的责任人 | 建立专用单及一条待办，责任人接手 |
| 投诉、救援 | 店长、服务顾问、客服 | 投诉实际情况；救援须客户提供的位置与协助需求，不假装已派车 | 责任人接手、记录实际协调进展，可紧急标记 |
| 销售、维修回访 | 获权客户业务岗位 | 同一客户本店已交付销售单或完工维修单；已知 VIN 不匹配时拒绝 | 关联原单号码，不赋予原单财务或附件读取权限 |
| 接手 | 当前责任人，或店长 | 未接手状态、当前版本 | 待接手→跟进中，追加事件；不产生联系结果 |
| 跟进 | 当前责任人，或店长 | 内部核对、当面反馈或电话；电话需客户允许后续联系且留有电话 | 追加实际内容，可明确下一日期；不会发送电话、短信或消息 |
| 交接 | 店长；或当前负责的服务顾问、客服 | 同店有效且岗位匹配的接手人、原因、下一期限 | 单据与待办责任人一并修改，保留前责任人、原期限和是否逾期 |
| 结案 | 当前责任人，或店长 | 实际解决、预约、客户不需要、未回应等结果及依据 | 关闭待办并记录完成日期，不当作收款或维修完成 |
| 问卷结案 | 当前责任人 | 标记完成时必填满意度 1–5 与是否推荐，保存问卷 v1；拒绝空回答完成 | 回答在不可变办理记录保存；不进行员工绩效排名 |
| 续保完成 | 当前责任人 | 必须先追加新的有效保险期限来源，且晚于原期限 | 续保任务完成，不虚构保险公司保单或收付款 |
| 取消 | 当前责任人，或店长 | 未结案、原因、当前版本 | 单和待办取消，既有记录保留；不回退任何事实 |

所有命令有幂等请求编号，修改同时检查单据或主档版本。重复请求返回原结果；相同编号不同内容、过期版本、越店及岗位不匹配拒绝。业务单、任务、记录、审计和回执同事务提交；失败不留下半单。终态不再接受接手、跟进、取消等动作。

## 规则与续保提取

每店每类一条可启停、可版本化的规则。店长配置周期、提前量和默认经办人。首保依据交付日期/里程，完成首保后停止首保提醒；保养依据最近保养、首保或交付的基准。日期到点或已登记里程到点任一满足即可提醒，未登记的事实不猜测。保修与续保依据登记截止日和提前天数，保险直连不在本轮范围。

“检查并生成到期任务”只建立本店内部待办，同一车辆、规则类型、同一服务基准或保险期间不会重复派单。规则编辑或同一期限另一份核验资料不会重复提醒；下一次实际保养或下一保险期间有新的事实基准后才能形成下一周期。取消某一周期任务不会自动再生成该周期，避免重复打扰。

续保任务列表可按类型及状态提取、查询、分派、跟进和结案。到期时间及来源显示在任务说明。客户没有电话仍可建立内部核对待办；主动电话动作会被拒绝，不能把无联络条件的记录伪装成“已联系”。规则默认经办人或批准者停用、失去本店岗位时暂停该条生成，返回可检查原因，要求主管处理。

后台入口由管理员显式启动：

```powershell
python -m app.reminder_worker --once
python -m app.reminder_worker
```

独立进程每 60 秒检查，网页进程不再挂一个重复定时器，也不依赖 AI/日报开关。无默认自启动、无外部联络。服务导出 `tick_reminders()`；基于日期、来源变化、规则版本和经办/批准岗位计算回执键，无变化的 tick 不重复扫描车辆或记新回执。

自动来源持久化为 `generation_mode=rule_worker`，保留当前规则版本与批准者；普通员工触发规则计算记 `rule_requested`，手工登记记 `manual`。自动任务的创建者代表规则批准责任归属，不代表该员工点击、联系客户或见证实际服务。专用详情、不可变记录和 FlowEvent 均明确“系统按规则自动生成内部任务”。不静默创建可登录的系统账号。

## 跨店服务历史授权

1. 先由本店获权员工核对客户与车辆，关联本店真实原单及一段可共享服务内容摘要。只支持相关客户的销售、维修、加装、保险、代办和客户服务原单；已知 VIN 不匹配拒绝。费用、客户私人信息不应写进摘要。
2. 来源店店长选择本店客户车辆、接收门店、对方提供的客户车辆关系编号、截止日和客户授权依据。两端必须是同一客户身份及同一 VIN；同车不同客户、任意第三店、未启用关系或门店拒绝。期限最长一年。
3. 接收店获权员工通过本店车辆页读取授权期间内的摘要，只返回单号、业务类型、日期、状态、服务摘要和来源店。不会返回结构化金额、联系方式、原单 ID、完整单据、任何附件或办理权限。原有下载路由仍按原门店和文件岗位规则校验。
4. 任一方主管可随时按当前版本撤销；撤销和原范围保留，不覆盖删除。后续查询立即生效，过期同样不可读。第三店不能读取或撤销该授权。任一端车辆关系或来源门店停用也停止跨店读取。已被浏览器显示过的内容无法远程抹除，但服务端不再返回该资料。

只有明确关联的服务摘要纳入此历史页；没有根据电话、车牌或共享 VIN 自动扫描并开放所有旧单、投诉文本及附件。更广的档案授权、附件逐件跨店授权、会员权益及财务授权需各自规则，不由本模块暗中扩大。

## 测试与边界

`tests/test_customer_service.py` 覆盖正常、拒绝、同电话/无电话不合并、越店、原单不匹配、无电话及联系许可、版本与幂等、失败整单回滚、并发生成一次、里程日期来源不倒退、规则重复和自动来源、授权/到期/撤销、不同人同 VIN、第三店及文件路径拒绝。`l612_customer_service` 追加在 `k511_repair` 后，冻结表定义，实际临时数据库升级检查列和外键。

`tests/browser_customer_service.py` 在独立合成数据库和真实 Chrome HTTP 下，用店长及客服账号验证网页全链，随机密码、无真实客户、无外部发送；390px 截图在仓库外。生产 HTTPS、PostgreSQL 并发和公司真实服务周期验收须另行完成。

2026-09-21 本轮验证：24 项专用自动测试通过；真实 Chrome 六项端到端场景通过，无 JavaScript 错误，六张手机截图逐页检查。撤销跨店授权后全页刷新仍保持已验证的乙店身份和当前车辆地址，原店摘要不再显示。浏览器合成证据保存在仓库外 `huakangos-care-evidence-g23eb69u/acceptance.json`；`node --check web/customerservice.js` 通过。以上是自动验证，不代表业务部门签字验收或正式启用。
