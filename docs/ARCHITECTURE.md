# 0.2 多门店与受控维护架构补充

业务表、审计、日报、复核项及意见使用store_id隔离；store_id不是由客户端表单指定，而是由后端验证X-Store-ID与用户授权后写入。StoreScoped的SQLAlchemy查询钩子为HTTP请求添加门店条件，before_flush检查归属和汇总视图只读。它是应用层隔离，不是数据库RLS，也不约束获得数据库文件或直接SQL权限的管理员。

stores、user_stores为门店与授权。管理员跨所有启用店；其他角色仅所授权门店，部门角色跨授权店一致。业务关系在同店验证，单据号改为(store_id,doc_no)唯一；VIN、保单号与车辆生效占用仍为全库唯一。旧0.1数据全部回填门店1，不猜测原始店别。

日报租约和唯一键增加store_id；定时任务遍历启用店。汇总看板合并授权店且有每日分店对照；不是集团合并会计。每份日报的新旧判断只使用该店业务修订号。

maintenance/supervisor.py由原始可信目录运行，按active.json拉起业务进程。maintenance/worker.py只操作独立Git克隆。模型不能调用命令，只产生可校验的精确替换；后端、依赖、测试、迁移、控制器禁止修改，前端登录/权限/写流程还有字节级保护片段。白名单与这些检查仍不能构成任意JavaScript变更的完整安全证明，必须人工看diff。

候选在固定可信Docker镜像内离线运行测试，推送分支后等待飞书应用机器人回调。feedback持久化状态、SHA和令牌哈希，maintenance_events记录步骤，bot_receipts去重，deployments记录运行切换和备份位置。批准只对指定openid、SHA、令牌、有效期和测试记录生效；数据库事务完成后才执行耗时发布。

本机发布保留业务库，暂停API后备份，导出不可变版本目录、健康检查、普通Git快进再恢复访问。成功回滚使用Git revert并切换代码，不恢复旧数据库。网络结果不确定或中断时暂停后续自动发布，保留已知版本与状态供人工核对。无后台数据库迁移，无force push，无保护分支绕过。

# 架构与继续开发入口

## 运行结构

```text
浏览器（同源 HTML / CSS / JS）
       │ JSON API；HttpOnly 登录 Cookie；CSRF 校验
       ▼
FastAPI
 ├─ security.py    登录、角色、模块权限
 ├─ schemas.py     输入类型、金额和业务校验
 ├─ services.py    单据状态机、权限复查、审核、关联、审计
 ├─ analytics.py   金额汇总、规则、快照与外发字段白名单
 ├─ reports.py     幂等日报、复核同步、DeepSeek JSON 校验
 └─ scheduler.py   前一业务日任务、补跑、数据库任务租约
       │
SQLAlchemy / Alembic
       │
SQLite（本地默认） / PostgreSQL（迁移目标，须实机验收）
```

前端不是只有演示静态页面：录入、审批和角色判断的最终执行均由后端完成。核心页面不引用外部 JavaScript 或字体服务。开发用 `/docs` 的 Swagger 界面不属于核心业务前端，可能需要访问其默认外部资源；生产环境关闭交互式文档页面。

## 领域模型

`vehicles` 是库存实物主表，VIN 唯一。`sales` 指向车辆，已审核订单通过 `active_vehicle_id` 唯一约束占用车辆；订单审核时冻结成本快照。交车是完成日期事件，不是随意修改金额。

`repairs` 独立记录售后业务，可指向 `policies`。`cash_entries` 是现金收支事实，最多指向销售、维修、保单、库存中的一个，类别与方向/关联类型相互校验。不要用“已收款”布尔值代替财务流水，也不要用销售金额反推现金流。

`audit_logs` 保存变化前后状态。`daily_reports` 保存固定输入快照、确定性摘要和可选 AI 结果。`findings` 维护跨日报的复核生命周期。`job_leases` 防止同一日期被并行重复请求。`app_metadata` 保存数据库自身的演示标记，不能由文件夹名伪造正式状态。

## 一致性边界

每次业务写入使用事务。SQLite 显式发出 BEGIN，启用外键和忙等待；初始化启用 WAL。审核/作废等动作带当前版本号，SQLAlchemy 版本列避免陈旧页面覆盖已修改的数据。唯一约束承担 VIN、保单号与生效车辆占用的最后保护，不只依赖前端先查后写。

业务数据和审计变更在同一事务中提交。AI 不参与业务写入事务：先保存快照和规则结果，再请求模型，最后保存模型输出或失败状态。长网络等待不会占用业务写锁。

同一门店、日期、业务源版本、规则配置、AI 选择、当日是否仍进行中等组成日报去重条件。单据补录或更改可生成新版本；历史日报不被直接覆盖。已有模型成功结果不因普通重试重复请求。

## 安全边界

Argon2id 密码哈希；数据库只存登录令牌和 CSRF 随机值的哈希。会话 Cookie 为 HttpOnly、SameSite=Strict；开启 HTTPS 后使用 Secure。写接口验证同源、JSON 与 CSRF。无浏览器 localStorage 令牌；生产 Host 白名单不接受通配符。

权限执行在路由和业务服务层；后端字段脱敏限制销售查看成本；首次改密之前只开放必要账号接口。角色/密码变更撤销会话。CSV 对可能触发电子表格公式的开头字符进行处理。

这些防护不等于经过独立安全审计。数据库、审计、CSV、备份都包含经营或个人资料，操作系统权限和网络暴露仍需管理。默认仅监听 127.0.0.1；不要随手改成公网绑定后直接使用。

## 性能与扩展

当前分析读取相关数据后在应用中计算。关联累计收款有预聚合/日期索引，避免为每笔销售重复扫描全部流水。还没有大规模压测、分页式快照仓库或专用分析数据库；长历史、多门店、大量并发应重新评估数据加载与报告存储。

新增字段依次修改：`models.py` → Alembic 迁移 → `schemas.py` → 必要的 `services.py` 校验 → `web/app.js` 的表单和显示 → `analytics.py` 的规则/汇总 → 回归测试。敏感字段不要自动加入外发白名单。

新增角色需同时检查 READ/WRITE/FULL_VIEW、字段脱敏、关联查找、CSV、看板、审计和报告接口，不能只改导航按钮。

## 对接下一阶段

先确认现有门店台账中的字段、收入/成本/收款定义、角色和实际审批人；再增加导入与通知。在启用真实客户数据之前确定保留周期、备份加密、服务器权限和外发授权。完整财务记账或退车业务应独立设计，不应往当前现金流水模型里塞“负销售额”绕过流程。
