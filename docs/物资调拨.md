# huakangos 跨店物资调拨

版本：新业务类型 `material_transfer / flow_version=2`。两店拥有各自的业务单、任务、文件与库存流水，协调记录有同一调拨号。原业务和物资从不修改 `store_id`。该实现用于物资，**尚不支持整车调拨**。

## 员工办理

1. 调出店库管或主管选择本店物资、数量、目标店、计划日期与原因，提交双方审批。只有自己店的资料可选；另一家门店的名称用于确定对方，不授予其库存或文件访问权。
2. 双方主管各自在本店待办批准；非管理员不能自批本人申请。主管可拒绝。发出前，调出申请人或主管可撤销。此时没有库存、现金或往来过账。
3. 双方批准后，调出库管上传实际发运凭据并确认发出。服务重新核对物资启用状态、名称、单位和足够的实际库存。整单任一行失败时全部回滚。
4. 调入库管可分批分别填写合格数量和拒收数量。合格部分绑定本店启用、名称和单位相同的物资档案，增加实际库存；拒收部分继续隔离为待退实物，不增加可用库存。未验收数量继续在途。
5. 调入库管对每次拒收记录确认发运退回；原店库管可分批确认实际退回入库。只有全部发出数量都已验收入库或退回入库，双方流程才结清。

已验收入库之后再发生质量退货，应另建反向调拨申请，不伪造原拒收。运输丢失、额外费用或赔偿还没有专用差异核销流程；不得按“收到”消除真实差额，保留未结在途并另行核对。门店内库位移动、整车调拨和内部实际资金划付仍待开发。

## 账本与价值

金额为整数分、数量为整数千分位。发出价值按发出时的移动平均账面价值分配；发完某物资时取完全部剩余价值。每批验收按累计处理数量分摊原发出价值，末次取余。退回使用对应拒收批次的原价值，不按新采购价重新计价。

`StockMove` 是本店实物过账来源；协调流水 `TransferMovement` 关联对应库存流水，不再重复加库存。拒收及退回发运仅改变在途分段。每次合格验收同时追加调出店应收、调入店应付，金额等于实际接受的库存账面价值。本轮无内部加价、无内部利润，`CashEntry` 不因调拨自动新增。

在途资产归原调出门店，直到对方合格入库或原店确认退回。图表、明细和 CSV 使用同一集合，集团按调出方只统计一次。完整集团范围的配对往来抵销为零；仅查一家门店时保留该店对外店往来。

## 岗位、证据与异常

| 分支 | 经办与必要事实 | 原子结果及下一责任人 | 超时与撤销 |
|---|---|---|---|
| 提交申请 | 本店库管/主管；启用物资、数量、对方门店、日期、原因 | 建立双方单据和主管待办 | 超过计划日期显示逾期；调出方发出前可撤销 |
| 双方审批 | 各店当前主管待办负责人；明确接收/调出安排 | 各自审批事实，双方都通过后生成调出库管待办 | 可拒绝，关闭双方任务；不改变库存 |
| 发出 | 调出库管待办负责人；本店可用实际凭据、足够库存 | 本店出库、在途记录及调入库管验收任务一起提交 | 发出后不可取消；需实际验收或拒收退回 |
| 分批验收 | 调入库管；原发出行、实际合格/拒收量、本店接收档案、凭据 | 合格入库及双方往来；拒收保持待退 | 剩余待办保留原责任人，主管可明确转交 |
| 拒收退回发运 | 调入库管；原拒收记录及实际物流凭据 | 追加退回在途、原店接收任务 | 不能重复发运，不能提前恢复原店可用库存 |
| 退回入库 | 原调出库管；原退回发运、实际接收量和凭据 | 追加原价值库存；全部实物结清后关闭双方任务 | 未收部分保持在途，不提供无依据核销 |

所有动作同时检查调拨版本和本店业务版本，请求编号绑定操作者与完整内容。状态、任务、库存、往来、留痕及回执在一次事务提交。冲突后先刷新核对；原请求重试不重复入库。后台跨店协调只更新双方任务/业务进度及配对往来，另一店实际库存必须由该店获权岗位确认。

双方只能下载本店有权限且扫描策略允许的附件；跨店详情只展示共同调拨事实，另一店凭据仍由对方保管。库存岗位看数量，经营查询岗位可查看价值。集团汇总为只读。

## 已执行验证

`tests/test_transfers.py` 验证分批合格及拒收、分批退回、整数余数、拒绝与取消、跨店 ID、重复请求、过期版本、库存竞争及并发验收、不可变事实、图表/明细/CSV和备份恢复。

`tests/browser_transfers.py` 在真正的本地 Chrome HTTP 中，用四个独立员工账号完成申请、双方批准、实物发运、验收拒收、退回入库和资金核对；390px 表单及关键数量卡片已目视检查。全部使用临时合成数据。生产 HTTPS、运输实物及公司流程验收还未执行。
