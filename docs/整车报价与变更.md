# 整车报价与变更

本模块对应 HK-009“车辆销售单”。新员工入口采用 `order / flow_version=3`，在既有整车收款、VIN 占用、交车检查、出库及提车流程上增加逐版核价和客户确认。既有 v1/v2 订单及其接口按原版本办理，不自动改写历史；新版界面通过专用报价入口建单。

## 销售与岗位办理

销售从“车辆报价与交付”或已接待客户进入新报价，选择本店明确车型目录，填写本单车辆价款、交付日期、确认有效期、具体约定和报价理由。车型的编号、参数、品牌车系及资料版本保存为当时快照；指导价是参考，所有本单报价都须另一位店长或管理员复核，包括由管理员提交的报价。

报价中的精品加装、保险、代办开关只表示另单办理需求，车辆价款不含这些业务的独立收费。客户确认车辆报价后后台才建立对应旧版配套服务单；服务自身仍需办理和实际结算，不能把勾选当作已履约。

| 岗位与入口 | 必须核对的事实 | 原子结果和下一责任人 |
|---|---|---|
| 销售提交报价 | 本人负责的客户、启用车型资料及版本、价款、期限与约定 | 冻结新报价；交独立主管核价，不产生现金或出库 |
| 店长批准／拒绝 | 本版车型、全部约定及金额；不能审批本人报价 | 记录复核人及理由；批准后库管配车，销售取得本版签回 |
| 库管配车 | 本店已审核入库、明确对应本版车型、仍可用的 VIN | 锁车辆并建立唯一占用；车辆本身仍在库 |
| 销售确认本版签回 | 当前报价、实车 VIN、已确认模板生成的合同原件及对应实际客户签回 | 本版正式生效；旧版本和文件保留，交财务收退差额及履约岗位 |
| 财务收款／退超收 | 本店账户、真实流水号、实际收退款凭据及正确原收款 | 追加现金和原单关联；分笔到款或原款退差额，不生成重复现金 |
| 服务顾问／检测人员 | 当前 VIN 的实际检查结果和凭据 | 不合格必须处理缺陷并复检；合格后交库管出库 |
| 库管出库 | 本版客户确认、足额结算且超收已退、合格检查、必办服务完成 | 记录实际出库；交销售办理客户提车 |
| 销售确认提车 | 当前交付确认单的真实签回及全部交付关口 | 标记实际交付、保留车的交付占用及售后来源 |

待办显示当前经办人、期限和不能办理的中文原因。主管可通过既有待办交接界面转交；报价同步保留开放任务的已交接经办人与独立日期。客户确认变更交期时，仅仍沿用原交期的相关开放任务随新交期调整。到期只产生逾期提示，不能自动批准、替客户签字、退款或交车。报价超过确认有效期须撤回并提交新版本。

## 执行中变更与异常出口

未实际出库时，销售可提出新报价；必须先处理当前待审版本及上一版超收，预收和权益在办占额也须先释放。待审或待本版签回期间保留旧生效价款，同时暂停资金抵用、更正、原单售后及后续交付，防止多个版本并行生效。主管拒绝或销售撤回均追加结果，恢复仍有效的旧版办理条件，不删除旧记录。

仅改变条款、日期而金额不变，同样必须重新取得客户本版签回。新合同快照包括报价版本、完整摘要、车型和 VIN；旧签回不能确认新报价。生成文件只是待客户核对的凭据，不能当作客户已经授权。

变更车型须主管先批准，库管凭实际核对记录释放仍未出库的原车，再按新车型选车。释放原车不转移门店归属，不抹去旧占用、检查、报价或签回历史；新车必须重新检查并签回。已有配套服务开始或完成时，不允许通过改车型或删开关隐藏原实物、保单及费用，须先办理相应终止和售后。实车已出库或客户已提车后不能改原报价，使用原单售后流程。

车型停用或改名不覆盖已经批准的快照；该原报价仍按固定车型编号选择符合要求的本店车辆。新增报价必须使用当前启用车型，不因历史可履约而放开停用主档。

降价生效后，系统分别处理结算来源：

- 原预收抵用超过新价款的部分，只追加退回原预收余额的关联记录，没有现金流出。
- 其余实际超收现金，由财务选择本单原收款和原账户，按实际退款凭据分笔退回。不能超过本版超收及该笔原收款的剩余可退额。
- 同一请求重复提交返回原结果；原单版本变化或并发占额失败返回冲突，须刷新核对，不能更换请求号盲重试。
- 超收未退完、仍有占额或未通过当前 VIN 检查时，禁止出库和提车。

有预收抵用的整单退订须从原单售后选择原预收回退，不能把抵用额当现金退。已有销售退订、实际退车、退款审批及原单售后关口继续有效；售后冻结并核对所引用的当前报价编号和摘要。

## 数据、权限与接口

迁移 `g733_sales_quotes` 依赖 `f632_vehicle_catalog`，静态创建六张表：报价、独立复核、版本处理结果、客户同版签回、配车释放及超收调整。金额使用整数分，报价和关联事实不能通过应用修改或删除。每次动作的原单版本、任务、车辆占用、资金事实、来源日志及幂等回执在一次事务提交。

API 前缀 `/api/sales-quotes/orders`：

- `POST /`：本店客户、可选接待单及其版本、完整首版报价和 `request_id`。
- `GET /{id}`：本店有权查看的原单、逐版报价和当前任务；库管和技师不获得金额、价格条款或财务文件。
- `POST /{id}/quotes`：当前原单 `version`、完整新报价及 `request_id`。
- `GET /{id}/vehicles`：该报价明确车型的本店可用 VIN 提示；实际配车时后台重新检查。
- 实际办理继续调用 `/api/flow/cases/{id}/actions/{action}`；新增 `quote_approve`、`quote_reject`、`quote_withdraw`、`release_vehicle`、`refund_excess`，没有任意改状态入口。

集团视图只读；报价办理接口要求单店上下文。客户归属、岗位、当前任务、文件可见性、同店关联和车辆并发占用由后端校验。新报价不授予读取其他店客户历史或附件的权限。

## 统计、文件与验证

新增统计分别列出期间报价版本、期间客户确认的价差、当前可退超收及期间原路退回。报价金额与价差不新增营业收入；实际现金退款和预收回退分列，图表、明细和 CSV 使用同一来源集合。恢复校验逐项核对报价摘要、同版签回及原文件、车型、独立审批、原现金和原预收关联、差额上限；改写源金额或摘要会拒绝恢复。

`tests/test_sales_quotes.py` 覆盖正常交付、独立批准、同金额改条款旧签回拒绝、车型改变、新 VIN 检查、服务已开始、拒绝与撤回、失效报价、岗位和跨店拒绝、重复与过期请求、并发改价／配车／原款退款、原预收回退及完整售后恢复。`tests/test_sales_quote_reporting.py` 验证来源金额、图表、CSV、权限及预收无现金流出。

真实 Chrome 390px 使用销售、店长、库管、检测顾问与财务账号完成三条场景：当前版车型与签回交付、同单降价旧签回拒绝、原款三分差额退款后提车，零 JavaScript 错误。证据保存在仓库外临时目录 `huakangos-browser-evidence-0zdu2147/acceptance.json`，不含公司数据。

实际 API 生成的合同样式已用官方 LibreOffice 临时解包环境渲染：短单一页，含十八项条款的长单两页，全部三页逐页目检通过。报价事实使用可分页的独立内容，长条款不放进禁止拆分的大表格；金额、车型、VIN、条款、签名和摘要可辨认。生成的正式模板仍须按实际经营主体和公司批准条款配置，测试中的模板确认只属于合成数据库。自动验证不代表公司业务验收或正式启用。
