# 从 DealerDesk 0.1 升级到 0.2

**不要将新压缩包中的任何演示数据覆盖真实数据库，也不要在运行时直接替换整个旧文件夹。**

先停止0.1服务。在旧目录运行 `python -m app.cli backup --output 你选择的绝对路径/upgrade-before-0.2.sqlite`（使用旧虚拟环境Python）。备份命令采用SQLite一致性备份，而不是只复制可能缺失WAL内容的主文件。妥善另存一份，不覆盖原数据库。

把0.2完整解压到新目录，保留旧程序作为迁移前回退材料。复制旧.env到新目录，并把 `DATABASE_URL` 改为一份**独立的备份副本**的绝对路径，先演练迁移。不要让0.1和0.2同时写同一个库。将新增配置参考.env.example追加，先保持自动维护关闭。

运行新目录的 `start.ps1` / `start.sh`，不要带Demo参数。启动脚本会执行Alembic迁移。原有用户、五类业务单据、日报、复核项和操作日志都归到「默认门店」（ID=1）；原有员工均授权这家门店，管理员能管理所有启用门店。旧数据不按员工姓名自动猜测分店。

核对迁移前后用户数、五类单据数、金额、日报和样例关联。在演练库验证通过后，停止原服务，对最新生产库再做一致性备份，以同样流程迁移生产副本，切换启动入口。保留原始旧库和完整旧目录直至业务核对完成。

登录「门店管理」修改默认门店名称并建立其他门店；到「账号与权限」给人员分配门店。先由每店录入几条脱敏测试记录验证隔离，再正式录入。

没有自动拆分旧库的功能。旧0.1数据库中若已混合多个门店，需要先有明确的逐条归属映射，再制定一次性数据迁移；不要直接批量修改store_id或复制关联单据。

本次0.1→0.2涉及数据库结构，必须人工完成；后续AI自动维护只能变更前端/说明，不承担数据库升级。0.2数据库不可直接交回0.1程序使用。迁移失败时只恢复升级前的程序与升级前的一致性数据库副本；迁移后已经产生新业务数据时，不能直接恢复旧库抹掉新增数据，应先对账制定处理方案。

自动维护运行版本在 `data/maintenance/active.json` 中记录，控制器在原始可信目录启动，而业务进程可能从 `data/maintenance/releases/` 下的批准版本运行。不要把手工编辑原始web文件误认为正在编辑线上代码，也不要删除当前或上一运行版本目录。人工跨版本升级须先停维护器并核对实际SHA。
