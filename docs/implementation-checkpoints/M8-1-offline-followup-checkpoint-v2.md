## 真实发现与修复

1. worker 从未调用已实现的事件分发/到期计划检查，显式跟进不会被唤醒。补齐调用，每周期最多一事件、一计划、一 Run，彼此独立会话；异常不饿死员工队列，停止/撤权仍复核。通知开关独立生效，默认关闭不变。
2. 单事件后固定等待 5 秒导致通知积压；页面闭环先出现通知迟迟不至。实际分发函数可以成功，真正问题是排队速度。改为有已到期工作就逐轮让出后继续，空闲/异常才退避；原 next_check_at/重试时间不变。
3. `lead.owner_assigned` 将创建人的 owner_id 当作已分派；`lead.reserve_recorded` 忽略真实 child order，反而接受松散链接。改为核对原分派任务以及同门店、同父单的真实订单证据，不改原业务流程。
4. 新计划保存后没有读取 PlanView，无法开启跟进；同会话通知不刷新，新卡片不可见。补齐终态/新计划读取、通知真实打开和刷新。未发草稿、答案不丢失；未打开成功不标已读。
5. Plan/通知读取存在跨上下文 ABA 竞态；跟进双击会重复发送；侧栏旧打开请求可能把新选择切回。以请求所有者、当前上下文和最新选择守卫，切店/新事项清理旧控件，禁止旧响应重新推进导航。
6. 开始 Run 前依赖整个动态 workspace 获取功能开关，投影并发 409 会阻断发送。已有登录态 `/status` 追加四个配置布尔量，前端优先使用；读取计划/卡片的原授权不变。
7. 旧批量确认后端在某项失败/不确定后仍提交后续卡。先核对真实轮次/步骤分组，再逐项确认，首项非目标终态即停止；剩余逐项返回 skipped，不修改原卡状态，不回滚已经成功的原业务。

精确文件范围和异常边界见 PATCH-M8-1-FOLLOWUP-01、BATCH-01、VALIDATION-01。测试中的“回访 done 会取消原 task”不是产品缺陷，保留反例，禁止把取消猜成任务完成。
