# huakangos · 本店业务财务结算

本次纵向交付增加独立的“业务财务结算”入口，处理本店客户预收、原单抵用、未用原款退款、客户月结集中收款、误记收款更正和其他入库原单退货应收。它是业务账，不是会计总账，不代替银行转账或税务开票。

## 业务办理与边界

|办理|经办与前置事实|原始依据和一次事务内的实际记录|下一责任人及取消|
|---|---|---|---|
|客户预收|服务顾问、销售等本店经办提出；财务确认真实到账|独立财务单、当前本店客户、启用的本店账户及本单“收退款凭据”。一笔 CashEntry 对应一笔原预收及正向本金流水，不抵原业务应收|创建后交本店财务；未实际收款可取消。实际收款后须走未用原款退款|
|预收抵用|明确一笔原预收及同店同客户的具体原单；经理与申请人须不同，管理员也不能自批|批准时占用原预收及原单客户可付额度。财务确认后扣原余额，追加原预收负向流水与 FinanceCreditLink，不新建现金|经理复核后交财务及原业务收款待办经办人；未执行可取消释放占额。不得抵保险、厂家或内部承担|
|未用预收退款|经理独立批准，批准时原款未用余额足够|批准占额阻止同时消费；财务必须退原账户，按批准原额追加真实出款及原预收负向流水|未执行可拒绝或取消，释放本申请占额；实际执行后不能取消抹账，可分次提出剩余原款退款|
|客户期间月结|财务选择本店客户及不超过一年的截至今天期间|冻结原单号、承担、原单版本、客户余额及摘要。经理复核时核对当前原业务金额；财务将一筆实际现金逐单分配，CashEntry 仅一次，多个 PaymentLink 明确分配来源|晚到收款仍可在原业务办理；余额变化使复核或过量分配拒绝。财务明确重算产生新账单版本，保留旧版及其真实已收款|
|误记收款更正|财务明确原实收、正确金额、账户、流水号、日期及同客户逐单分配；经理独立复核|原现金及原支付不改，追加反向账务调整和可选正确重记，关联不可变 Correction；确实未到账时允许正确金额为零，不创建零元现金。默认保留原真实到账日，也可明确更正后的实际日期，不可晚于今天|未执行可取消；正金额执行后可从后继记录继续追加更正。反向调整不是银行退款；已退款或已分配占用的来源须保留原业务事实并先解决冲突|
|普通会员充值／独立预收误记更正|财务从有效原款选择，独立经理批准；减额不得侵占已消费、已抵用、实际已退款或已批准占额|原发行和收款保持，追加反向调整、可选正确重记和本金差额；批准减额占用未用本金，执行与释放同一事务；会员内部往来成对记录，不新造中心现金|未执行可拒绝／取消；后续真实原款退款使用当前有效金额和账户。充值套餐按原批次完整份数同步原赠品；本金或赠品已用不足时须先走原业务合法回退，不凭空增加债务|
|其他入库退货应收|必须已有本店 warehouse 的 other_in_return 实际出库，原 StockMove 为 wh_other_return，数量、原成本及原入库关联完整|财务核对供应方并提出明确应收，经理批准建立独立应收，申请和批准不生成现金。财务可分笔凭真实凭据收到退货款|批准前可取消／拒绝；批准后通过独立目标更正追加修订，原批准不改。目标低于净收款时形成超收应退，另经独立批准和原账户实际退款；不能取消抹账|

审批与执行为当前门店相应待办员工办理，主管可通过已有明确转交操作处理责任交接。新单及待办试用默认预计两日办理；超期只显示待办，不自动扣钱、退款或关闭原业务。集团汇总为只读，无集团汇总写入口。

普通整车订单、轻量维修和附加业务仍使用原流程版本关口。详细维修 v3/v4 必须先完成客户授权、质检与承担冻结，仅其客户承担参与结算。精品必须已确认报价且没有在办退货。集团本金、券包和预收的占额都纳入原单可收余额；原单、原预收和真实账户均参与版本或行锁，不能靠更换请求编号盲重试。

## 原单退货和集团核销回退

精品实际原单退货或未发货取消后，若已付额超过剩余应收，先追加回退原预收抵用，恢复同客户原预收余额；再按原现金收款允许剩余退款。整数分摊沿用原精品退货事实，没有实物退回或明确取消不能回退。

已交车后的本金、券、套餐或预收抵用，通过独立售后方案中的原路退回办理。`group_aftercare` 不提供普通外部端点，每次必须由 `aftercare_service.assert_group_plan` 核验本店原单、经理批准、当前方案及客户确认：批准时占原核销剩余，取消只释放，生效时追加原钱包返还、原单负向支付关联及原内部往来冲正。不产生现金；预收返还的是原余额，客户实际提现仍须另走原预收退款。

券或套餐只能退原冻结整数份；原到期日、规则版本、适用门店及优惠承担均保持不变。已经过期的权益可以按原方案返还历史批次，返还不自动延长有效期，也不折现。交车前普通核销撤销的关口保持原状。

维修和精品的消费积分按已履约客户净消费累计取整，预收抵用计入原客户支付。售后减少净消费后，先追回本次消费原批次未占用积分；已被消费的不足部分记“待追回积分”，不会阻止合法的本金回退或实际现金退款。审批、资金执行及积分变化用本次已生效原业务关系关联凭据，不借别店、别客户或未批准售后文件。

## API 与模型接入

`/api/business-finance/orders` 建立独立财务单；`/orders/{case_id}/actions/{approve|execute|collect|cancel|reject|recalculate}` 使用 `request_id`、FinanceOrder `version`、Case `case_version`。办理原单的动作额外提交 `source_versions`。真实收退款金额为正整数分；误记更正及目标修订可明确为零。普通集中收款分配须为 1–100 个不同原单且合计等于一次实际现金；整笔未到账撤错使用零正确金额及空分配。已实际退款后的更正显式使用 remaining_after_refunds：正确总额包含保留的原退款，逐单分配只包含正确剩余金额；零剩余分配仍保留已实退的正金额总款。相同人员及相同内容的请求可重放，冲突内容和过期版本拒绝。

只读入口 `/sources?customer_id=`、`/advances?customer_id=`、`/receipts?customer_id=`、`/other-returns` 提供当前有权选择的原始来源。员工页面以客户、原单号、账户名和供应方名称选择，后台复验全部相关 ID。

`business_finance_sources.case_credit_amount` 与 `case_reserved_amount` 为原业务支付/占额接口；`sync_source` 在同一事务内同步原单任务、消费积分和开票上限。详细维修的 RepairPayment 与精品 RetailPayment 均明确绑定集中付款对应的 PaymentLink 和本次财务凭据，不再依赖“一个现金 ID 只能一个原单”的假设。

追加迁移为 `x824_business_finance`，依赖 `w723_aftercare`。该迁移建立 14 个业务财务表及 2 个原核销售后桥接表，将原 PaymentLink 的现金唯一键与账户凭证唯一键改为索引。银行流水去重仍由本店账户串行、全部现金/支付来源校验及原始 Correction 链保障；只有明确 CashBatch 可一款多单。

本次追加 `u13h_finance_corrections` 与 `x46k_supplier_overpayment`，旧迁移不改。前者建立本金更正申请、执行事实和应退目标修订；后者增加真实供应方超收退款申请及占额。两者之间的采购预付和加装赠品修订按迁移链保留，详见[原收款更正与供应方超收退款](原收款更正与供应方超收退款.md)。

## 统计与恢复

`business_finance_analytics` 同时生成图表和明细，CSV 使用同一明细集合：当前预收余额、期间预收流水、最新未完成客户账单尚可分配额、有效实际集中收款分配、期间办理的误记更正差额、其他入库退货待收款。

预收余额和业务抵用都不重复计营业收入。普通集中收款的分配合计只对应一次真实现金；部分退款后误记更正的净分配与总款差額必须由不可变原退款切片证明。误记更正的原款与反向调整从“有效实际现金”排除，正确记录按冻结的真实到账日统计；办理日差额另表。客户月结冻结额度不能作为新增应收，也不代替原单当前余额。集团汇总不显示本模块客户姓名和可写的原单路由。

历史门店对账定义 v3 保存当时有效现金排除集合，旧定义不随后续原充值更正扩展。新定义 v13 增加本金更正及目标修订，v14 再增加供应方真实退款，v17 增加组合充值更正，v20 增加部分原退款切片；当前有效现金为定义 6，旧定义和旧封存只保留原始来源集合。`validate_business_finance_sqlite` 核对原预收流水/余额/占额、原抵用退回限额、实际现金的全部逐单分配、冻结账单摘要与后继版本、原款更正链及日期、原物资退货成本和售后批准关联，新增校验本金差额、修订链、逐笔真实退款及占额上限。总恢复还校验原业务关联、每个附件字节 SHA256 与扫描状态。

## 本轮验证与保留限制

自动测试见 `tests/test_business_finance.py`、`tests/test_group_aftercare.py`、`tests/test_business_finance_analytics.py`。涵盖真实 API 采购/维修/精品来源、经理独立审批、原单与账户竞态、重复请求、旧版本、跨店拒绝、普通凭据不能冒充收款凭据、部分退款与整数价值守恒、不同承担隔离、原本金/套餐/预收回退、积分不足追债、非空恢复及篡改拒绝。

`tests/browser_business_finance.py` 已用真实 Chrome HTTP 和 390×844 视口，以服务顾问、独立店长及财务账号跑通十一项检查：实际预收与批准抵用、一款多单月结、原误记追加更正、预收及普通会员本金更正、整笔零到账撤错、更正后的未用原款退款及跨店拒绝、已到账后供应方目标调低、超收原款实际退款、已实退原款的正确剩余分配、后继原账户真实退款；零 JavaScript 错误。扫描采用显式 `structure_only`，界面标明未查毒；此验证不代替生产 HTTPS 或严格扫描。关键截图已人工检查，细节与最终自动验证成绩见本次专项记录。

当前未支持跨客户/跨门店抵用、保险厂家集中代收、外部银行直连、会计总账、预收利息或币种换算。有原业务支付关联的客户实收、普通会员充值和独立预收已可追加误记更正及明确零到账撤错；已批准其他入库退货应收也已可追加目标修订及原款超收退款。充值套餐现已增加原批次权益联动，详见[专项记录](充值组合原款误记更正.md)。已不可逆消费时须先核对原业务处理及公司责任规则，不擅增追偿／损失模块；通用业务实收部分退款后的剩余切片更正已在 d02q 按原退款依据实现，见[部分退款后原收款误记更正](部分退款后原收款误记更正.md)；续会费误记仍作为需复核的审计候选，不据此扩大压缩原表范围，也不将本轮结果等同 HK-090 全分支完成。公司业务验收及全量 193 项验收仍需逐项完成。
