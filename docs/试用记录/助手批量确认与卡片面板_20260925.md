## 二、"连续批量确认"是什么（业主 2026-09-25 的澄清）

> "我说我现在要直接进入订单流程，然后你就把所有前序流程按照顺序以分组形式直接给我让我挨个确认点，
> 点完之后直接触发下一轮对话，按照上下文直接生成订单合同。就是其他流程都是类似的，
> 用户很有可能说了一个中间流程，你就需要直接以批量卡片形式返还给他"

按这个口径改了三处：

1. **提示词**：员工报的是中间/最后一步时，先想清**前序链**，在**同一次回复里按顺序把所有步骤的确认卡都准备好**，
   每张标 `step_order`/`step`（服务端存下来，页面按"第 N 步"分组）；资料不全时**能办的先办**，
   缺的在同一段话里一次问清，不许一步一步问、更不许一步一轮。
2. **页面**：每个步骤一组，可「全部确认（N 张）」；右上角还可以「**按顺序全部确认（N 张）**」走完整条链。
3. **服务端**：`POST /api/business-assistant/sessions/{id}/proposals/batch`——员工一次点击，
   服务端**逐张照办**：各自的 digest、岗位、门店、版本、过期和业务规则校验，各自提交、各自留痕；
   失败的那张单独报回来，不影响其它张。模型**不能**调用这个入口（它只接受员工在页面上的那一次点击）。

## 三、真实模型试跑（一次性实例，不碰预览库）

用业主给的场景（"章先生看完车要直接订车……最后打印订单合同"）：

| 轮次 | 结果 |
|---|---|
| 1 | 第 1 步「售前接待」1 张（客户/电话/车型/来源齐全），并说明后面几步等确认后再准备 |
| 2（一次「按顺序全部确认」后自动继续） | **同一轮准备出第 2 步「分派接待回访」+ 第 3 步「车辆报价」共 2 张**，说明第 4/5 步要等真实报价编号 |
| 2 执行 | 两次批量确认：1 张办成（生成接待单 `HK20260925-…`），2 张被系统按业务规则拒绝并**逐张报回原因**（报价需选本客户名下车辆或已有接待单；分派岗位不匹配），助手没有谎报成功 |

另一轮故意让车型目录为空：助手列清了整条链，只准备能办的第 1 步，并说明"车型目录为空、
报价单选不到真实车型，不能编造"，给出两条可行路径（补车型资料 / 找有权限岗位）。

```
python tests/assistant_chain_probe.py --output <仓库外目录> --confirm --rounds 1
python tests/browser_assistant_batch_cards.py --screenshots <仓库外目录>   # 真实 Chrome
```

## 四、顺带修掉的一个真问题

一轮要准备十几张卡时，非思考模式的 **2500 token 上限会把回复截断**（`finish_reason=length`），
而代码把它归进了"连接异常"——员工看到的是"业务助手连接异常，请稍后再试"，实际是内容被截断。
现在上限提到 8192，并把截断单独报出来："这次要准备的内容太多，模型回复被截断。请发送'继续'，
我会分几轮接着办。"（不再冒充连接故障；提示词也要求一次回复最多准备 12 条左右，剩下的下一轮继续。）

## 七、第二轮反馈：删掉回复上限 + 卡片必填项（提交 `6e353cf`）

业主："1.为什么要设置回复上限啊，赶紧删掉！ 2.需要员工回答的部分，你能不能在分组卡片的单张里
把这些选项列为必填项，只有确认过后才能继续点下一张"

### 7.1 回复上限全删

| 原来的上限 | 现在 |
|---|---|
| 下发 `max_tokens`（先是 2500，后改 8192） | **不再下发**任何输出长度上限，长度由服务方自己的上限决定 |
| `PER_ROUND_TOOLS = 12`（一轮只执行前 12 个工具，其余回"未执行"） | **删除**：一次回复里提多少个准备调用就执行多少个 |
| 提示词"一次回复里最多准备 12 条左右" | 删掉，改成"没有一轮最多准备几张的限制" |
| `HARD_TOOLS = 200` | 保留，但只是**畸形回复兜底**（一次提 200+ 个工具调用按无效拒绝），不是给员工的额度 |

### 7.2 卡片必填项（迁移 `h51i_proposal_questions`）

- `prepare_operation` 新增 `questions`：`key`（落到哪个字段）、`label`、`options`（服务端查到的真实候选：
  人员/车型/账户）、`required`（默认必填）。存在卡片上，会话视图里返回。
- 页面在这一张卡里渲染：有候选就是**下拉**，没有就是文本框；**没填完不能点"确认办理"，
  也不能翻到下一张**；整组的"全部确认"和右上角"按顺序全部确认"在组内还有没填完的卡时禁用。
- 确认/批量确认带上答案：服务端先卡住没填完的（409，列出缺哪几项），只接受**这张卡自己声明的 key**，
  落到原接口的真实字段上（精确命中优先；模型写成 `quote.model_id` 这种带前缀的，用最后一段 `model_id`；
  通用业务的 `values.字段名` 落进 `body.values`），并**再走一次原网关校验**才执行。
- 只有"员工要填的那几项"缺着的卡现在也能生成：准备路径用类型正确的**占位值探一次**确认缺口仅此而已，
  占位值不会进卡片，员工填完在确认时按真实字段再校验。
- 提示词：查不到的、只能由员工决定的事实**做成那一步卡片上的必填项**（有真实候选就列成选项），
  不再在聊天里来回问。

验证：真实 Chrome 用例增加了"第 3 张卡的两个必填项 → 确认与翻页都禁用 → 填完自动放开 → 批量确认里
带上答案"（截图 `assistant-cards-required.png`）；真实模型试跑里助手在第 1 步卡上列了"关注车型"必填项，
填完确认 1/1 办成，下一轮自动接着用真实接待单继续；24 个前端 Node 用例、66 个 JS 语法检查、
