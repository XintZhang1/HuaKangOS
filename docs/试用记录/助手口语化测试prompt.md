# 业务助手口语化测试 prompt（XC 试用 · 随手说版）

目的：员工在真机上不会照着手册说话。这里故意写**随意、口语、缺信息**的说法，看助手能不能：
① 自己把该查的查出来（不把找资料的工作推回给员工）；② 缺关键事实时只问必要的一两个问题；
③ 说清"下一步能办什么、还差什么"；④ 该走的确认卡给出来、不该办的（没权限/规则不允许）说清楚；
⑤ 不编造客户、金额、编号、审批或"已经办好了"。

用法：在预览里选对应岗位账号 → 左侧"业务助手" → 直接粘贴下面的话（**不要补充任何解释**）。
每个编号建议**开一个新对话**，避免上下文互相帮忙。

> 数据前提：R02/R03 的公共资料与维修基础资料建好之后，涉及供应商/保险公司/作业项目的问法才有东西可选。

## 一、售前与客户（xc-sales 陆销售 / xc-reception 周接待）

| 编号 | 直接粘贴这句话 | 想考什么 | 红灯（说明没帮上） |
|---|---|---|---|
| P01 | 我那个客户说周五再来，帮我记一下 | 缺客户/单号时是否先查本人接待单，再问"是哪一位/周五几点"这类必要问题 | 张口就要内部编号；或直接编一个客户名办完 |
| P02 | 刚才那个接待单意向挺强的，帮我往下走一步 | 是否先列出本人待跟进的接待单让员工选 | 自己挑一张最新的就改；或说"我这边没有入口" |
| P03 | 客户电话我忘了，13900001111 这个是他的吗 | 是否按电话查客户/接待单，而不是凭空确认 | 直接说"是的"（编造） |
| P04 | 帮我建个新客户，姓张，电话回头再补 | 是否说明电话可稍后补、并准备新客户确认卡 | 因为缺电话就整个拒绝 |
| P05 | 这个客户之前修过啥？ | 是否按客户查历史维修/工单，且只说本人可见范围 | 编造历史；或答"查不到"却没试 |

## 记录方式

每条记录四件事：**助手的原话**、**有没有给出确认卡**、**有没有乱编**、**员工要不要再补一句才能继续**。
判"能辅助用户"的最低标准：P01/P02/P07/P10/P12/P23/P27 这七条里至少五条**一次就问到点上**，且全程零编造。

## 首轮实测（2026-09-25，一次性实例 + 真实 deepseek-flash，不碰你的预览库）

跑法：`python tests/assistant_probe_instance.py --output <仓库外目录>`（自建临时库与端口、建 5 个 probe 账号、
按普通接口建 1 张售前接待单，然后用同样的口令逐条问；**不确认任何卡片**）。
结果文件：`results.json` / `results.md`，另有 `tests/assistant_prompt_probe.py` 可对你的预览直接跑（需要账号口令）。

**一次就问到点上的（12 条）**：P01/P02/P27 读原单状态说清"卡在待分派、该谁办"；P03 用真实记录核对电话、
不硬认；P04 发现同名客户先问是否新建；P05/P11/P12/P13 查不到就说查不到并给出下一步；
P06 说清 S5 还没建档；P08/P09 说明前置未完成而不是硬做；P21 找到对账入口并按岗位判断可进入；P26 明确"没有可引用的被挡记录"。

**首轮暴露的问题（已修）**：

| 问题 | 表现 | 修复 |
|---|---|---|
| 搜不到入口就说"系统没有这个入口" | P15 采购、P18 调拨、P19 开票、P24 报表/销量、P25 账号：功能明明存在，助手却回答"我这边没查到入口" | ① 目录检索加上**领域别名**（采购/开票/调拨/账号/报表/销量/盘点/退卡…都按员工原话能搜到）；② 搜不到时返回领域清单并要求换词再搜；③ 系统提示新增硬规则：**说"没有入口"之前必须先用员工原话搜一次**，确实没有才可以说。复测 P15/P18/P19/P24/P25：全部改成"入口找到了，还缺 X"或"这个入口对 XX 岗位开放，你这边看不到" |
| 多步目标用满工具轮次后回一句"请发送继续" | P15 首轮回复是"本次还没准备好操作。请发送继续" | 轮次接近上限时给模型一条收尾指令：用已查到的信息直接回答或只问一个必要问题。复测 P15 变成"供应商和物资查询都是空的，请确认供应商与机油滤芯的名称/编码" |
| 盘点等"流程类"词搜不到 | P17 盘点 | 领域别名补到流程域（盘点/领料/退料/报损），复测 P17 直接说出盘点要在库位执行 |

**还没验证到的**：P07–P09、P14、P19–P20 需要一张走到报价/订单/会员的完整单据才能真正压测（首轮临时库里只有一张待分派接待单）。
建议在你的预览里按 R02→R14 建出真实数据后，再跑一遍这一批，尤其 P07/P08/P14/P19/P20。

**工具预算（2026-09-25 放开）**：一轮最多 24 个模型轮次、每轮真正执行 6 个工具、单轮总时长 300 秒；
私有配置 `%LOCALAPPDATA%\huakangos\business-assistant.json` 里可以加 `"max_rounds": 4–40`、
`"turn_timeout_seconds": 30–600` 自行调整（不写就是默认值）。接近上限时助手会先收到"收尾"指令，
所以不会再出现"本次还没准备好操作，请发送继续"这类空转回复。

## 点确认的实测（2026-09-25，一次性实例 + 真实模型，业主同意测试期直接点确认）

信息齐全的三条短句（C01/C02/C03）走完"聊天 → 确认卡 → 点确认 → 真实落库"：

| 编号 | 说的话 | 助手准备 | 点确认后的真实结果 |
|---|---|---|---|
| C01 | 新建客户：李试用，电话 13900002222，允许后续联系 | 新建客户档案确认卡 | HTTP 201 建立客户 `id=2`（姓名/电话/联系意愿与卡片一致） |
| C03 | 给客户 13900001111 开维修工单：车牌试用A1001，故障是刹车异响 | 维修工单确认卡 | HTTP 201 生成 `HKR20260925-F9802FE095A3`，状态 `assessment`，可办事项 `quote/authorize/quality/release/cancel`，车牌与故障按卡片写入 |
| C02 | 把这张接待单分派给试用销售（店长） | 分派确认卡 | HTTP 200，接待单由"待分派"变为"待接待反馈"，负责人改为试用销售，版本 1→3 |

要点：确认前助手只说"已填好请核对"；点确认时用的是卡片 digest，和页面点按钮走的是同一个入口
（`POST /api/business-assistant/sessions/{id}/proposals/{pid}/confirm`），落库仍由原业务接口按员工本人的
岗位、门店、版本与幂等执行——助手全程没有替员工确认，也没有绕过任何校验。

跑法：`python tests/assistant_probe_instance.py --output <仓库外目录> --confirm --only C01,C02,C03`
（`--confirm` 只对一次性测试库使用；不加这个参数时探针只发消息、从不点卡）。
