## 二、现在的做法：**整表一次发，不再分批**（2026-09-25 业主裁定后）

你问"为什么需要一批一批上传，是被轮次或者工具调用卡住的吗"——是，卡在**我加的三道自设上限**上，已经全部拆掉：

| 原来的限制 | 值 | 现在 | 为什么原来会卡住整表 |
|---|---|---|---|
| 单条消息字数 `MAX_MESSAGE` | 6000 | **12000** | 67 行整表约 6700 字，超了就被截断，只能分批发 |
| 每轮真正执行的工具数 `PER_ROUND_TOOLS` | 6 | **12** | 一轮只能准备 6 张卡，67 行要十几轮 |
| "连续两次返回过多工具就停止处理" | 有 | **删除** | 模型一轮提几十个准备调用是整表导入**正常行为**，却被当成异常掐断 |
| 同时挂着的待确认卡 `MAX_PENDING_PROPOSALS` | 20 | **200** | 第 20 张之后就报"待确认操作已达上限"，整表必然跑不完 |
| 单轮时长 / 轮次 | 300 秒 / 24 轮 | **600 秒 / 24 轮** | 一轮要准备几十张卡，300 秒不够 |
| 工具调用总预算 | 轮次×3 | **轮次×12** | 24 轮 × 12 = 288 次，够整表 |

保留的只有两个"防跑飞"的硬闸：一次返回 **200 个以上**工具调用按无效回复拒绝、总调用次数有上限。
**没有任何按表格行数设的限制**：一次上传、一个会话、一次发送就够了。

实测（同一个 67 行 xlsx，一次上传，一个会话）：

| 轮次 | 结果 |
|---|---|
| 第一次整表实测 | 卡 56 张、确认成功 56 张 → **车型目录 0 → 55**（车系 18、待确认归属 0） |
| 第二次整表实测 | 卡 122 张（三轮准备）→ **0 → 60**（车系 20、待确认归属 0）；同一车型在同一车系里按"名称+年款"复用同一条（`create_entry` 命中已有记录就返回，参数不一致才 409），所以重复确认不会建出重复车型 |
| 第三次（单轮、不重试） | 卡 50 张、确认成功 50 张 → **0 → 50**（车系 13、待确认归属 0） |
| 第四次（加了"卡数由系统给"的修之后） | 第一轮一张卡都没准备（"只说不做"，脚本自动换会话重试一次）→ 第二轮卡 **60 张**、确认成功 60 张 → **0 → 60**（车系 20、待确认归属 0） |

四次都没有"按行数被拦"的报错；差异来自模型每轮决定准备多少行（真实模型不是确定性的），
但**每一次都是"上传一次 → 助手逐行准备卡 → 我逐张点确认 → 目录真的增加"**，`未确认归属 0` 说明车型都挂上了车系。
第四次它这样收尾，数字和系统统计一致：

> 本轮共生成 60 张待确认卡，请逐张核对点击确认。
> 未成卡的行及原因（原样）：第 39、40 行（元PLUS 540km…）电池容量为空，纯电必填；第 47、48、49 行（唐 EV 各版）……
> 第 51–55 行（大唐 DM-i/DM-p、大汉 DM、宋Pro 激光雷达版）已按现有字段成卡，指导价与电池容量留空未填。

### 空值被"留空/填 0"的行（口径要你定）

第四次实测的库里查了一下：60 条车型中 **10 条指导价为 0**（大唐 DM-i/DM-p、大汉 DM、宋Pro 激光雷达 ×2，
以及表里那 5 条"在售车系，价格未核实"的占位行），其中 **5 条插混车型的电池容量也是 0**。
系统没拦——`VehicleModelInput` 只对**纯电**强制电池容量，插混不限；指导价也没有"必须大于 0"的规则，
而卡片上确实显示"指导价 0.00"，员工（这次是脚本）是看着这个数点的确认。三种口径请你选：
① 就这样（0 = 未公布）；② 给接口加"指导价必须大于 0"，未公布的车型先不录（会一并挡掉未上市的换代车型）；
③ 表里这几行先删掉，等官方公布价格再导。

### 系统按业务规则拒绝的行（不是助手乱猜）

纯电车型缺电池容量时，`VehicleModelInput` 的硬校验会拒绝，助手把这些行**原样报回来**，没有谎报成功：

```
{'status': 422, 'message': '纯电车型排量必须为零，并填写动力电池容量', 'route': 'vehicle-catalog'}
```

第三次实测里它这样收尾：

> 已按清单逐行生成待确认卡，共 44 张（第 1-38、41-46、56-61 行）……
> 以下 23 行因缺必填字段无法成卡，需要先补资料：缺电池容量（纯电必填）：第 39、40、47、48、49、50、62 行；
> 缺指导价：第 47、48、49、51、52、53、54、55、62、63、64、65、66、67 行。

卡是真的（实际 50 张，确认后目录 +50），但**它自己报的数不准**（说 44 张、说 23 行缺字段，
去重后其实是 17 行）——这是下一节修掉的第 3 个真问题。

### 车型挂车系（你点名要做的这条）

`POST /api/vehicle-catalog/entry` 一次提交就带 `brand_name + series_name + 车型参数`：系统按名称查找或新建品牌与车系，
并写 `ModelClassification` 把车型挂到车系下——**不需要先建车系再挂**。实测确认卡 payload：

```json
{"brand_name":"比亚迪","series_name":"元UP","name":"元UP 飞驰版 401km 领航型","model_year":2027,
 "fuel_type":"electric","seats":5,"displacement_ml":0,"battery_wh":45120,"guide_price_cents":8180000}
```

早期助手会把"车系"这一项漏掉（只填品牌），导致车型显示"未确认车系"；在导入指令里明确写出字段名
（`series_name=表里的车系列`）之后，四次实测的 `未确认归属` 都是 0。单位也要交代清楚：指导价表里是元、
接口要分（×100），电池容量表里已是 Wh。

## 三、这轮实测暴露并修掉的三个真问题

| 问题 | 现象 | 处理 |
|---|---|---|
| 模型"只说不做" | 长会话里它会照抄自己上一轮的话："第 7 批 4 张待确认卡已真实生成"，而数据库里**一张卡都没有**（查过 `business_assistant_proposals`：该批 0 行） | 服务端新增纠正闸：模型没有工具调用、却声称"已准备/已生成确认卡"、而本轮确实 0 张卡落地时，退回一轮要求它真的调用准备工具或改说没有准备（`claimed_actions` + `proposals_since`，新增用例覆盖） |
| 长会话里重复准备旧批次 | 同一个会话里连发 12 批时，模型把第 1 批的行反复准备（12 批共 72 张卡只有 13 种车型） | 批量导入改为**每批开新会话**；整表一次发之后这个前提也不必要了（一轮就能把整表准备完）。同一车型重复确认按"名称+年款+车系"落到同一条，不会重复建（第三轮实测 122 张卡只建出 60 条） |
| 汇总数字自己口算、和卡数对不上 | 实际 50 张卡，它说"共 44 张"；说"23 行缺字段"，去重后 17 行 | 卡数只有系统知道：每一轮把权威数字作为一条系统消息塞进上下文（原地更新，不堆消息）——"系统统计：本轮到目前为止实际生成 N 张待确认卡……请直接使用系统这个数字，不要自己数"。新增用例锁住它；第四次实测它报的"共 60 张"和系统统计、目录新增数**完全一致** |

另外修掉一个**试用脚本自己的 bug**（不影响产品，但会让试用报告说谎）：一次确认几十张卡时，确认接口回的是
"这个会话的一批待确认卡"（最多 12 条）而不是只回这一张，脚本原来取 `proposals[0]`，于是把第一张卡的明细
抄到了每一张上（报告里 111 条确认记录长得一模一样、`request_id` 全相同）。现在按 `id` 找回自己那一张，
报告里每张卡的明细、结果、拒绝原因都是真的。

结论修正：**不需要分批上传**。助手能一次性吃下整表、逐行准备卡、把系统拒绝的行如实报回来；
要留意的只是"它汇总时的数字别信口算，以页面上的待确认卡和系统统计为准"（现在系统会把数字喂给它）。

## 三之二、代码评审（Codex 对 PR #9）提的四条，全部采纳并已修

| 评审意见 | 为什么是真的 | 处理 |
|---|---|---|
| **前序事实没回到模型手里**（P1） | `validate_operation` 算出了 `prerequisites`，但 `prepare_proposal` 只把 `path_args/query/body` 写进卡片、返回的卡片视图里也没有这一项——"第二条限制"其实只写在提示词里，模型根本看不到 | 工具结果里带上 `prerequisites` 与一条 `prerequisite_rule`（逐项确认、不许替员工新建中间单据），同时写进这张卡的 `result`，页面上待确认卡会显示"办理前请先确认：…"（新增 Python 用例 + 前端用例） |
| **待确认卡上限 200 与会话只回 80 条冲突**（P1） | 81 张以后的卡拿不到 id/digest，员工既确认不了也取消不了 | `session_view` 的窗口改成"**全部待确认（上限+余量）+ 最近 40 张已办完**"，保证每一张能点的卡都在返回里；新增用例插 95 张卡验证最旧那张仍可见 |
| **写操作被挡后评审提示丢了**（P1） | 读路径有 `hint`，写路径走"员工点确认 → 原接口"，`confirm_proposal` 只存 status/message/data/route，提示被丢掉 | 确认结果里保留 `hint`，并在员工看到的文字后面补一句人话："这一步需要更高的岗位权限；可以让助手按这条被挡记录准备一张评审申请卡，提交给店长评审"；新增用例 |
| **会话租约 4 分钟盖不住 600 秒的一轮**（P2） | 长任务跑到第 5 分钟会被当成"已中断"，第二条消息可以进来，两条链交错写提案 | 租约按本轮上限算（`busy_lease_seconds`＝轮次上限+60 秒），并在每一轮续租；新增用例（含 30 秒下限的边界） |

这一轮改动只在助手自身的服务端与页面渲染，**没有碰任何业务接口、迁移或预览数据**；助手专项 47 项、
助手+范围+评审三个模块共 96 项、24 个前端 Node 用例、66 个 JS 语法检查全部通过。

## 四、留给你的三个决定

1. **剩下 12 行怎么处理**：元PLUS 540km 各参数页都只有 430/510/630km，没有 540km 版本；唐 EV 730km 在售的是 2024 款荣耀版
   （108.8 kWh，与表里 2026 款不是同一车型），830/850km 与大唐 EV 800km 属换代车型、官方未上市未公布参数；
   海豹/海豹06/海豹07/海豚/海鸥/驱逐舰05 只有车系没有具体配置或没有价格。系统按业务规则拒绝它们（纯电必须有电池容量），
   助手如实报了回来。可选：① 先不导入这些行；② 用官方上市后的参数页补；③ 允许我给"未上市"行填 0 并标注（系统会拒绝纯电 0，走不通）。
2. **空值口径**：见上面"空值被留空/填 0 的行"——0 元指导价、0 kWh 插混电池现在都能建进目录，要不要在接口上加正向校验。
3. **要不要把这套导入做成正式功能**：现在的做法是"上传表格 + 助手逐行准备 + 员工逐张确认"，50–60 行要点 50–60 次。
   如果需要，可以做一个**受控批量导入**：一次确认一批（同一批参数在同一张卡上列出），仍然走原接口、仍然逐条校验。

## 五、怎么重跑

```
# 整表一次发（一次性实例，不碰预览库；会真的点确认）
python tests/assistant_catalog_import_run.py --output <仓库外目录> --whole

# 老的分批方式（每批 6 行、每批新会话）
python tests/assistant_catalog_import_run.py --output <仓库外目录> --batch 6

# 只跑前 5 行、先看它准备什么（不点确认）
python tests/assistant_model_import_probe.py --output <仓库外目录> --rows 5
```
