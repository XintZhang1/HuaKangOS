# huakangos 正式期初核验

这份流程用于启用**本店尚无客户、库存及真实业务的正式新库**。启用经营主体策略后，可以先配置并独立批准真实资金账户，再按编号向这些账户导入期初余额。支持客户主档、资金账户日初余额、物资目录和有来源的期初数量价值，以及已在店、经确认可售的首次车辆库存。已有演示资料、旧业务或已确认期初的门店明确拒绝。系统不会删除旧资料来腾空目标库。

这不是未结业务迁移。原需求 HK019「车辆请款导入」、HK027「请款导入车辆发货」、HK028「请款导入车辆到货」仍属于采购业务批量办理，**不能以本期初入口代替验收**。本次补充建设计划阶段二的安全启用基础，并衔接 HK177/178 的车型和整车仓、HK183/184 的物资目录与仓储来源；不因此将这些原需求全部标为完成。

## 员工办理

1. 管理员先建立门店与真实岗位账号；主管维护本店启用的车型、整车仓或混合仓及明确库位。至少要有不同员工承担准备、主管复核、库管和财务核验。准备人可以参与另一项有权限的核验，但批准主管、库管、财务必须分别由不同经办人确认，管理员也没有同人豁免。
2. 准备主管进入“正式期初核验”，加载虚构示例了解格式，再选取公司已核对的 JSON 原资料。客户以明确来源行创建独立主档，指定负责账号；电话仅作为原资料字段，绝不自动合并客户或集团身份。
3. 执行“逐行预检”。错误明确到资料类别、行号和字段，不能用错误批次继续。原始 JSON 的字节摘要、来源编号、日期、数量金额，以及车型/库位/父仓和客户负责人账号映射固定保存。单文件最多 120,000 UTF-8 字节，最多 300 客户、100 账户、300 物资、200 车辆。
4. 上传本人核对的来源凭据，执行“试导入并回滚”。系统实际插入并检验本批关联与约束，然后回滚客户、账户、物资、车辆、共享 VIN 保管与库位账，正式数据库中不会留下这些试插入对象。只保留预检、回滚通过及操作证据。
5. 另一位主管上传本人复核依据并批准。这一步不产生实际库存或现金。
6. 库管对照当前实车与实盘资料，重新输入每台 VIN、库位编码和各物资数量；财务上传本人财务核对表，分别输入每个账户的日初余额、物资原价值合计、车辆原成本合计。一分钱、一个 VIN 或一个库位不一致都拒绝；各账户不能用一增一减抵销差异。没有实物资料的批次不强制库管核验；没有账户和实物价值的纯客户/零库存目录批次不强制财务核验。
7. 三岗依据齐全后，最终确认待办交回批准主管。主管核对资料摘要、各岗凭据、数量和金额，一次启用。本批客户、账户、物资及车辆和所有来源账在同一事务提交。版本过期、其他批次抢先启用或 VIN 冲突时，整次失败，不留部分入账。

待办默认七天，逾期仍保留原责任人，不自动猜测核验结果；主管可转交给本店有相应岗位的其他员工。手工交接不会被后台同步重新覆盖。实物与财务核验必须在最终确认的**同一本地日**完成，按配置的 `APP_TIMEZONE`（默认 `Asia/Shanghai`）判断；跨日请取消旧批次、核对新资料并重新办理。

### 正式主体策略与期初账户

正式环境先完成“经营主体版本 → 门店绑定 → 实际账户绑定 → 启用新业务主体冻结”的独立申请批准，然后办理本流程。空库检查允许这些配置申请与已批准账户；任何已有客户、物资、车辆、现金、实物流转、真实业务或已确认期初仍拒绝。

策略模式的每一条 `accounts` 必须明确提供 `account_id`，以及完全一致的 `name/account_type`、非负整数分 `opening_balance_cents` 和核对来源 `source_reference`。账户必须是本店启用、已经批准且与本店冻结经营主体一致的实际账户。不能按相同名称自动认领另一账户，也不能创建尚未批准归属的新账户。界面列出本店可用批准编号，策略模式的虚构示例将 accounts 留空，防止把示例余额套到实际账户。

预检事件固定 `account_context`：本店策略、门店绑定和主体资料版本，以及逐行账户编号、账户版本、名称/类型、批准渠道绑定与其主体版本。试导入、批准、各岗核验和最终确认都重新核对；账户版本或批准绑定改变后必须取消重新预检。试导入复用原账户，回滚新增客户、库存、来源账和保管记录；最终确认也不会重建账户。

期初批次按创建当天的批准主体负责，保留资料中的原期初基准日。这不表示该主体在旧基准日曾经批准，也不生成当年的现金交易。策略启用前的旧方式仍只在账户为空时创建账户，明确拒收 `account_id`；不能借旧入口绕过正式策略或三岗核验。

## 可导入的事实

| 类别 | 必要来源和校验 | 最终事实 |
|---|---|---|
| 客户 | 姓名、明确负责人账号；电话可空；联系许可默认关闭 | 独立本店客户及逐来源行创建映射，不自动建立或合并集团客户身份 |
| 账户 | 策略模式显式本店批准 `account_id` 与原名称/类型；非负日初余额整数分、逐账户核对表编号 | 复用原 Account，追加 `OpeningAccountEntry`，与本期实际收付款分开 |
| 物资 | 唯一 SKU、名称/单位、非负数量整数千分位与价值整数分；有数量必须有来源编号 | `Item` 与不可覆盖的 `OpeningStockEntry`；零数量不能有非零价值 |
| 车辆 | 合规17位 VIN、启用车型编码、整车/混合仓库位编码、原成本/标价整数分、逐车来源编号，明确 `available_stock` | 新库存代次1、共享 VIN 身份、中央保管、真实库位、`OpeningVehicleEntry` 和位置记录 |

车辆只支持本系统尚无库存或历史代次的 VIN。已有历史、已售、调拨在途、采购发运或其他车辆作业占用一律拒绝初始导入，不从旧状态推断可售。客户车辆共享 VIN 身份本身不是库存；若身份存在但无库存历史，可明确关联同一 VIN。车辆供应商字段保持空白，不杜撰采购、供应商应付或付款。

物资初始数量保持门店原价值，后续入出存可以逐笔核对 `OpeningStockEntry + StockMove`。本入口不猜测旧物资的库位；需通过现有“库位启用核对”逐项建立真实分布。车辆库位在期初核验时已经明确，后续销售、店内移库、跨店调拨及其他出退库沿用同一保管事实。

## 金额口径与权限

账户页面列示“期初基准日日初余额 + 当日及之后有效实际收入 − 有效实际支出”。期初不会创建 `CashEntry`，不能计入本期收入、采购付款或会员充值。实际收付款仍由既有业务生成；更正原收款时，按现金口径第3版排除被替代原记录与纯记账冲回，避免收支列虚增。界面和 CSV 使用同一集合。

新增实际流水不得早于该账户期初基准日。已有期初来源的账户不能改名或改变现金/银行类型，以保持现有按账户名称关联的现金来源稳定。允许按已有主数据规则停用账户，停用不抹去余额。余额页面不是银行直连，也不会声称与外部银行已自动对账。

主管/管理员准备与批准；库管核对实物；财务核对金额；审计只读。集团汇总上下文不能进入本店期初详情或办理。库管界面/API不提供账户余额、车辆成本、标价或客户联系资料；财务核对页不开放客户电话与联系许可。原始 JSON 仅主管/管理员下载。所有文件继续按本人、本单、门店、文件类别和扫描状态校验；未通过检查的文件不能作为核验依据。

## 异常与恢复

预检失败逐行修正后重新提交。源资料、负责账号映射、车型或库位在预检后变化时，取消旧批次并重新预检；没有任意改状态接口。未正式启用的批次可取消，已上传文件和核验记录保留。正式启用后不能覆盖、删除或再次导入；后续差异通过明确业务处理。

新旧入口共用 `OpeningBatch.confirmed_store_key` 的唯一门店约束。旧 v1 不能绕过新批次的三岗流程；旧 v1 已确认的门店也不能再次走空库导入。历史 `h208_master_data` 迁移保持原样，新表迁移为 `z026_opening_import`，依赖 `y925_private_files`。

恢复验证除数据库/文件完整性外，还重算原 JSON 摘要与汇总，核对各岗本人凭据、审批分离、客户/物资创建映射、账户余额、逐 VIN 首代次、原成本、共享身份和真实库位来源。修改一分钱、错连门店或丢失原核验文件均拒绝。数据库管理员仍具备技术特权，这不是密码学不可篡改存储。

策略模式还核对 OpeningAccountEntry 的实际账户编号、预检固定的账户/批准绑定、原批次 Case 的冻结主体。不能删除或替换这条归属链后仍通过恢复。库管通用事件和专用页面均不显示账户映射、余额或客户负责人资料。

本版没有导入应收、应付、预收、会员余额、旧销售/维修状态、待调拨库存、待验车辆、在途采购、负账户余额或会计总账。上述资料需要独立、有原单和后续结算能力的迁移方案。
