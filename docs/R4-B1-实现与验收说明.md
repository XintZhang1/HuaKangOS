# R4-B1 实现、运行机制与验收边界

## 1. 原范围不变

原 `docs/原始功能需求表.docx`、`docs/requirements.json` 的 193 项映射、`web/workflow-guides.json` 的 111 条发布工作流、已评审能力清单和原迁移目录（65 个版本脚本及 2 个支持文件）按基线校验。十模块功能不以换工具层为由删除。集团直营平级门店、会员仅记账而不接实际支付接口的范围不变。

新工具不是把 193 项各复制为一套新业务，也没有替换销售、维修、财务、库存的原状态机。

## 2. 代码中已经接入的七类工具

| 工具 | 已实现行为 | 明确不做 |
|---|---|---|
| `find_business_objects` | 依原业务查询按名称、单号、车牌等查候选；员工走业务选择器 | 不猜同名对象、不放开管理员账号查询 |
| `discover_business_forms` | 从原生可用目录发现表单，并关联原工作流说明 | 目录未命中不等于系统没有该功能 |
| `inspect_business_form` | 取得实际表单字段、必填、单位、可用动作；原单读取最新版本 | 不让员工或模型手填内部版本 |
| `prepare_business_form` | 解析姓名为真实编号、集中缺项、原 API 预校验、准备真实待确认卡 | 不执行、不跳过原规则、不把缺少来源伪装为有来源 |
| `prepare_business_batch` | 同类独立新建共享表单定义，逐行返回真实卡或错误 | 不把同一原单连续动作伪装为独立批量 |
| `save_work_plan` | 保存目标和有向无环依赖、真实卡/原单/发布工作流引用 | 不接受模型自报完成状态、不产生后续业务 |
| `get_work_status` | 读取草稿结果、实际原单待办、本人/他人/待分派责任 | 不再次调用模型，不自动确认或创建下一单 |

新工具只增强现有工具集，原 `find_workflows`、`get_case`、`list_operations`、`inspect_operation`、`read_data`、`prepare_operation` 等仍作为已评审能力保留。复杂专用销售、维修、财务明细、附件等仍可能使用原工具，不能宣称所有业务都已高层封装。

### 编号、单位、候选

姓名只在当前授权候选中唯一匹配时转换；同名/候选不全返回明确选择结果，不默选第一项，不给所有候选建卡。缺少必填关系时使用真实中文候选；确实没有来源则先返回缺来源，不让员工猜 ID。

金额遵循原生字段单位；新 typed-master 表单的 `*_cents` 按元输入、`*_milli` 按实际数量输入，由 Decimal 精确换算。额外小数精度、非有限数拒绝而不悄悄舍入。原 `prepare_operation` 仍按其原 API 存储单位，提示词明确区分。

新卡的标题、字段和候选名称来自原表单与实际查询，不是模型自由撰写的展示标签。显示人名与单号，提交仍是原编号和原 payload。展示快照与实际员工补填结果单独留在助手元数据；原校验摘要、状态和业务 API 仍为权威。

## 3. 一件事，而不是一堆散卡

多步骤目标可以保存有顺序的计划。模型输入顺序不决定先后，程序验证无重复引用、无循环、无悬空依赖后按依赖排序。原卡必须属于当前员工/门店/对话，原单重新走授权读取；没有原单的未来步骤须引用真实发布工作流。

状态依据实际记录生成：待补填、待确认、已过期、执行中、结果不明、失败、取消、这一步已办理分别显示。取消前一步不算后一步完成；原单没有待办不等于到账、实物交接或外部手续全部结束。

确认新建原单后，从原 API 返回的规范路由取得真实编号，用作依赖证据。随后刷新原单的实际责任人。**本版只保存/展示下一步及其真实依据，不会自动将未来计划变为可执行草稿，也没有实现无人值守的跨模块流程编排。** 下一步需要员工明确继续办理时，助手可以据此准备。

界面增加“本次办事”区，默认展示前两步，其余可展开；长内容在紧凑面板内滚动，不代替原卡片确认区。单项或只读询问没有计划时不强行加空面板。新目标保存后选中新的计划，旧计划仍可切换。

保存、确认或取消后的进度刷新直接读取原接口，不消耗模型调用；只重绘计划区，不清空草稿或已填字段。失败显示读取错误，不把之前成功的提交改成失败；会话/员工/门店切换后的迟到结果被丢弃。

## 4. 与 MCP 的连接

内置 DeepSeek → 原对话编排 → 共享业务工具 → 原业务服务。

外部本机 MCP 客户端 → `scripts/huakangos_mcp.py` → 已登录员工的原 HTTP 入口 → 同一套业务工具 → 原业务服务。

工具 API 从普通员工会话确定身份与当前门店，不接受模型自报的账号或门店。执行调用复用原 CSRF、权限、原单版本及草稿摘要。同一对话的外部调用与内置生成通过原会话忙碌锁隔离，不自动重试结果不明的操作。工具目录没有“确认”能力。

这版附带的是**固定 `2025-11-25` 协议的 tools-only stdio 兼容适配器**。包含 initialize、initialized、ping、tools/list、tools/call、JSON-RPC 错误与结构化工具结果；stdout 只输出协议消息。不是新版无状态协议的实现，也不是完整 MCP SDK；没有远程 HTTP MCP/OAuth/订阅/任务/动态资源/并行取消。

当前环境不能下载 MCP SDK，适配器使用现有 httpx 与标准库。已验证独立进程与本地真实应用 HTTP 链路，**未获得官方 SDK 或任意指定外部客户端的兼容性认证**。后续需要远程多租户接入时，应另行设计标准授权、最小权限令牌、客户端注册与连接生命周期，而不是公开这个本机配置。

## 5. 数据与部署

新增迁移 h52j，仅为计划表与索引。原有域表不重定义。升级检查确实从 h51i 建立合成旧库、放入既有对话和草稿，再升级并逐表比较原行。备份检查额外拒绝计划跨员工/跨对话引用、缺草稿和循环依赖。旧备份没有计划表时仍可检查；应用实际启动前仍须达到当前迁移头。

无需改变业务的部署网络、实际支付接口或增加十个独立 agent。正常部署要一起更新 Python 与前端；独立测试包不要覆盖生产 `.env`、数据库、附件及仓库外助手配置。

## 6. 实测口径

新对照默认 101 个独立场景、202 组。冻结 R3T3 工具＋提示词，与 R4 工具＋提示词同运行时、同合成数据对比，使用不同源码/提示词/工具 schema 指纹。**没有将所有提升归因于 MCP 协议，也没有提前宣称新方案胜出。**

101 场景是开发调试样本而非统计上独立的盲测集；历史失败样本已用于设计修复。283 全量保留，但 193 项说明巡检不能算 193 条业务交易闭环。真实报告回传后还需逐项审阅语义、事实、重复操作、额外追问、工具数和耗时；只通过结构断言不足以证明员工省事。

本轮回归命令、数量和日志在 `docs/r4-validation/results.json`。浏览器证据为真实 Chromium 加载实际 JS/CSS，使用合成数据与原 ASGI API 桥接；环境不允许浏览器直接导航本地站点，没有修改该限制。因而并未验证实际浏览器 Cookie/CSP/同源/代理/登录部署链路。另有真正的 MCP 子进程→本地 HTTP→原 API 测试，两者不要混淆。

本轮真实 DeepSeek 生成请求为 0。原生 Windows 桌面、指定第三方 MCP 客户端、PostgreSQL、多人并发/故障恢复/攻击测试、公司真实数据、附件与完整十模块闭环仍未验收。
