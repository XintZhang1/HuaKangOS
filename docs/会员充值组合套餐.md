# huakangos 会员充值组合套餐

本批实现 HK-123「会员卡储值套餐设置」，并扩展 HK-124 至 HK-127 的组合购买、原款退款和赠品来源追溯。它是**实收全部进入集团本金，再按冻结规则赠送权益**的组合。每笔实际收款只生成一个 `CashEntry`；本金和赠金、积分、券、服务次数分别记账。

功能已经过自动验证及合成员工浏览器演练，尚未经过华慷集团业务验收，也不表示 193 项功能已全部完成。管理员必须明确配置公司规则；新规则默认不启用，系统不预设真实售价或赠送比例。

## 已冻结的业务规则

- 每个组合版本有名称、编号、每份实收本金、发行期间、适用门店、退款期限和补充条款。同编号发布新版本，原规则和已购批次保持原记录；停用通过发布新的禁用版本完成。草稿尚未收款时，旧版本被替换或超过发行期间，不能继续发行，需撤销并按新版本申请。
- 每份实收必须全部成为集团通用本金。组合的适用门店限制**发行及赠品使用**；已存入集团钱包的本金按集团通用门店授权使用，不能声称为限店本金。现有本金可替代、没有充值批次消耗归属，退款核对原充值未退上限和集团当前可用本金，不推断哪一次消费使用了哪次充值。
- 每个版本可包含赠金、积分、券、服务次数各一个明确规则，至少一类。每项配置正整数单位；赠金账本单位为分，积分、券和次数各自使用独立整数。表单中赠金用元展示和输入后严格转换为分。
- 赠品须引用当时最新的、零售价、不单独现金退款的已有冻结权益规则，且适用门店与组合完全相同。抵扣额、内部结算价、优惠承担方、作业编码和有效天数沿用该原规则。随后更新权益规则不会改变已冻结组合的组成；要改变组合需另发组合新版本。
- 购买若干份后，系统分别生成**该购买自身**的赠品钱包，各钱包冻结原规则、数量、证据及到期日；不与其他购买批次合并。组合本金仅通过原 `GroupEntry.topup`、唯一真实现金和中心／门店配对往来记录。
- 含积分的组合会将“先抵原消费退款待追回积分，视为本批次使用并减少可退完整份额”的说明追加、冻结在 `refund_terms`。发行时按已有追原欠额服务扣减新积分，不阻断真实资金退款、不改原积分来源。

## 整份原路退款

第一版只支持退回仍完整的份额。设原购 N 份，已退和已批准占额共 R 份，每份本金为 P，第 i 项赠品每份为 Ui，其原批次可用数量为 Ai，集团可用本金为 B：

`当前可新申请完整份额 = min(N − R, B // P, A1 // U1, …)`

这里的 Ai 必须来自该次购买的原赠品钱包，扣除消费、兑换、积分欠额抵扣和各类占额后计算。**不能用其他同规则批次补足**。例如三份组合每份赠两张券，原六张中用了其中一张，则最多退两整份；剩下的一份不能拆开、临时折现或猜测已用赠品应扣价。

冻结退款期限有两种：

1. 所有原赠品到期前才可申请、批准和执行整份退款。批准后到期仍须拒绝执行，可撤销释放占额。
2. 允许过期后退回仍完整的原份额。过期不会重置余额，也不会延长赠品使用期限。

申请只建立待复核单，不冻结余额。另一位店长批准时重新检查完整份额，并在同一事务中占用集团本金及所有原赠品。申请人不能批准自己的申请，包括管理员。财务接手后按批准的固定份数、金额和原收款门店的原账户登记实际退款，原子追加本金负向退款、每个原赠品的负向回收及明确来源关联；不为赠品再生成现金。系统只记录已核对的实际银行结果，不执行银行转账。

本金原普通退款、通用赠品现金退款及单独积分调减会识别组合来源并拒绝绕过。集团中心保存一条受集团权限保护的最小钱包来源关联，用于其他门店同样识别组合赠品；不会因此开放另一家店的购买单、客户历史或附件。

已完成维修的售后仍走原售后批准方案，按原核销恢复同一个赠品钱包及本金；普通“撤销核销”不会绕过交车关口。售后返还不延长到期日，不自动产生组合现金退款。恢复后的余额重新参与原组合完整份额检查，并遵守该组合原退款期限。

## 岗位、凭据及异常出口

| 分支 | 经办及前置条件 | 原子事实与下一责任人 | 取消、冲突与期限 |
|---|---|---|---|
| 规则发布 | 集团管理员明确各项价格、赠品、门店、期限和条款 | 追加不可变规则及组成，默认禁用 | 再发布版本；不改已有购买 |
| 购买申请 | 本店获权员工、已确认本店客户与集团会员关系、已向客户说明条款 | 独立组合办理单，分派财务 | 申请人或店长可撤销未收款单 |
| 实际收款发行 | 当前接手财务，当前可发行规则、版本、原客户及本单收付款凭据 | 一笔现金及本金、全部原批次赠品、配对往来、事件与请求回执一起提交 | 任一组件失败全部回滚；同请求返回原结果，旧版本拒绝 |
| 退款申请 | 原收款门店、同会员、当前可退完整份额、明确整份条款 | 独立退款办理单，分派店长 | 申请阶段无资金占额，可退回或撤销 |
| 退款批准 | 不同于申请人的当前接手店长，本单客户申请或复核凭据 | 锁定集团会员和原钱包，检查后同时占额，分派财务 | 与消费、其他退款并发只允许守恒的一笔成功 |
| 实际退款 | 当前接手财务，已批准占额，原账户、真实新凭证号、本单收付款凭据 | 本金及各原赠品同时扣减，原款负向现金、原赠品回收关联、事件与回执一起提交 | 不接受临时金额或替换赠品；执行前仍核对期限与占额 |
| 撤销或退回 | 申请人／店长可撤销，店长可退回 | 已批准本金及全部赠品占额一起释放，关闭相应待办 | 已实际收款／退款不得覆盖，需原退款路径；终态重复办理拒绝 |

办理单默认预计两天内完成，进入“我的工作”，超期沿统一待办提醒；不自动付款、退款、释放资金或替员工完成事项。门店汇总为只读。服务顾问、财务和店长各自办理自己能证明的事实。

实际收退款必须上传并选择**本单**收付款凭据，生成文档不能代替实际凭据。附件必须通过当前配置的附件安全策略，隔离文件不可使用。演练选择 `structure_only` 并明确显示“未查毒”；生产扫描要求沿系统正式配置执行。

## 入口与接口

网页入口为“会员充值组合套餐”，也可从“会员卡与续会”的当前客户进入。员工选择本店客户后购买或查看原购买的完整份额；购买、退款窗口和办理详情均展示完整份额限制、当前可用数量、原账户与冻结期限。管理员以门店名称勾选，使用中文规则标签。

- `GET /api/recharge-bundles/rules`；`POST /rules` 追加规则。`values` 包括 `code/name/enabled/principal_cents_per_share/allowed_store_ids/sale_starts_on/sale_ends_on/refund_policy/refund_terms/components`；每个组成仅提交 `benefit_rule_id/units_per_share`。
- `GET /purchases?customer_id=…` 返回本店原购买与可退完整份额，不能查询其他店购买凭据。
- `POST /orders`：`request_id/customer_id/purpose/values/reason`。购买 `purpose=purchase`，值为 `rule_id/shares/terms_accepted=true`；退款为 `purpose=refund`，值为 `purchase_id/shares/terms_accepted=true`。
- `GET /orders`、`GET /orders/{case_id}` 获取有权查看的本店办理。
- `POST /orders/{case_id}/actions/{approve|execute|cancel|reject}`：提交 `request_id/version/case_version/member_version/values`。批准须 `evidence_id/reason`；执行固定须 `account_id/reference/evidence_id/reason`；取消、退回须理由。不允许自行覆盖金额、状态或组件。

`Case.kind=recharge_bundle`、`flow_version=2`。独立数据表包括冻结规则和组成、办理单、购买来源、赠品钱包来源、退款及退款各组件和实际回收关联。使用原 `GroupReceipt` 的请求幂等与同事务回执，以及原 `GroupEvent/FlowEvent` 审计；所有资金、权益事实沿原不可变账本追加。

## 报表与恢复

`recharge_bundle_service.analytics_rows` 提供授权门店内唯一现金来源、按种类独立单位的赠送／回收流水，以及当前批准退款占额。集团汇总只读，不依赖查看者拥有本店办理权，每类来源有 25,000 行拒绝截断的上限。

总图表已接以下同源数据集，明细与 CSV 使用同一统计集合：

- `recharge_bundle_cash`：按真实现金业务日统计的组合本金净收，沿唯一 `CashEntry`，不再加到现金总数第二次，也不称营业收入。
- `recharge_bundle_bonus/points/coupon/package`：组合赠送及原组合退款回收的净变化；赠金为分，其他各自整数，不能跨种类混加。实际消费核销仍在原权益统计中。
- `recharge_bundle_refund_holds`：当前批准退款本金占额，是集团会员总占额的组成，不能重复相加。

追加迁移为 `a127_recharge_bundle`，依赖 `z026_opening_import`。静态迁移建立八张表，不改历史迁移。原本金恢复校验加入批准组合退款占额，原权益恢复校验加入各原组件占额。`validate_recharge_bundles_sqlite` 核对冻结组成、各原单位、主体门店及凭据、独立审批、唯一真实收款、原账户退款、赠品来源、完整回收、有效期和不可绕过的原单关联。

## 本批验证和明确范围

`tests/test_recharge_bundles.py` 现有 14 个自动用例，覆盖正常、拒绝、取消、过期版本、原请求重放、跨店原历史拒绝、原账户、规则默认关闭／冻结、有效期、原赠品部分用后整份退款、第二组件失败全事务回滚、消费积分欠额、已交车售后恢复原批次，以及两连接同时审批／跨店本金或赠品使用。非空 SQLite 拷贝恢复验证包含仍批准的原本金和各原赠品占额；篡改原组件单位或批准证据会被拒绝。

相关旧本金、权益、会员生命周期和售后回归已组合运行通过；最终全库回归与 PostgreSQL 验收由总验收记录统一记录，不能用本域验证数量替代整体验收。

`tests/browser_recharge_bundles.py` 使用隔离新库、真实本地 HTTP Chrome、390×844 窄屏及三个员工账号，通过四个完整场景且无 JavaScript 错误：管理员配置、三份一次真实收款与四类赠品、乙店原维修核销一券、甲店独立批准／撤销释放／再原路退两份。截图已经检查，条款与当前完整份数可读。本地 HTTP 演练不替代正式 HTTPS 环境验收。

本批不包含把实际收款分摊到收费本金、收费券及收费服务包的混合售价模型；原有单独券包购买仍沿权益模块。已部分使用的一份不支持临时给已用赠品定价后扣款退款；若公司需要，须先冻结追回价、税务／对外结算及优惠承担冲回规则再另做流程。本金批次限店、临时促销叠加、阶梯赠送、人工替换赠品也不在此固定规则闭环内。正式模板和公司条款仍需业务验收，不能将软件默认条款视为公司已审批合同。
