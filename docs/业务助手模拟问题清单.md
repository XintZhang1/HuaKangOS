# 业务助手模拟问题清单

## 最新修复：接待找单、补电话与跟进 · 2026-09-24

用户反馈的三个问题已定位：助手未先检索本人工单；没有把当前意向阶段的follow映射为跟进；把错误资料类型customer造成的拒绝当成账号无权限。现在用find_cases先查询，get_case返回当前原生动作及电话修改入口，prepare_customer_contact生成原customers修改表单；错误单数类型返回参数错误并提示正确类型，不扩大管理员或员工权限。

真实DeepSeek关闭/开启思考各完成两轮合成对话：先自行找到单据、准备补电话，只问缺失的沟通结果；提供结果后准备原意向跟进并登记次日日期。合成员工确认后分别核验电话和日期，各2笔表单。普通7次、思考8次模型请求。既有越权、跨店、重复、旧版本及错误路由处理仍受相关回归约束。[本轮报告](verification/assistant-thinking-20260924/测试报告.md)。

仍需真实场景反馈：复杂多单目标可能继续需要选单；本次结果不能证明模型总能正确理解。没有具体时段字段时只登记日期和用户提供的文字，不承诺下午提醒。不得为了少问一句而虚构沟通事实。

记录日期：2026-09-23 至 2026-09-24。以下使用真实模型接口和 Windows Chrome；全部是独立临时库中的虚构资料，未操作正在试用的门店数据。

最新结论：当前 DeepSeek 已实际通过三项办理链路：接待资料追问后确认新建、补电话后确认安排回访、主管在390px窄屏确认新增车辆品牌。检查发现并修复了已有登录会话冷打开业务助手的启动顺序问题，冷打开、刷新和正常登录复测通过，该专项调用模型0次。以下保留此前失败及修复证据，不能把历史断点误读成最新状态。全量需求和其他业务尚未因此获得验收。

## 本轮实际覆盖

DeepSeek 读取可见表单的中文标签、当前值、校验状态和已有选项，然后选择填写、勾选、选择、点击。脚本拒绝任意代码、SQL、猜测控件、猜测选项和密码操作。模型没有得到 API 密钥、密码、Cookie 或真实客户资料。

两轮共调用 **34 次**，模型为 `deepseek-flash`，用量 **36,163 tokens**。第一轮保留了失败证据；第二轮只补充表单选择方式的说明，没有修改业务页面来迁就测试。

| 场景 | 操作账号 | 第一轮 | 恢复专项 |
|---|---|---|---|
| S01 空库尝试车辆报价 | 销售 | 出现添加车型、客户的补充指引 | 无需重复 |
| S02 新增品牌 | 主管 | 模型填写并保存，HTTP 201 | 作为明确说明的准备资料 |
| S03 新增车系并选择品牌 | 主管 | 模型反复改写已选品牌，未保存 | 模型重新操作通过，HTTP 201 |
| S04 新增纯电车型参数 | 主管 | 模型填写并保存，HTTP 201 | 作为明确说明的准备资料 |
| S05 明确车型所属车系 | 主管 | 因车系未建成而未执行 | 模型操作通过，HTTP 200 |
| S06 新建无电话的售前接待 | 销售 | 模型填写并保存，HTTP 201 | 作为明确说明的准备资料 |
| S07 分派接待给销售 | 主管 | 模型已选中员工后又重新搜索，未提交 | 模型操作通过，HTTP 200 |
| S08 补电话并安排接待回访 | 销售，390px窄屏 | 因分派未完成而未执行 | 模型补电话并提交，HTTP 200；客户电话和回访状态核对一致 |

每个“通过”还做了独立只读查询，核对实际记录，未把模型自述当成成功。两轮没有浏览器 JavaScript 异常，也没有业务请求的 HTTP 4xx/5xx。

登录、创建员工账号、首次改密和每个场景打开首个页面是测试准备，不计为 DeepSeek 操作。恢复专项在另一个全新临时库中，通过既有接口准备第一轮已经成功的品牌、车型和无电话接待；这三项准备不计入第二轮模型成绩。因此本记录是两个隔离试验的组合证据，**不是宣称同一新库已由模型连续完成全部业务链路**。

## 发现的问题和处理

| 编号 | 现象与证据 | 判断 | 当前处理 |
|---|---|---|---|
| DS-F01 | S03 第3轮已点击品牌结果，第4轮输入框有效，但模型又填写查询文字，清除了刚完成的选择 | 模型操作错误；未证明前端缺陷 | 提示模型“选中后输入有效、结果收起即可提交，不要重填”；恢复专项通过 |
| DS-F02 | S07 已点中销售员工后，模型误以为结果消失等于未选择；最后还声称误点了取消，实际操作记录没有该点击 | 模型状态理解及说明不准确 | 以实际控件和请求为准；相同提示修正后通过。不得把模型总结直接登记成已确认缺陷 |
| DS-F03 | 新车型要分别建立品牌、车系、车型，然后再确认车系归属 | 操作步骤偏多，属于体验改进建议 | 业务助手应分步引导并保留已填资料。没有证据支持删除原有归属核对规则 |
| DS-F04 | 第一轮搜索输入与结果按钮在同一轮被重复改写，旧结果已消失 | 模型使用了过期控件；执行器成功拒绝 | 保留“每轮控件仅本轮有效、点击后重新观察”校验；记录为模型输入问题 |

没有把上述失败直接归类为“前端坏了”。后续自动问题列表也应区分：缺必要资料、业务规则拒绝、模型填错、界面/服务异常，以及仍待人工判断。

## 新问答模块的真实多轮试验

另运行了新业务助手的真实 HTTP 和 DeepSeek 接口，未模拟模型回复。两轮合计 **25次调用、82,450 tokens**，同样使用 `deepseek-flash`，在另建的两个临时库进行。服务器只加测试审计，记录实际响应的模型名、调用数和用量；不记录请求头、提示词、密钥或模型原始响应。

- 首轮：2条员工消息、9次调用。助手先问姓名和来源，补齐后又要求确认另建客户，没有生成办理卡，也没有创建业务。错误地将 `customer-choice` 领域名称作为操作编号，系统拒绝并自动记入问题列表。
- 第二轮：5条员工消息、16次调用。缺资料时追问；补充新客户姓名和来源后生成办理卡；测试脚本模拟员工明确确认，原生业务入口创建了唯一接待；重复确认返回原结果，没有重复创建。
- 主管用原生接口分派接待后，助手正确追问回访所需的电话、下次日期、沟通结果。员工补充后，测试达到累计25次的调用上限，审计保护停止进一步远程请求。出现的“连接异常”来自本次测试额度保护，不是已经证实的 DeepSeek 服务故障。**通过新问答模块确认回访的最后一步尚未验收。**

| 编号 | 问题 | 判断与处理 |
|---|---|---|
| DS-A01 | 模型把领域名或替换过的路径当操作编号，还曾向目录传入不支持的查询参数 | 模型参数错误。系统拒绝，问题列表可查。已补充领域与操作编号区别；需继续改善专业操作说明和模板参数使用 |
| DS-A02 | 无电话时，原页面临时把回访电话设为必填，但原 API 动作字段仍说选填 | 真实动作说明缺口，已将条件补进后端动作字段，不修改历史规则。第二轮助手已明确追问电话，根任务另有字段专项测试 |
| DS-A03 | 模型曾把接待字段放在请求顶层，而不是 `values` 中 | 模型字段结构错误，系统拒绝并记录；之后形成的接待卡已通过原生确认。应继续减少重复探索和错误重试 |
| DS-A04 | 多轮办理重复查询接口定义，回访补齐前耗尽本次有限测试预算 | 操作效率问题；本轮保留断点，不把未执行的回访确认算成功。可继续优化常见业务的专用操作说明与上下文 |

- `%LOCALAPPDATA%\huakangos\verification\deepseek-conversation-trial-20260923-b`

## MiMo 切换后的首次试验（2026-09-24）

保留前述 DeepSeek 历史，新增独立 MiMo 证据目录：`%LOCALAPPDATA%\huakangos\verification\mimo-conversation-trial-20260924-a`。

使用已验证的 MiMo Token Plan 官方接口和 `mimo-v2.6-flash`，实际4次调用、14,549 tokens，3条员工消息。**本轮未通过，也未创建业务。** 首次工具查询之后，模型多次返回超出允许数量或格式不正确的工具调用，系统拒绝并记录“业务助手返回的操作过多”。后3次模型响应均达到2500 completion tokens。

旧审计只保留模型、用量、状态，没有保留工具调用本体，因此不能事后给出精确函数名和数量。后续脚本已增加工具调用数量、函数名、结束原因的只读审计，不保存参数、请求头或原始提示词。待修复专门的业务引导后，再使用新证据目录重跑，不能以供应商接口探测200代替业务成功。

此轮原始 `checks` 中“缺少姓名和来源时保留问答，未创建接待”只检验了没有写入；实际收到的是错误提示，并没有完成追问，**该项不能算通过**。测试脚本已经收紧为必须确实询问姓名和来源，避免把错误提示当成多轮问答成功。原始证据仍原样保留。

## 恢复 DeepSeek 后的复测（2026-09-24）

按用户最新选择切回 DeepSeek，使用另一份私有配置和新临时库。证据：`%LOCALAPPDATA%\huakangos\verification\deepseek-conversation-trial-20260924-c`。

本轮17次调用、45,089 tokens、5条员工消息，没有达到40次的测试上限。接待确认和重复确认仍然通过；电话字段已经从真实原单读取到 `required=true`。**回访确认仍未通过。** 模型把详情操作模板错误写成 `GET /api/flow/cases/{id}`，被系统拒绝；随后反复断言系统没有回访入口，没有改用真实的 `{case_id}` 模板查询。

新增问题：

- **DS-A05，工具说明及错误恢复需要改进**：不能让员工依赖模型正确拼接口模板。应对常用业务提供专用查询/办理工具，或在操作编号不匹配时给出精确候选；不得为了通过测试而放开未知接口或自动执行业务。
- **DS-A06，新客户必填条件说明不完整**：助手把姓名解释成“可留空”，但原生规则是“已有客户编号”与“新客户姓名”二选一。此前成功试验提供了姓名，因此不能据此认为这句解释正确。需明确有条件必填信息。

本轮所记录的问题均保留在原始对话和自动问题列表中；该结果不宣称业务助手已经完成接待到回访的整条问答链路。

## 专用办理工具修复后的真实链路（2026-09-24）

证据：`%LOCALAPPDATA%\huakangos\verification\deepseek-conversation-trial-20260924-d`。DeepSeek 实际 **16次调用、52,114 tokens、4条员工消息**。使用新临时库；没有模拟模型回复，没有直接改业务数据。

本轮依次通过：

1. 只说登记接待时，助手追问新客户姓名和来源，没有提前创建业务。
2. 补姓名、来源及关注车型，电话留空。助手生成接待待确认卡；脚本模拟员工明确确认后，原生业务入口创建唯一接待；重复确认仍只有一条。
3. 主管通过原生接口分派给销售。这是明确的测试准备，不计为 DeepSeek 办理成绩。
4. 销售要求安排回访，助手追问电话、日期、沟通结果；补充后生成回访待确认卡。明确确认后核对原单电话、日期和回访状态，重复确认没有新增第二条业务。

系统新增原单查询和办理动作专用工具，模型不再需要拼接回访路径或推算业务版本；系统仍按原生岗位、当前状态、必填字段和版本检查。DS-A02、DS-A05、DS-A06 在上述场景的修复后验证通过。执行中仍有一次模型使用不存在的 `POST /api/flow/lead`，系统拒绝并记录，随后模型恢复成功；不能将一次成功理解成模型以后不会填错。

该次证据的 `business_success=true` 表示上述业务链路通过。紧接着尝试复用登录会话冷打开 Chrome 时，发现前端启动顺序问题，因此原始顶层 `success=false` 和 `browser_contract.success=false` 保留原样。后续定位及复测见下节，未篡改失败记录或重新标记该次浏览器成绩。

## 真实手机页面确认和冷启动复测（2026-09-24）

证据：`%LOCALAPPDATA%\huakangos\verification\deepseek-brand-browser-20260924-a`。主管用1条明确消息说明品牌名称、编码、启用状态；DeepSeek 实际 **8次调用、26,752 tokens**，生成真实待确认卡。Windows Chrome 的390px页面使用本次合成主管账号正常登录，读同一真实对话并点击“确认办理”。确认请求HTTP200，卡片显示“已办理”，原生品牌列表仅有一条对应记录，未在确认前创建。保留 `brand-pending-390.png` 和 `brand-complete-390.png`，已查看截图；未发现文字溢出或按钮无法点击，浏览器无 JavaScript 异常。

该轮一次主资料查询使用错误类型，收到404并自动记录后恢复。自动列表将该项粗分为 `rule`，人工根据错误类型参数判断属于模型输入错误。**DS-A08：问题自动分类仍需人工复核**，不能仅凭HTTP状态把模型参数错误认定为业务规则拒绝。简单新增品牌仍消耗8次调用，后续可继续减少无效探索；本轮保留实际用量。

## 试验汇总与使用边界

当前有完整证据的三类结果分别是：模型操作原有表单的8个合成场景组合、业务助手接待到回访的真实多轮链路、业务助手新增品牌的真实手机页面确认。接待链路的确认由测试脚本模拟员工确认，品牌的确认由真实前端按钮完成；两者不要混为同一个端到端浏览器试验。

所有试验均使用隔离测试库存储、独立随机端口和临时账号，登录密码及会话仅保留在运行内存。试验结束关闭本次服务并清理临时业务库，保存的只有源码外脱敏证据。历史 MiMo 试验失败证据保留，按用户后续选择已切回 DeepSeek，没有继续 MiMo 调用。

## 尚未验证

本轮没有覆盖操作手册所有章节、193项全部功能、资金实收付、库存、会员核销、文件上传、手机相机和生产 HTTPS。模型理解同一页面也可能在下次运行时变化；本记录是一次有限的真实试验，不是无人值守办理任意业务的证明。
