# 维修明细工单 v3

本交付覆盖一条完整维修纵向流程：固定主档项目／配件报价、主管价格授权、客户逐版授权、实际开工及领退料、质检返工、多方承担和后续到账。员工入口为“维修明细工单”。它创建 `Case.kind=repair / flow_version=3`；原通用开单仍创建 v2，v1／v2 单据保留原处理规则，不自动升级或借用本接口改状态。

## 业务动作与交接

| 动作与进入条件 | 本人确认的事实／依据 | 同一事务的效果与下一责任人 | 文件、超时与取消出口 |
|---|---|---|---|
| 服务顾问开单 | 本店客户档案、车牌、报修问题、预计交接日 | 建立本店工单、报价待办；没有现金、库存或客户欠款 | 不从电话自动合并客户。实际开工前可取消，历史报价保留 |
| 报价／增项 | 本店启用作业项目、物资目录，逐行数量、单价、本次优惠及原因 | 冻结不可变完整报价版本和项目名称、编码、单位、标准费用；产生主管价格审批任务 | 已有待授权版本必须先明确撤销，不可覆盖。取消待授权增项恢复上次已授权版本 |
| 主管价格授权 | 当前报价；明确本次最低可接受金额、是否批准低价例外及原因 | 追加该报价价格审批记录，交服务顾问取得客户授权 | 不从标准费用、库存成本或某个固定折扣猜公司的价格授权线；低于本次最低值且未明确批准例外时拒绝 |
| 服务顾问记录客户授权 | 主管已批准；本单当前报价版本的实际客户授权文件 | 冻结“报价 ID＋报价内容摘要＋授权文件”关系；授权金额成为当前约定金额；交技师 | 必须重新上传新版本授权凭据；同一旧授权文件不能绑定另一报价。上传不等于验证签名真实性，顾问须核对文件内容 |
| 技师实际开工 | 当前版本已授权，接手施工待办 | 记录本人实际开工，配件发料交库管；不自动发料 | 重复开工拒绝。已有施工后不能删除式取消，需明确停工保留费 |
| 库管发料 | 工单已开工、当前报价已授权、接手发料任务；实际配件及交接证据 | 按当前授权配件行限额追加 `StockMove` 和原领料关联；扣本店数量及精确库存价值 | 未授权增项、超量、缺货、待质检、停工均拒绝。完成其他前置动作不代表物资已经发出 |
| 库管原领料退回 | 结算冻结前；选择本单实际原领料及实际退回数量、证据 | 按原发料剩余价值分摊，追加正向库存和负向消耗事实，不改原流水 | 重复退回和超过原可退量拒绝；退回后原配件未领齐则阻断施工完成／质检。已质检后退料使工单重新质检 |
| 技师提交施工 | 已开工、当前版本已授权，正常维修的配件净领用已齐 | 记录实际完成情况，交服务顾问质检 | 未领齐时核对领退料或协商停工保留费，不能直接交车 |
| 服务顾问质检 | 技师已提交；本单实际质检凭据、明确合格／不合格及结论 | 追加当前报价质检记录。不合格回技师处理；合格交主管确认承担 | 不合格阻断结算及交车。处理后须重新提交并复检，不覆盖历史失败记录 |
| 主管冻结承担 | 当前版本质检合格；客户／保险／厂家／内部承担及确认凭据、人工成本 | 各承担总和必须等于当前授权金额；冻结一次。各外部承担分派财务任务，客户交接交服务顾问 | 保险用本店启用的保险公司主档；厂家用本店“厂家”类别往来档案；内部主体明确填写。未确认承担前不能收款或消费会员权益 |
| 财务实际到账 | 已冻结承担，接手该承担方待办，实际账户、金额、流水号、凭据 | 唯一现金 `CashEntry`＋唯一 `PaymentLink`；`RepairPayment` 只关联承担方和原现金，不增加第二份现金 | 可分笔、可在客户接车后记录保险／厂家到账；不得挪用其他承担方的未结金额，客户已占权益额也不能再收现金 |
| 服务顾问确认接车 | 质检、承担已确认，客户实际承担结清，全部权益占额已核销或释放；接车凭据 | 记录实际接车日；保险／厂家有余额时转“已交车待月结”，财务待办继续；全部外部结清才完成 | 不提前以已付款代替实物交接；接车后本版不允许再领退料、改报价或修改承担 |

待办默认当天到期，实际交接日期保存在原工单；财务任务按**各承担方**明确的到期日判断。系统展示逾期，由主管核对与人工转交，不自动施工、收款、交车或变更价格。已有开放待办保持人工转交的员工；刷新金额不会偷偷改派。

## 版本、优惠和已施工停工

金额为整数分，数量为整数千分位，API 拒绝浮点金额、额外状态字段和超限数量。单行原价按数量乘单价四舍五入到分，优惠按新增金额权重采用最大余数分配，尾差按稳定行序分配，明细合计始终等于版本合计。

开工前可重新形成替换报价，仍需完整审批、客户授权。开工后的普通增项必须携带全部原授权行，保留来源、单位、价格及已有数量；可以增加数量或增加新项目。既有行已授权净金额不重新分摊，本次优惠只分摊到新增部分。待新版本授权期间暂停施工完成及发料，原库存流水保留。停用项目／物资可以保留已授权历史，但不能新增数量。

已施工取消采用 `purpose=stop` 的独立报价版本：保留原项目配件清单，明确已完成事项、退料安排及双方约定的保留费用，金额不能超过原授权金额。主管确认价格，客户用新文件授权；随后禁止新增发料，库管退回未用料，技师记录已完成工作，服务顾问做停工后的安全交接检查，再按约定保留费结算。保留费不是系统猜测的折旧或违约金，协商结果由经办岗位确认。

该停工路径仅限**承担冻结、实际收款之前**；本次没有做已结算工单修改、已交车收费退款或原施工费用争议处理。已施工项目逐个完成打卡、排班排程及工时绩效也不在此版本，不生成员工排名。

## 原领料价值与费用

发料按现有 `Item` 的当时库存平均价值分摊；最后全部发出时带走全部剩余分值。每笔 `RepairStock` 关联其唯一 `StockMove`。退料依据对应原领料剩余数量及价值比例分摊，最后退回余量归还全部余值，不能拿后来进货的新价格重估旧领料。

例如库存 2.500 件、价值 3.08 元，发 2.000 件扣 2.46 元；该原领料退 0.500 件返还 0.62 元。重新发出的配件形成新原领料，不能重复使用第一次退回额度。领退料和工单版本同事务，竞争动作只有一笔生效。

冻结结算时，主管确认实际人工成本；工单直接成本为人工成本加该工单配件净消耗价值。标准作业收费不是人工成本。当前不分配门店房租、工资总额等间接费用，不宣称提供完整会计成本核算。

## 多方应收、集团权益和收入

`RepairAllocation` 中客户、保险、厂家、内部最多各一行；正数金额合计必须等于当前授权应收，零元工单可没有承担行。分配一经确认不可覆盖；无客户承担时仍可在质检及分配确认后接车。

每个外部承担分别保存到期日及实际到账链接。客户欠款 = 客户承担 − 客户实际现金 − 集团本金已核销 − 其他集团权益已核销；新增现金／权益占额还要扣除所有有效占额。保险、厂家现金不能抵客户欠款，集团权益不能抵保险、厂家或内部金额。内部承担是费用归属确认，不产生现金，也不计对外维修收入。

集团模块统一调用：

- `is_detailed(row)`：识别 `repair/v3`。
- `customer_due(db,row,include_reservations=True)`：唯一客户可占用金额，已同时扣本金、赠送、积分、券和套餐的已核销／占额；`False` 仅扣已核销，用于完成已有占额的校验。
- `sync_after_member(db,user,row)`：核销、撤销后更新财务待办及完成状态，不确认接车。
- `eligible_benefit_units` 与 `eligible_benefit_credit`：当前已授权、已质检并冻结结算的正常维修，按作业编码和“次”单位限定套餐次数及实际作业金额。停工版本不开放套餐核销；集团模块另扣该编码已核销和有效占额。
- `receivable_rows`：逐外部承担返回金额、已收、尚欠和真实到期日。`receivable_amount` 汇总其尚欠；`revenue_amount` 排除内部承担，经营报表再按集团权益实际收入规则扣除由履约方承担的权益优惠。

开票额度、经营报表和应收下钻由统一报表／财务入口使用上述真实外部承担，不能直接把 `Case.amount_cents` 的内部部分算作销售收入。期间维修交付按实际接车日；后续保险到账按实际现金日期。二者不混成同一时点。

## 文件、权限及上线边界

每个文件引用都复用 `file_exists → file_security.require_usable` 并验证当前岗位、门店和原单；隔离、检查失败以及当前策略不认可的文件不能推进动作。技师和库管读取数量、授权状态及自己的业务凭据，API 不返回报价金额、库存成本、承担金额或金融凭据。服务顾问可读客户价格，成本仅管理／财务／审计可见。多店汇总只读。

本次客户授权以实际上传文件与不可变报价摘要绑定，未增加新的合同／报价 DOCX 模板，不将系统通用业务记录当作公司已经批准的正式维修合同；也不自动识别客户签名。正式模板、保险／厂家接口、返修新工单关联、已交车退费和精细排程仍需后续建设。

迁移 `k511_repair` 接在 `j410_transfer` 之后，冻结新增十张表，不修改历史维修语义。后端入口 `/api/repair-orders`；员工页面 `web/repair.js`。测试使用独立临时库，不接触公司真实业务。

`tests/test_repair_orders.py` 覆盖版本分派、普通／停工报价、优惠守恒、价格拒绝与明确例外、旧授权重用拒绝、增项前发料阻断、原领料退回、失败质检复检、多方金额与后到账、十三动作跨店、岗位、隔离凭据、不可变事实和真实竞争发料／退料／收款。`tests/browser_repair.py` 用服务顾问、店长、技师、库管、财务五个员工账号，在真实 HTTP Chrome、390 像素页面上走完整链路和中文错误提示；测试环境显式 `structure_only`，不据此宣称生产病毒扫描已经通过。

自动测试和浏览器演练是实现证据，不代表公司已经完成业务验收或正式启用。
