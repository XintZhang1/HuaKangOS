# 保险核价与结算

本轮提供独立 `insurance / flow_version=3`，对应原需求 HK-014「保险核价」及 HK-141「保险收入结算」的实际业务链。旧保险版本的在办记录继续按原版本办理。这里的自动验证不代表公司业务验收或正式启用。

## 业务入口与来源

员工从“保险核价与结算”选择本店客户及实际 VIN，可以明确关联本店整车销售、原保单、原续保任务。客户车辆与销售车辆同时填写时必须属于同一客户、同一 VIN。销售人员只能查看自己的客户/业务或已明确接手的待办，其他门店业务和原件不通过此页面共享；集团汇总只能查询统计。

新销售 `order / v4` 的当前报价明确包含保险、已经配车且取得客户本版签回时，同一事务创建一张待核价保险单。该操作只分派责任，不填写保险公司、不推断保费、不生成收付款。旧 `order / v2、v3` 的语义保留，可以明确关联新独立保险单。自动创建入口通过 `create_for_sales_quote` 验证销售当前版本、客户签回及激活记录。

明确关联续保原单时，原保单必须属于本客户、本 VIN；新期限必须晚于原保单截止日。新出保结果追加车辆保险期限记录，保留原期限和凭据。续保任务仍由经办人按实际跟进结果结案，不因建单或上传文件自动完成。续保关联保存在独立不可变 `InsuranceRenewalLink`，不会改写原保单。

## 核价、确认与实际出保

销售或服务顾问逐项填写险种保费、保险公司、保险期间、报价确认期限、约定和预计佣金。金额以整数分保存，同名险种不得重复，单版最多 40 项。门店代缴时必须在核价前确认保险公司收款户名及账户/缴费识别号；这些内容随报价冻结。

另一位店长核价，申请人即使是管理员也不能自批。客户授权记录绑定该版完整摘要，包含险种明细、实际 VIN、保险公司及缴费户、期间和条款，不仅绑定总金额。超过确认期限、旧报价、过期业务版本、错误凭据均不能通过当前版授权。

没有实际资金、预收占额或外部提交时，可以撤回、拒绝后重报或建立新报价；已有实际事实后必须走原保险终止及原款处理，不能覆盖历史报价。普通取消只适用于没有实际资金或外部提交的申请。

经办人先记录实际投保/补件提交，再记录保险公司真实结果：“已出保”“拒绝投保”或“要求补件”。要求补件或拒绝后，原提交和结果均保留，可以再次实际提交。尚未收到结果的提交不能被普通取消或被推定为投保失败。保单号按本店及保险公司防重复。文件上传和人工登记不代表已调用保险公司接口。

## 保费与佣金的三个独立口径

| 口径 | 有效事实 | 资金、收入影响 |
|---|---|---|
| 门店代收代缴保费 | 财务确认客户原款实际到账；按该原款实际支付保险公司 | 每次真实收/付各产生一个 CashEntry；客户款 PaymentLink 只作分配，不再计一遍现金。保费不作为门店保险收入。 |
| 客户直付保险公司 | 财务核对客户向保险公司直接付款或原款直接退回凭据 | 只记录双方实际凭据和金额，不产生门店 CashEntry、PaymentLink 或预收抵用。 |
| 保险公司佣金 | 财务按实际结算依据提出本保单累计应得佣金，另一店长确认，再分别记录实际到账/原超收退回 | 预计佣金不产生收入或应收；批准目标与此前批准目标之差形成实际佣金变动。实际到账只记一次现金，可以晚于出保。 |

代收原款允许分笔收取和分笔代缴，代缴不得超过该客户原款未付金额及本单应付保险费。账户必须追原客户款账户；不能拿另一单客户的资金凑付。银行流水在同一资金账户全系统防重复，操作同时触碰 Case 和 Account 版本，竞争失败整笔回滚。

保险保费还可以使用独立财务模块的本店预收抵用或客户月结集中收款。集中收款的一笔现金可分配到多张保险单；各 InsuranceTender 明确绑定原 PaymentLink。预收抵用绑定原 FinanceCreditLink，不再次生成现金。只有明确分配到本单的财务宿主原件可以被窄范围引用，任意同店或跨店文件不能冒充本单资金证据。

原收款更正继续使用独立财务模块。保险已代缴原款时必须先真实追回，才能更正该原款完整剩余金额；撤保中或已撤保的保险不通过通用更正绕过原款结清。

## 撤保、原退与佣金追回

经办人先取得保险公司真实终止/未出保结果，填写其实际保留保费及每笔原客户款的退款分配。保留保费不能增加已生效客户保费，也不能用预计佣金抵扣。方案独立版本化：另一店长复核，客户同意本版摘要，财务凭实际原件使方案生效。批准时原退款额度占用；未生效方案拒绝或撤回后释放，不删除申请和审批记录。

方案生效不会自动造现金，也不会自动把原款视为已退：

1. 原款仍在保险公司时，先按原代缴记录确认保险公司实际退回。未追回部分不能先退客户。
2. 客户退款追到原正向 InsuranceTender。原现金从原账户退回，原预收抵用只回到原预收余额。可以分次实际退，累计不能超过方案分配和原款可退金额。
3. 客户直付模式只登记保险公司对客户的原路直退，不制造门店收退款。
4. 撤保后须重新按实际结算凭据独立确认累计佣金，金额可以为零。若低于实际已收，财务沿原佣金收款和原账户登记实际退回；若仍有应收则继续保留财务待办。

需要再次减少保留保费时可建立后续撤保版本，逐笔额度包含此前批准未退及已经实退的部分，不重复释放原款。当前路径处理保单整体终止以及原实际保费的分次结清；保单仍有效时任意增减险种、批改承保标的或追加保费应另建设明确批改流程，不能伪装成这里的撤保。

## 分工、交车与销售售后

| 阶段 | 经办岗位与下一责任人 | 拒绝、超时与撤销 |
|---|---|---|
| 建单、报价 | 销售/服务 → 另一店长核价 → 原经办人登记客户授权 | 核价拒绝后重报；确认期限到期拒绝旧版授权；无实际事实可撤回/取消。 |
| 投保、补件、出保 | 销售/服务按实际保险公司结果办理 | 原提交保留，补件重新留凭据；没有结果时不推断失败。 |
| 代收、代缴、直付核对 | 财务分别确认真实资金或直付凭据 | 非财务拒绝；超额、原款不符、重复流水或版本竞争拒绝；真实原退追加记录。 |
| 撤保 | 经办人 → 另一店长 → 客户本版同意 → 财务生效及原退 | 未生效可撤回，拒绝不生效；已生效必须沿后续真实原退结清。 |
| 实际佣金 | 财务提出 → 另一店长确认 → 财务实际收退 | 预计值不记账，独立复核可拒绝；变动保留各版目标及实际原件。 |

任务有明确期限和当前接手人，继续显示在“我的工作”；超时不会自动产生办理结果或现金。任务转交沿系统现有授权交接入口。当前待办与历史已办记录分开显示，原件和已办交接可展开查阅。

只有明确约定交车前完成的关联保险阻断销售交车。真实出保/终止及客户保费、保险公司保费必须结清，待生效撤保和预收占额也会阻断；后续佣金结算不额外阻断交车。未约定该条件的独立保险按自身进度办理。

销售售后不能顺便退保险公司保费。关联保险须独立终止，并完成客户原款、保险公司款及实际佣金结清，才能作为“独立已结清保险”从销售售后中排除。恢复检查以售后申请时点验证完整保险清单、当时取消事件、已生效方案和当时资金事实；后来才取消或收到退款，不能反向证明早先已结清。

## 文件、统计与恢复

核价、客户同意、实际投保、保险结果和撤保方案引用本保险单“客户授权”原件；实际资金、佣金确认及撤保生效引用“收款凭据”。生成文件不能充当实际凭据，同一原件不能冒作不同办理事实。隔离或未完成扫描的文件不可用，重扫及私有存储继续遵守统一附件策略。

父级整合的统计提供实际出保信息、期间已确认佣金变动、实际佣金收退和当前客户本金/佣金应收。佣金变动按独立确认的业务日，现金按实际收付业务日；分店明细、图表和 CSV 使用同一数据。期间保费是出保信息指标，不能加入门店保险收入。月结定义第 7 版冻结保险来源，旧定义及旧封存清单保留原范围。

`validate_insurance_sqlite` 独立离线核对客户/VIN/门店、报价摘要及险种合计、独立审批、客户摘要、保单期限记录、原现金与预收路径、原代缴/客户退款守恒、佣金批准及实际现金。它重放直付和佣金收退时的批准额度，现金与保险行同时改成超额仍会拒绝。`validate_insurance_credit_return` 与 `validate_parent_aftercare_exclusions` 为总恢复及销售售后提供窄来源证明；不修改恢复库。

代码位置：`app/insurance_models.py`、`insurance_service.py`、`insurance_finance.py`、`insurance_api.py`、`insurance_backup_integrity.py`、`insurance_specs.py`；页面 `web/insuranceorders.js`。追加迁移 `i935_insurance_orders` 依赖 `h834_procurement_cost`，静态冻结 21 张表，不引入模型元数据运行迁移，不改旧保险历史。
