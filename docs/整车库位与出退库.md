# 整车库位、其他出库与原车实退

本模块对应原需求 HK-025「整车其他出库」、HK-030「整车店内移库」，并为销售售后提供受控的实车隔离、检查及重新入库能力。它与整车采购、跨店调拨和销售共同使用 VIN 保管事实，不改变原库存记录所属门店。功能存在、自动验证、业务验收及正式启用是四种不同状态；本次交付为合成环境自动验证与员工浏览器演练。

## 员工入口

选择一家门店后打开「整车库位与出退库」。库管或主管建立作业，主管复核，库管对照实车重新输入 VIN 并选择本单实际凭据。其他出库用于实车退出可售库存的内部转用、报废或其他经批准处置；临时借车、试驾车辆不从该入口办理。

首次使用旧库存时，旧 `Vehicle.location` 文本不会自动匹配仓库或库位。没有结构化定位的车辆须建立「现场库位登记」，经主管复核后由库管实际核对车与位置。新采购或跨店验收在真实收车时直接记录所选结构化库位。

库位必须属于本店启用的整车仓或混合仓。存在车辆、隔离车辆或未完成作业时不能停用；有不可变定位历史的库位不能更换所属仓库，有历史的车辆仓不能改成物资仓。历史资料可查询，名称修改不重写交接原单和证据。

## 办理分支与责任

| 分支 | 入口与必要事实 | 实际影响及下一责任 | 异常出口 |
|---|---|---|---|
| 现场定位 | 本店已确认、未被销售或调拨占用车辆；明确库位及原因 | 主管批准后，库管用实车 VIN 和实际凭据追加定位；不增加门店库存 | 实际定位前原申请人或主管可取消；申请可被主管拒绝 |
| 店内移库 | 已有明确来源位、不同目的位；申请时占用 VIN | 主管批准；库管发出减来源位置数量，进入本单在途；目的位实际接收后加目标位置数量 | 发出前可取消；发出后目的位可拒收，再由库管实际接回原位；不能把已发出作业直接取消 |
| 其他出库 | 未占用且位于明确库位；原因及实际接收方/处置去向 | 主管批准后，库管实车发出；原代次退出可售库存，保管当前指针清空，追加一台负数量及负原成本 | 实际出库前可取消；实际出库后通过原单退回，不直接恢复旧行 |
| 原其他出库退回 | 本店已完成原出库；当前 VIN 无库存、发运、销售、调拨或其他作业占用 | 主管批准；库管核对原 VIN、实际凭据和本店库位；新建递增代次，追加一台及正原成本，关联原出库事实 | 批准前后但未实收可取消；一笔原出库只能实际退回一次 |
| 客户退车隔离 | 原销售售后方案当前批准及客户同意；原销售实际出库事件、原 VIN 占用来源 | 后台只建立库存域子单与 VIN 占用，不证明已收车。库管另传本子单实际凭据并接收到隔离位 | 未实收时由售后撤回计划；实收后不能取消抹除交接 |
| 退车检查与处置 | 隔离收车后，服务顾问或经主管转交的本店技师记录本次检查 | 主管引用最近一次检查，选择合格放行、整改复检或拒收。合格后库管实际转入明确库位才新建可售代次 | 不合格不能放行；整改必须新增复检。拒收后库管实际交还客户，保持无新库存；原售后据此结束 |
| 未发车销售终止 | 售后批准、客户同意及财务纠正实际生效，原销售没有发车 | 在同一事务中追加释放凭证，仅释放未交付原单占用；不修改车辆库存 | 已发车或已交付不能使用该快捷释放；必须走实际退车链 |

审批、检查和实际动作均要求当前待办负责人。主管可在专页转交待办并明确期限；接手员工必须有本店对应岗位。逾期仍显示在当前待办，不自动替员工确认出库、检查、接收或退款。申请与批准、检查与放行由不同员工承担；管理员同样不能批准自己提出的作业，也不能对自己执行的检查作放行判定。

## 库存与财务边界

- `VehiclePosition` 保存每一库存代次当前明确库位或在途/出库状态，`VehiclePositionEntry` 是不可覆盖的位置事实。移库来源负一台、目标或退回原位正一台，门店库存及总价值不变。
- `VehicleOperationClaim.active_vin` 的全局唯一约束与版本化 `VehicleCustody` 共同阻断并发销售、采购、调拨和作业。跨店检查只返回统一冲突提示，不暴露对方车辆、客户或成本。
- `VehiclePositionEntry.inventory_delta` 仅在本模块其他出库为 `-1`、其他退回或客户合格退回为 `+1`。采购/调拨/销售的定位钩子为 `0`，其经济库存事实仍来自原领域，统计不能重复累加。
- 门店内移库不产生收入或往来。其他出库不推断处置收入或收款；客户退车的费用、原路退款、应收调整、积分/权益纠正由原销售售后域处理。车辆子单不会自动退款。
- 已提车原 `Vehicle`、原库存代次、成本、门店及已交付 `VehicleHold` 均保留。实际退回合格时建立本店新代次。已发车但未提车的原单在实际合格退回时追加释放凭证并退休旧代次，仅删除尚未交付占用；原销售状态与出库历史保留，由售后原单守卫阻断继续执行。
- 金额全部为整数分，一车一台；原出退成本精确反向。移库不以最新采购价重算原车成本。

## 权限与接口

`Case.kind=vehicle_operations`、`flow_version=2`；原流程版本不被转换。通用 Case data 只记录作业标识、类型和进度，金额不放入通用嵌套 JSON。专页成本及价值字段只给管理员、主管、财务、审计。库管、服务顾问、技师不返回成本；服务顾问和技师只能读取客户退车子单。集团汇总权限不开放门店车辆作业详情和附件。

主要接口：

| 接口 | 用途 |
|---|---|
| `GET /api/vehicle-operations/catalog` | 当前单店岗位能力 |
| `GET /api/vehicle-operations/orders` | 本店可见作业分页 |
| `POST /api/vehicle-operations/orders` | 明确类型创建申请，携带 request_id |
| `GET /api/vehicle-operations/orders/{case_id}` | 本店按岗位返回事实与可办理动作 |
| `POST /api/vehicle-operations/orders/{case_id}/actions/{action}` | request_id + Case.version + 严格动作字段；库存、事件、待办、凭据关联与幂等回执一次提交 |

`prepare_customer_return`、`get_customer_return_proof`、`cancel_customer_return_plan`、`release_undispatched_order_hold` 为售后域调用的私有同事务接口，不单独提供任意状态或占用编辑入口。prepare 输入是客户授权凭据，实际 intake 必须使用车辆子单另一份实际接收凭据。所有本单文件沿用隔离、扫描、岗位访问控制；结构校验通过不等同杀毒检测或签名验证。

## 恢复与验证

冻结迁移 `v622_vehicle_operations` 依赖 `u521_invoice`，不从可变 ORM 模型创建历史迁移。`vehicle_operations_backup_integrity.validate_vehicle_operations` 核对位置账、当前位置、门店/库位/证据关系、审批、检查、VIN 占用、新代次及原成本；`vehicle_backup_integrity` 只有在完整核对末代实际其他出库来源后，才允许无当前库存且无跨店在途的保管记录。不能通过“缺少当前车辆就跳过”恢复异常数据。

专项自动测试见 `tests/test_vehicle_operations.py`：移库接收及拒收原退、现场 VIN 拒绝、批准后取消、原车出退与新代次、销售和供应商退回竞争、跨店及岗位拒绝、重复请求、过期版本、并发实际确认、旧文本定位、当前库位主档保护、已交付与未交付退回、不合格整改复检、拒收后实际交还、待办转交、不可变事实及合成非空恢复篡改拒绝。采购与跨店既有专项一起回归。

`tests/browser_vehicle_operations.py` 使用实际 Chrome HTTP、Cookies、CSP，在独立临时数据库和随机员工账号下演练 390px 的库管/主管/服务顾问/财务页面，不继承公司数据库，关闭 AI、调度并显式使用结构扫描演练模式。包括错误 VIN 中文拒绝、移库拒收原退、其他出退原成本权限、客户不合格整改复检后新代次入库、跨店拒绝及刷新回原页面。截图、结果、账号密码及数据库均不进仓库；程序 finally 关闭测试浏览器及本次服务进程。

## 本版限制

每张作业单只办理一台车；店内移库不跨门店。没有临时借用/试驾车账、VIN 扫码硬件、库位容量或停车预约、二手车评估、减值会计、自动处置收款和对外物流/税务/厂家接口。客户退车入库沿原库存成本，额外整改成本及经营财务处理不在本子单自动资本化。旧库存来源不完整时不会猜测未结状态或自动导入；现场定位证明位置，并不补造历史采购款。实际生产 HTTPS、多人多机并发、员工业务验收与真实备份恢复仍需正式部署环境的验收证据。
