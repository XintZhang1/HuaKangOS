# 物资采购、供应商应付与原款退款

本模块是阶段三的物资采购纵向闭环，使用独立 `procurement / flow_version=2`。旧 `purchase` 单据继续按原版本处理，不自动转换。入口为“采购与应付”；门店必须配置启用的供应商主档、物资和资金账户。

## 员工办理

| 分支／入口 | 经办人及必要事实 | 同一事务中的影响／下一接手人 | 凭据与异常出口 |
|---|---|---|---|
| 新采购申请 | 库管或主管；选择本店启用供应商，填写原因及一至一百行物资、数量、单价 | 冻结供应商名称、编号、税号、付款天数和物资编号、名称、单位、数量、价格；产生主管审批待办；不增加库存、应付或现金 | 申请事实及事件留档；没有实际到货、付款时可取消；退回后需新建申请 |
| 批准／退回 | 主管；待审批，申请人和批准人分离（管理员为显式例外） | 批准后交库管；退回关闭审批。批准不等于到货或已付款 | 退回填写原因，原申请保留；批准后、实际到货前仍可取消 |
| 分批验收 | 接手库管；已批准，逐行核对本次数量及实际验收凭据 | 每行追加到货批次与 `StockMove`，更新物资数量及库存价值；实际到货才形成供应商应付；未到齐继续原库管待办；应付交财务 | 凭据必须属于本单、当前岗位可读且文件安全检查可用。过量、跨单、跨店、隔离文件、已关闭到货均拒绝；多行任一失败全部回滚 |
| 实际付款 | 接手财务；当前应付大于零，核对实际账户、金额、流水号和凭据 | 新建唯一现金来源 `CashEntry`，不可变 `PurchasePayment` 关联原单；分笔付款扣减应付；尚欠继续原财务接手 | 不支持预付款；不得超过实际到货扣除退货后的应付。同账户流水号复用拒绝；后台不会转账 |
| 终止剩余到货 | 主管；已批准、到货未关闭，说明供应商不再供货的原因 | 关闭尚未验收余量，不伪造收货或退款；已验收部分继续正常付款／退货 | 不删除已收批次；需补货时重新申请。已到货订单不能用“取消”消除业务事实 |
| 申请退货 | 库管或主管；选择本单实际到货批次、数量、原因和凭据 | 冻结退货行，产生独立主管复核待办；不修改库存或现金 | 只能退原批次尚未退回的数量，不能引用别单批次；未发出时主管可撤销 |
| 批准／撤销退货 | 主管；申请人与批准人分离，审批需剩余批次数量足够 | 批准数量在其他退货审批中占用，交库管实物发出；撤销释放该审批占用并关闭对应待办 | 仍不移动库存或确认退款；已实际发出后不能撤销记录。并行批准不允许同批次重复占量 |
| 退货实物发出 | 接手库管；已批准并核对原批次、当前本店库存及交接凭据 | 再校验数量，按原到货批次剩余价值分摊；追加负向 `StockMove`、原流水关联及退货事实。减应付；此前超付部分转为“供应商应退”并交财务 | 重复发出、库存不足、原批次退完、数量／价值不相容均拒绝。审批不是实物保管证明，发出时必须重新核对 |
| 供应商实际退款 | 接手财务；有供应商应退，选择本单原付款及原账户，核对实际到账流水和凭据 | 追加入账 `CashEntry` 与关联原付款的 `PurchasePayment`；支持部分退款；净付款下降，余额结清关闭财务待办 | 不能换账户、超出原付款尚未退款额或应退额。仅凭退货申请不能登记退款；不会调用银行／供应商接口 |

所有动作使用采购单版本号，退货动作另核对退货申请版本；相同请求编号和同一参数返回已记录结果，参数不同则冲突。员工看到冲突时先刷新核对结果，不用新编号盲目重试。采购、库存、现金、待办、事件及请求回执一次提交。已有开放待办保留人工转交的接手人，后台同步不会因工作量变化偷偷改派。

待审批、收货、退货待办默认当天到期；应付待办按剩余未付批次最早到期日。到货批次到期日为**实际验收日加该采购冻结的供应商付款天数**。超时展示在现有到期待办中，由主管核对、转交或走取消／终止分支，系统不自动批准、不自动收发货、不自动付款。没有供应商到货承诺日期推断。

## 账目与数量口径

- 所有金额保存为整数分，数量为整数千分位；网页仅负责小数输入转换，后端拒绝浮点金额、负量、额外状态字段和超范围数量。
- 单行约定金额按 `数量千分位 × 单价分 ÷ 1000` 四舍五入到分。分批到货按照**该行尚未验收的金额与数量**比例四舍五入分摊；最后一批拿走全部剩余分值。退货按**对应原验收批次尚未退回的金额与数量**采用同样规则。不能按当前平均单价重新估值。
- 当前应付 = `max(0, 实际验收价值 − 实际退货价值 − 已付净额)`；供应商应退 = `max(0, 已付净额 − 实际验收价值 + 实际退货价值)`；已付净额 = 实际付款 − 原款实际退款。应付和应退逐单展示，不跨供应商抵销。
- 分批到货付款期限按原采购统一冻结的账期和到货日计算。已付净额先抵最早到货批次，批次退回部分先减少该批次应付；因此同一单内到货与到期顺序一致。当前余额及到期行会随实际退款、退货变化，不能作为任意过去日期余额快照。
- 库存仅使用 `Item` 和不可变 `StockMove`；现金只使用 `CashEntry`。采购的批次、退货和付款表是明细与原单关联，报表不能再把它们作为第二份现金／库存相加。物资入出存报表通过现有 `StockMove` 自动包含采购。
- 全部约定数量验收完或主管关闭剩余到货、所有退货申请结束、应付及应退同时归零后，采购完成。完成后的真实退货会重新打开相关待办。退货不会扩大原采购可验收上限，换货补货需新单。

例如采购 `2.500` 件、单价 `1.23` 元，约定金额 `3.08` 元。首批收 `1.000` 件分摊 `1.23` 元，余批分摊 `1.85` 元。退首批 `0.500` 件返还原批次 `0.62` 元，剩余原批次价值 `0.61` 元；最后全部退回时不留分差。测试也覆盖总价值一分、三次到货及三次退货的末次余数。

## 权限、文件与对账

单店业务由本店岗位处理；集团多店视图只读。主管、财务、审计可读金额，库管可读数量、批次、交接但读不到供应商付款约定、成本、现金明细与财务文件。API 每次验证岗位、门店、原单和文件关联，页面隐藏按钮只是提示。

供应商停用前检查未完结采购；有采购历史、库存流水或期初库存的物资不能改计量单位。主档更名或后续账期调整不覆盖原采购快照。资金账户与原付款链接固定，账户历史由全系统账户保护规则约束。

文件通过本单上传入口进入隔离检查；`eng.file_exists → file_security.require_usable` 是每次使用凭据的门槛。上传成功本身不代表实际验收、签名认证或病毒扫描通过。合成浏览器测试显式使用 `FILE_SCAN_MODE=structure_only`；不能据此宣称已验证生产扫描器或真实业务凭据。

`GET /api/procurement/payables` 和 `/payables/export` 使用同一当前原单集合，分别汇总应付与应退。CSV 使用整数分、UTF-8 BOM，保留单号、门店及供应商，可下钻回原单。当前版本对账上限一万单，超过会拒绝而非返回截断合计；未实现任意历史期间应付重建、供应商发票和税额拆分。

## 接口和迁移

- `POST /api/procurement/orders`：请求编号、供应商 ID、原因、多行物资 ID／数量千分位／单价分。
- `GET /api/procurement/orders`、`GET /orders/{id}`：作用域内分页、原单事实与岗位可见字段。
- `POST /api/procurement/orders/{id}/actions/{action}`：请求编号、采购版本、该动作严格字段；动作包括 `approve/reject/cancel/close_receiving/receive/pay/return_request/return_approve/return_cancel/return_dispatch/refund`。
- 迁移 `i309_procurement` 接在 `h208_master_data` 后，冻结建立采购头、明细、批次、退货请求／行／实物及付款关联表；不修改旧版本单据。不提供删除历史账本的降级操作。

自动测试在独立临时库运行；`tests/test_procurement.py` 覆盖角色、跨店、原单关联、部分验收／付款／退货／退款、不可变事实、版本拒绝、精确余数、同批次退货占用撤销、人工转交保持、真实并发验收／付款／退款／取消。`tests/browser_procurement.py` 使用实际 HTTP Chrome、三个员工账号和 390 像素宽页面，全程通过员工表单办理、上传及下载 CSV。

## 本次边界

不支持采购预付款、供应商直连、银行自动转账或已过账流水任意作废；只对实际验收到货记应付，原款退款必须由实际退货形成应退。物资按现有平均库存维护，原批次退货按原批次价值追溯；若此前混合领用造成退原批次后库存价值为负，或数量归零却残留其他成本，系统拒绝并提示核对。该异常尚无自动批次成本调整工作流，不能通过清零价值绕过。正式采购、退款凭据和业务验收仍需公司复核，自动测试与浏览器演练不等于正式启用。
