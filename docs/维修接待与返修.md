# huakangos 维修接待与原单责任返修

本交付提供维修预约、现场来访登记、洗车与快捷项目预填，以及售后原单责任返修。它补充 HK-031、HK-032、HK-033、HK-038 的实际业务入口。功能已实现和自动验证不等于公司业务验收或正式启用；公司仍须确认工位配置、快捷组合、责任审核依据和内部费用承担主体。

接待与责任申请使用 `Case.kind=service_intake / flow_version=2` 的专用 API。实际到店转换的新维修使用 `repair / flow_version=4`，复用原 v3 的不可变报价、价格审批、客户授权、领退料、质检及多方结算。旧通用维修 v1/v2 与旧明细 v3 不自动升级，旧单也不会因车牌相同自动获得 VIN 绑定。

## 日常办理

入口为“维修管理 → 预约、洗车与原单返修”。主管先在“工位与快捷项目”建立服务工位，配置基于启用作业主档的快捷组合。组合只保存作业及数量；转单时冻结当时标准价格。员工仍须逐单取得主管价格授权和客户对当前版本的授权。

| 步骤、岗位和入口条件 | 本人确认的事实及依据 | 同一事务内的效果与下一责任人 | 凭据、超时及异常出口 |
|---|---|---|---|
| 主管新增工位或快捷组合 | 工位用途为维修或洗车；组合引用本店启用作业主档及整数千分位数量 | 保存配置；不安排实际施工，不形成库存或现金 | 组合明细不覆盖，改变组合需新代码。停用有待到店预约、实际占用或未完成维修的工位被拒绝 |
| 服务顾问、接待或客服登记预约／现场来访 | 已确认客户车辆关系、VIN、工位、带时区开始结束时间、客户诉求，可选快捷组合 | 建立接待单与服务顾问“核对实际到店”待办；同工位有效预约区间不可重叠 | 单段最长十二小时；相邻区间可衔接。现场来访允许当前前十五分钟至未来一天内的排队时间，不代表已经实际到店 |
| 服务顾问、接待或客服改约 | 未到店预约；新工位、新时段和客户确认的原因 | 更新计划并记录事件，原待办已明确交接的员工保持不变；同时锁定新旧工位版本 | 新时段不得早于当前时间。已到店、已转单不能改写预约身份；改约影响按计划日期选择的报表批次 |
| 服务顾问、接待或客服取消／核实未到 | 预约尚未记录到店；说明取消原因。未到须已超过预约结束时间 | 关闭接待待办并释放计划时段，不生成维修单 | 系统不会按时间自动判定客户未到。过期由当前责任人核实，主管可人工转交 |
| 接手到店待办的服务顾问确认到店 | 逐位核对现场 VIN、实际里程、本接待单上传的核验文件 | 追加不可变到店事实，状态变为已到店，交服务顾问建立维修明细 | VIN 不符、错门店文件、隔离或未通过当前扫描要求的附件均拒绝；生成模板不能代替实际凭据 |
| 服务顾问实际到店转单 | 已有到店事实；客户车辆仍启用，工位和快捷组合有效 | 只建立一张独立 v4 维修，冻结客户、共享身份、VIN、原到店证据和工位；产生报价任务或快捷预填的价格审批任务 | 重复、过期版本、并发转换被拒绝；不会自动批准报价、确认客户授权、开工、领料或收款 |
| 接手服务顾问记录未开单离场 | 已到店但尚未转单；本人核实离场原因和实际文件 | 追加离场事件、结束接待和待办，保留原到店记录 | 不能把“已到店”改成“从未到店”。已转单后的退出在维修单办理 |
| 技师确认实际开工 | v4 当前报价已授权、接手施工待办；实际进入已配置工位 | 原维修开工事实与工位占用记录同事务保存；有配件时产生库管发料任务 | 工位仍占用、同 VIN 已在本店其他工位施工、当前时段保留给其他未结束预约（包括已转单待开工）时拒绝；计划到期不自动释放实际占用 |
| 技师移出工位或重新进位 | 移出须已提交完工；重新进位须为已开工且仍待施工的工单。记录本人实际进出情况及本单凭据 | 追加进出位事实并更新工位占用；质检失败后的再次施工须先实际重新进位 | 移出不是完工或交车。不能靠移位结束未完施工任务；缺陷未处理及未复检仍不能交车 |
| 服务顾问确认客户接车 | 复用明细维修的质检、承担、客户结清和权益占额门槛，实际接车文件 | 记录交车并释放仍由本车占用的工位；未结保险、厂家继续由各财务待办追款 | 实物、现金及发票结果分别留证。发票差异交独立财务待办，不冒充系统已经调用外部平台 |

工位时段在数据库统一保存 UTC，界面显示本地时间；预约待办到期日按 `settings.timezone` 换算，上海凌晨预约不会错落到前一天。实际接手、释放和到店以系统记录的发生时间为准。首版为门店内部工位资源，未提供技师工时产能、员工绩效排名、跨店工位排程或外部预约同步。

## 售后原单责任返修

首版责任返修限于**本店、同一客户、同一已核验 VIN、已经客户实际接车且已有冻结结算的维修明细原单**。不从车牌、电话、会员号或简要历史摘要推断责任，也不借用其他门店的只读服务历史进行本店返修过账。

| 步骤与岗位 | 必要事实和权威来源 | 原子效果、下一责任人 | 文件及退出方式 |
|---|---|---|---|
| 主管补核验旧 v3 原单 | 已接车的原维修、本店原客户车辆、逐位 VIN 核对、原始凭据位置及原单核验附件 | 仅追加不可变客户车辆绑定，不改变原报价、实物、现金或流程版本 | 原单无强事实时拒绝返修；不允许覆盖绑定，不提供批量猜测迁移 |
| 服务顾问申请返修 | 原单当前版本、最终结算报价行、同客户同 VIN 的已确认共享身份、本次诉求、维修工位 | 建立独立责任申请，锁定同原单当前唯一未结返修，交主管责任审核 | 原单未接车、未核验、错客户、错 VIN、伪造其他报价行或跨店均拒绝。申请不复制原收款、旧配件或权益 |
| 主管批准或拒绝责任 | 对原缺陷的审核依据；批准时明确全部内部费用承担主体及本申请实际凭据 | 批准追加不可变责任记录并交服务顾问核对本次到店；拒绝结束申请并释放原单未结占用 | 普通申请人不能批准本人责任。批准前或批准后未转单可由主管说明原因取消；保留审核历史 |
| 服务顾问核对本次返修到店并转单 | 责任已批准，本次现场 VIN、里程和新的到店文件 | 建立独立 v4 责任返修与冻结来源，追加实际到店转换事件；交服务顾问报价 | 不把原来一次到店视为本次又到店。每申请只能转一次；转换后只能在本次维修办理退出 |
| 本次报价、客户授权、施工领退料和质检 | 本次实际工作及配件主档、独立授权文件、独立库存收发和质量记录 | 全部复用明细维修的原子版本、价格授权、库存守恒和质检门槛 | 没有“复制原单已付款所以自动完工”。增项重新报价和授权；已施工退出须协商停工保留费并按本次原领料退回 |
| 主管冻结内部承担 | 本次当前授权金额和原批准的内部主体、本次实际人工成本、承担凭据 | **本次全部金额计内部承担**；不生成客户／保险／厂家应收，不使用客户集团本金或其他权益，不计对外收入 | 新增客户收费服务请独立建立普通维修，不能附在责任返修单向客户再收。内部主体不一致或非全额内部承担被拒绝 |
| 服务顾问确认返修接车 | 本次质检通过、内部承担已冻结、本次实际接车凭据 | 完成本次返修，关闭责任申请，释放工位及原单未结返修占用 | 原单已有现金不变。本次未开工取消可结束返修；已开工后采用停工保留费路径，不能抹除施工和库存历史 |

这是门店内部责任确认与业务费用记录，不是厂家保修政策引擎，也不是法律责任自动判断。首版未实现跨店责任分摊、按比例客户自付返修、原单损害赔偿或旧 v0.2/v1/v2 历史返修迁移。原单后续保险／厂家到账仍属于原单，不进入新返修现金。

## 权限、文件与账本

- 每个读取、关联 ID 和命令都受本店查询范围约束；集团多店汇总只读。服务顾问可处理本店接待，接待岗位仅能选择本人可读客户车辆；责任返修原单另经原维修读取权限核验。
- 接待命令使用独立幂等回执；重复同一经办人、同一请求号和内容返回原结果，改变经办人或内容拒绝。维修 v4 继续使用既有维修回执。业务、资源版本、事件、待办、文件引用和回执一次事务提交。
- 当前客户报价授权必须使用 `authorization` 文件类别，服务顾问核对它对应的不可变报价摘要。库管和技师不能读取或上传维修／精品报价授权文件；前端隐藏不是权限边界。
- 所有新实际凭据必须属于相应原业务并经过 `file_security.require_usable` 门槛。历史原单核验凭据在责任申请时也重新检查隔离状态。上传或结构校验不等于客户签名真实性、病毒扫描或责任证据真实性得到认证。
- 钱仍为整数分，配件数量为整数千分位。实际库存沿用 `StockMove` 及库位统一过账，退款和旧库存不会因新返修重复入账；实际现金仍只有 `CashEntry`，`PaymentLink` 只关联它。
- 维修首次客户授权调用会员消费积分规则冻结，实际交车／到账变动后同步符合规则的积分；纯内部返修没有客户消费积分。发票协同按本业务实际金额和状态更新财务调整待办。

## 数据与恢复

追加迁移 `t420_service_intake`，前置 `s319_membership`。它冻结十二张 `intake_*` 表，保存工位、快捷组合、预约、不可变到店、客户车辆绑定、返修申请、原结算项目、内部责任、维修来源、进出位流水及幂等回执。迁移不导入演示业务，也不升级旧维修语义。

`service_intake_backup_integrity.validate(connection)` 已接入统一恢复校验。它核对原业务门店、客户与 VIN 绑定、预约到店与唯一转换、原单最终结算项目、客户授权类别及报价摘要、返修内部承担，并按不可变进出位流水重建实际工位与同 VIN 占用。内部责任返修不能出现客户现金或集团权益支付关联。恢复校验不证明数据从未被有数据库权限的人员共同篡改，也不代替真实工位清点或业务人员核实。

## 验证与证据

自动测试位于 `tests/test_service_intake.py`，包括正常接待与责任返修、快捷洗车冻结报价、到店后离场、拒绝／取消、旧 v3 补核验、人员交接、跨店及多店只读、伪造原行和 VIN、隔离文件、客户授权私密性、报价和原数量成本守恒、非空恢复及七种篡改拒绝。竞争测试覆盖同工位预约、重复转单、重复开工、不同工位同 VIN、同原单重复责任申请；还有已转单保留时段和当地凌晨到期日。

接待批次、实际到店和当前工位报表分别核对原记录、图表和 CSV。计划日批次不是实际到店日，当前占用不是过去任意时点重建；不得用不一致批次计算转化率。

`tests/browser_service_intake.py` 使用新合成数据库、随机岗位密码、真实 HTTP Chrome 和 390×844 页面，五岗位完成：错误 VIN 拒绝→实际到店→待审批预填→独立报价与授权→技师进位→库管发料→质检→客户 105 元实际收款与接车→原单全额内部 15 元返修→再次接车；原现金不变，本次内部返修不再收客户款。另验证实际到店后未开单离场。五条员工链已通过且无 JS 错误，截图逐页目检；截图保存在仓库外合成验收目录，不包含真实客户或密码。

浏览器与测试使用明确的 `FILE_SCAN_MODE=structure_only`，页面如实显示“仅结构检查通过（未查毒）”。本机验证不替代正式 HTTPS、真实扫描器、PostgreSQL 多机并发、公司业务确认及正式月结验收。
