# 经营主体与账户归属

## 本版范围

产品品牌 `huakangos · 华慷集团` 不代表任一家门店的法定经营主体。系统不预填真实公司名称、识别号、登记地址或银行资料，也不宣称工商认证。这里实现有来源的主体版本、门店绑定、资金账户绑定和原业务归属接口。

原表 HK-189 机构设置、HK-185 财务基础字典与 HK-097 开票，以及合同、采购凭据，是相关使用场景。原表并未单列完整企业会计核算系统；本模块不能据此替代总账或声称全部功能已验收。

本批已将窄接口接入通用和专用业务的创建、原单派生、实际现金以及文档快照。下文列出已实际验证的联动范围；独立配置测试不能代替全域回归与公司验收。模板仍须公司提供经营主体资料、正式格式与业务审批后单独核验。

## 员工办理

1. 管理员在一家具体门店提出“主体资料版本”申请，填写实际资料，保存后上传本人核对的来源文件。
2. 管理员提交，系统把复核任务交给本店另一名启用主管。管理员不能自批，也不能作为主管的默认替补。没有另一名主管时提交失败。
3. 主管查看原资料、上传本人本次核对凭据后批准；不一致时拒绝。批准产生不可覆盖的主体资料版本。
4. 管理员分别申请门店绑定、每个实际资金账户的主体绑定，再由主管独立批准。批准版本不自动修改其他门店或历史账户。
5. 空门店配置完毕后，另提“启用新业务主体冻结”申请。全部启用资金账户须有相同主体的批准绑定，且不能仍有未结、未知归属的活跃旧业务、库存、资金或内部往来。

门店与账户绑定仅支持**批准当日**生效。跨日未批准的申请应取消并按实际日期重新提出；不回填历史，也不安排未来自动换主体。

另一主管应留下本人实际核对记录。重复上传与申请人完全相同的文件字节会复用原附件；这不会改变原上传者，也不能冒充主管自己留下的核对凭据。

审批前可以由原申请人取消。已生效配置不能删除或回退覆盖；改名、地址更正另建主体资料版本，再单独批准门店使用该版本。主体编码和识别号是稳定身份，不能用资料修订改变。

待办有负责人及期限。逾期不会自动批准、自动联系或自动转交；管理员或主管可明确选择本店另一主管、处理日期及原因转交。旧负责人随后不能继续批准，责任和事件保留。

## 账户与切换限制

账户绑定保存本店 Account 编号与原版本、名称快照、主体资料版本、实际户名、渠道类型、渠道标识、机构名称和批准来源。

- 户名必须与所选主体资料名称一致。别名、集团代收、授权收款不靠字符串猜测。
- 同一个实际银行或钱包渠道的规范化标识不能重复建立经营账。现金存放处的标识只在本店内唯一。
- 本检查仅按实际输入的标识防重复，不验证开户真实性；不同拼写是否同一真实银行账户仍由员工依据文件核对。
- 已绑定账户不能换成另一个实际资金渠道，也不能改属于另一主体；应另建明确独立账户。门店现有基础账户网页支持银行和现金两类；钱包渠道需要相应 Account 类型入口接通后才能办理。
- 新业务的实际账户必须与该业务冻结主体一致。原路反向现金关联原实际现金、原账户和原主体，不能改成当前默认账户。
- 不对账户之间互抵净额：每个账户都须核清。物资数量与价值、整车在库/在途/销售占用、未结业务/独立待办、客户预收、旧会员本金、未清店间调拨以及集团会员/权益内部结算余额均阻挡换为另一主体。

已提车销售单须同时有原实际提车事件和已交付 VehicleHold，已转订单的线索须有原预订事件与本店订单子单，才按各自流程视作终态。只有状态文字不算依据。独立发票、退款或回访待办、未结子单继续阻挡；不删除交付占用历史来“清空”库存。

同一主体仅名称或地址换版本不重标旧业务，旧名称、原账户户名及凭据继续保存。不同主体的业务不能在一次月结、现金分配或原责任方案中混合；同一主体的不同名称版本可以在明确核对后共同结算。

正式新店允许先完成主体与账户批准、启用策略，再办理[正式期初核验](期初资料安全导入.md)。期初仅复用资料中明确指定的已批准 Account 编号，试导入和确认都不重建账户；旧基准日余额追加到独立期初账，不当作实际收款。新方案保留创建日的冻结主体，不声称旧基准日曾已核准归属。

## 历史与原单责任

策略启用记录当前本店 Case 和 CashEntry 的编号界限，不把界限前的记录自动归给现在的主体。只读历史显示“主体未确认”。新增业务日期早于策略批准当地日期会拒绝；时间戳使用数据库 UTC，比较日期时按配置时区换算。

正式环境 `APP_ENV=production` 中，`freeze_case_entity` 即使收到 `required=False` 也要求先批准本店策略；经营主体配置申请本身豁免，否则无法完成首次配置。仅有品牌、门店名称或未批准申请不能办理正式新业务。

原业务主体未知时，生产环境或本店已启用策略后的新增实际现金会拒绝。不能靠当前账户资料补认历史资金。旧未结业务没有自动迁移方案；有真实业务的旧库需要另行确认资料与有据迁移，不以此模块偷偷补齐。

原单已经有冻结主体时，以下明确派生用途可保留原责任：

| 派生用途 | 必须存在的实际关系 |
|---|---|
| 售后 | AftercareOrder 的原业务编号 |
| 蓝票/红票 | InvoiceApplication 的原业务或原蓝票编号 |
| 整车原出库退回/客户退车 | VehicleOperation 的原出库，或售后单与原车辆订单 |
| 理赔/责任纠正 | ClaimOrder 的原维修业务 |
| 未用预收退款 | FinanceOrder 指定的原 FinanceAdvance 业务 |
| 收款更正 | FinanceOrder 指定的原现金主体上下文 |
| 其他入库原退货回款 | FinanceOrder 指定的原实际 StockMove 业务 |

派生上下文继承原 `policy_id/binding_id/revision_id`，追加 `source_case_id/derived_kind`，不改原记录。服务按实际已保存的关系核验，用途不是调用者自报即可生效。普通新单借旧主体、串店原单、无原主体或多个相关原单主体不同，都拒绝。

## 给业务域的窄接口

所有函数使用调用者现有 SQLAlchemy 事务，**不提交**。业务域仍须完成岗位、原单关系、金额/库存容量、实际日期、原路退款和附件授权等自身校验。

```python
# 1. 普通新 Case：首次 flush 后，首个 FlowEvent 之前。
freeze_case_entity(db, user, case)  # 正式环境自动强制

# 2. 原单派生：先 flush 实际领域关系行，首个 FlowEvent 之前。
# 不要先冻结当前主体，然后再尝试改成原主体。
freeze_derived_case_entity(db, user, case, source_case)
# 等价：freeze_case_entity(db, user, case, source_case=source_case)

# 3. 结算前校验真实账户归属；反向款传原实际现金。
require_account_entity(db, user, case, account_id, actual_date,
                       original_cash_id=original_cash_id)
# CashEntry flush 后、本次领域动作提交前追加。
record_cash_entity(db, user, case, cash, account_id,
                   original_cash_id=original_cash_id)

# 4. 多原单月结、分配或责任方案：每个原单都须获权且同一主体。
assert_same_case_entities(db, user, source_cases)

# 5. 查看冻结资料。不会默认为当前门店主体。
case_entity_snapshot(db, user, case)
```

只有后两步身份一致，不代表足够支付或可退款；实际金额上限仍由各原账领域检查。CaseEntityContext 与 CashEntityContext 是归属索引，不是第二套收入、支出或库存账。报表不能把上下文当成新增收付款。

### 两店协调

调拨、清算的发起人可以没有对方岗位。此时不能假扮对方员工或扩大目录、客户、文件查询。

已有三种受控中央来源分别是 MaterialTransfer、VehicleTransfer、ClearingOrder：

```python
with existing_coordination_scope(db, party, fixed_parties):
    db.add(case)
    note_coordinated_case(db, user, case)  # 必须首次 flush 前
    db.flush()

# 中央来源已经 flush，固定双方 Case 编号后：
with existing_coordination_scope(db, party, fixed_parties):
    freeze_coordinated_case(db, user, same_case_object, central_source)
```

令牌绑定当前 Session 事务、原发起员工、既有领域 authority 和该待创建 Case 对象。冻结再检查中央来源、固定门店对、固定 Case 编号、申请人、requested 初态及无实际物资/现金事实；不能拿历史任务回来补填。只返回 None，并追加“系统按双方来源冻结本店主体”事件，不向发起人返回对方名称、识别号、账户或文件。
