# huakangos 业务对账、月结清单与店间实际清算

本模块把“业务来源已经记录”“财务已经核对”“主管已经封存”“银行实际到账”分别留证。它提供单店期间对账和原单应收月结清单，以及物资／整车调拨往来的双店实际现金结算；不是会计总账，不生成银行指令，不把对账清单当成收款。

## 期间对账与版本

财务在具体门店选择开始、结束日期和核对依据，系统创建独立对账业务单、待办及不可变来源快照。期间不得晚于今天，日期跨度最多365天。同店同期间已有版本时，必须从原版本明确重算或复开，不能另建互不相关的重复月结。

快照逐条保留来源类型、原记录编号、原业务关联、金额／数量、原始冻结内容与总摘要：

- 所选期间的实际 `CashEntry`、原单 `PaymentLink`、`StockMove`、旧门店会员账、集团本金及独立权益账。
- 物资采购付款、到货、退货；整车采购付款、到货及出入库；精品收退款关联、出库及退货。付款按关联现金或收款链接业务日期，实物按关联库存账或原实物日期。
- 生成时点的集团本金／权益内部往来、物资／整车调拨往来，以及本店仍待办理的消费占额和退款申请。当前状态与所选期间明确分列，不重建过去余额。
- 生成时点的未收款：沿原业务列出客户、原单、应收／已收／待收；维修多方承担分别列客户、保险、厂家等付款方。实际收款继续在各原业务办理。

金额单位均为整数分。现金、收款关联、库存价值、会员本金、权益和内部往来分别核对，不能相加成“总资金”。赠金分、积分、券张、套餐次数分别按种类汇总，套餐再按作业编码区分；物资数量按物资ID分列，不能跨不同SKU／单位相加。页面提供核对要点、逐条差异及前200条冻结来源，完整版本可下载CSV；导出使用当前门店授权并保留防公式注入处理。

| 动作 | 经办、入口及必要事实 | 结果与下一责任人 |
|---|---|---|
| 生成期间对账 | 本店财务／管理员；合法期间、核对依据 | 生成版本1快照及财务待办，不新增实际账目 |
| 记录差异 | 财务／管理员；草稿版本、该版本真实来源条目、整数分差额、说明及本批凭据 | 留下逐项待核对记录；0分可表示需要核实的事实差异，不强迫编造金额 |
| 记录处理结果 | 财务／管理员；尚未处理差异、差异版本、本批处理凭据及结论 | 保留原差异及处理结果；不更改现金或库存。需要纠正原账时，先在原业务追加正确事实，再重算 |
| 提交复核 | 财务／管理员；无未处理差异 | 重新计算来源摘要；发现晚到、冲正、应收或待办额度变化则拒绝，要求新版本。通过后转店长封存待办 |
| 独立封存 | 另一位本店店长／管理员；已提交、无未处理差异、本批复核凭据 | 再次比较来源；复核人与制表／提交人必须不同，管理员也不能自批。保存封存人、时间与证据，结束本版本待办 |
| 重算新版本 | 财务／管理员；尚未封存版本、原因 | 旧版本标为已有后继，保留其来源、差异、摘要和事件；新版本重新采集来源并返回财务待办 |
| 复开 | 店长／管理员；已封存版本、明确原因 | 追加唯一后继版本；旧版本仍保持已封存及原封存事实。新版本重新财务核对和独立复核 |

同一动作使用固定请求号、对账版本与业务单版本，一次事务提交快照状态、差异、事件、待办及回执。过期版本、重复请求内容不一致、串店原单和隔离凭据均拒绝。正常重复请求返回原结果，不产生第二版或第二次处理记录。

封存不会禁止真实业务晚到入账。封存之后若来源变化，打开旧版本会显示变化提示；旧快照仍可下载，应由店长根据公司业务规则决定复开。系统没有通过锁账拦截实际收款，也不声称封存能排除封存之后提交的交易。跨门店集团视图不能创建、处理或封存对账。

## 原调拨往来实际清算

本版实际清算入口仅接受付款门店的负数原应付条目，来源为已发生验收的物资／整车配对往来。服务验证对方对应正数条目、相同调拨／验收、双方门店与原金额。申请可以是部分金额，但“待支付申请＋已支付未到账＋已结清”累计不能超过原应付。数据库检查约束、原条目锁、独立额度版本及双方单据版本共同阻断竞争占用。

| 动作 | 经办、事实与权限 | 原子结果、责任和异常出口 |
|---|---|---|
| 申请部分／全部清算 | 付款店财务／管理员；本店原应付、尚未占用额度、实际约定日期和依据 | 占原条目额度，建立双方各自的清算业务单及财务待办。只生成协调资料，不记现金 |
| 确认实际付款 | 付款店当前待办财务／管理员；尚未付款、本店有效账户、唯一银行／现金凭证号、本清算单已通过附件策略的凭据 | 本店新增一笔实际现金支出；状态变为已支付未确认到账。保留全部占额，不提前核销往来；收款店继续办理 |
| 确认实际到账 | 收款店当前待办财务／管理员；付款方已经登记支付、本店账户和本店实际到账凭据 | 收款店新增一笔实际收入；按固定申请金额追加双方原往来等额反向核销，释放占额并累计已结清；双方单据结束 |
| 撤销／拒绝 | 尚未发生实际付款；付款店可撤销、收款店可拒绝 | 释放本申请占额并结束双方待办，保留历史，没有现金或往来核销 |
| 记录差异 | 尚未结束的任一方本店财务；本店清算凭据与真实说明 | 留在本店事件中，状态和现金保持真实事实。已支付不能用取消抹掉支出，未到账继续显示内部在途及收款方待办 |

正常清算每一方只确认自己的银行事实，不能代替另一家门店记收入或支出。后台跨店协调仅创建或结束双方本地任务／单据，并在双方均确认后追加对应往来核销；不读写对方账户、附件或其他业务。读接口只返回当前一方宿主单ID及本店现金／凭据，不暴露另一方文件或原业务历史。

例如原调拨应付99分，乙店申请并实际支付60分：99分原应付保持不变，60分占额且显示内部现金在途，剩余39分仍可申请。甲店实际收到60分后，各店各有一笔60分现金，乙店对原负应付追加+60分、甲店对原正应收追加−60分；剩余39分仍未结清。重复到账、过期版本或竞争核销不会重复过账。

单店现金流保留本店真实内部收入／支出并单列；集团“对外现金”口径排除内部清算现金，但另列内部真实出入及尚未确认到账金额。已付未收不会因集团汇总而变为“双方已经结清”。历史 `TransferSettlement`、`VehicleTransferSettlement` 不覆盖；核销独立记账。

集团会员中心在本项目中只做本金、权益及内部往来记账；集团已有独立财务系统负责实际付款。对账快照不生成中心银行现金，也不增加中心实付/到账审批、支付接口或实际资金清算任务。此项明确不建设，不是后续另交付。

## 接入、验收与恢复

- API：`/api/reconciliation/batches`、`/batches/{id}/actions/{action}`、`/batches/{id}/export`；原调拨应付 `/origins`；双方清算 `/clearing`、`/clearing/{id}/actions/{action}`。动作字段见 `app/reconciliation_api.py`，没有任意状态或金额修改接口。
- 原单宿主使用 `reconciliation`、`interstore_clearing` 的流程版本2。财务、店长、管理员及审计员可读，审计员只读；其他员工不能通过通用单据、文件接口绕开角色限制。
- 财务事件都关联操作人、理由、原单、可用凭据和版本。未完成任务按既有到期及交接能力提醒，不自动代员工确认、不自动访问银行。
- 报表接入 `internal_cash_ids(db)` 与 `settlement_rows(db,user)`，后者返回当前授权范围内的本店现金、原往来核销及未确认到账清单。金额保持整数分，现金下钻指向当前一方清算宿主。
- 迁移 `q117_reconciliation` 追加8张冻结表，依赖 `p016_retail`，不重写旧迁移。
- `validate_reconciliation_sqlite(connection)` 只读验证冻结快照摘要、版本链、差异来源／凭据、独立封存、原调拨配对、清算占额、双方现金与原流水、核销金额守恒。保留历史快照允许合法晚到变化，不用当前余额覆盖历史版本。数据库管理员仍有技术修改能力，这不是加密防篡改存储。

2026-09-21，13项专项 API 测试通过，验证真实物资与整车调拨付款／到账、部分金额守恒、撤销／拒绝、跨店／凭据／岗位拒绝、重复与过期版本、并发占原条目与并发到账、管理员自批拒绝、晚到重算、原版复开保留、CSV、独立单位统计，以及整车采购和精品实际退货来源变化。内部现金／待收／往来图表与表格、CSV和原账一致，旧现金接口不能抹掉清算现金。非空恢复测试对快照来源及摘要、现金、额度和核销篡改分别拒绝。

真实 Chromium 的390像素财务及独立店长页面完成4个场景：99分原调拨的60分部分申请、付款后内部在途、晚到拒绝及新版本差异处理／独立封存、对方实际到账后双方结清；无 JavaScript 错误，截图逐页检查并保存在仓库外。增加了本店授权下的实际CSV下载验证。这些是合成资料本地HTTP验证，不替代生产HTTPS、公司真实月结和银行对账周期验收。

同日真实 PostgreSQL 17.11 验证达到 `q117_reconciliation`：全新空库迁移、124张表／933行合成资料转入及逐表摘要、33份附件SHA-256、`pg_dump`至独立空库恢复均通过。非空样本含一笔双方实际结清、一笔已付待收、月结差异处理及独立封存／复开；原快照、现金、核销与占额均被保留。详情和可复现脚本见 `docs/PostgreSQL验证.md`。两连接竞争检查针对数据库版本／锁及回滚，不等同于所有业务API已在PostgreSQL上完成并发测试。

尚未实现银行退汇／付款后撤回、手续费／汇差、跨原条目净额合并付款、银行流水自动导入匹配或会计期间锁账。已付款后发生退汇时，本版只能记录差异并保留未结状态，不能自动恢复额度或伪造对方到账；需补充有原款关联的实际退款闭环后覆盖该分支。上述限制应列为正式启用内部清算前的业务规则确认项，不得把正常清算场景通过称为所有财务需求完成。

## 来源定义升级

2026-09-21 新批次采用 summary.definition_version=2，除原来源外，纳入 invoice_results（按实际issued_on，蓝正红负）、warehouse_entries、当前warehouse_balances、membership_fees（关联现金业务日）、membership_points_changes及debt_payments、当前points_claims及派生待追回积分/发票差额。

历史未存此标记的批次按定义1解释，生成、封存摘要保持原范围。读取/再次提交按该批次自己的定义比较变化；重算/复开才采用定义2。未知定义拒绝，不猜测。UI明确提示旧版没有新增来源。派生行恢复校验限定类型、定义、原单门店/route、金额差额及原始积分债务来源；它们并非无来源的任意报表行。仍不构成客户统一月结收款单，也不全局关闭业务期间。


后续显式定义3增加售后/业务预收/集中收款/误记更正，定义4增加期初/私有文件/充值组合，当前定义5增加核赔、CSV原行与精品套餐冻结来源。以上仅重算或新建时采用；读取/封存旧批次保持其原定义。客户月结实际收款已有专用业务财务模块，仍不把快照确认作为到账或全局会计锁账。

## 来源定义9：核销后找到原物资（2026-09-22）

新建、明确重算或复开的批次使用定义9；原1—8定义仍按自己的集合重算源变动，原快照与摘要不覆盖。定义9只补本店找回事实，不把尚未接好的精品集团草稿纳入正式核对来源。

| 来源 | 口径 | 核对含义 |
|---|---|---|
| `transfer_goods_facts` | 本批业务日期期间 | 本店实际找到、核对、复验、发回、接收、处置等观察；同一物资可有多个观察，不可当成入库数量相加 |
| `transfer_goods_postings` | 本批业务日期期间 | 真正原成本恢复及其原库存条目；坏件零恢复也保留实际处理记录 |
| `transfer_goods_reviews` | 生成时点 | 本店独立批准/拒绝记录，不包含另一门店的原件 |
| `transfer_goods_settlements` | 生成时点 | 本店对原损失承担的有向反向往来；不是已支付现金或已核销余额 |
| `transfer_goods_terms` | 生成时点 | 找回与原追偿新旧条件之间的不可变引用 |
| `transfer_goods_refunds` | 生成时点 | 找回与真实原退款的引用；金额来自既有 `transfer_recovery_payments`，现金只计 `cash_entries` 一次 |

找回协调头和跨店方案不是本店可写财务来源，不整张导入月结；六类来源全部按本店过滤。仅获财务/管理/审计读权限的单店角色可见，集团汇总不能创建跨店对账。

恢复校验逐字段比对原始关联、实际量价、承担、经办人及凭据，核对期间/时点、日期与冻结摘要。重新计算摘要不能使错原损失、错门店、错复核人或错口径合法；删条目而保留原摘要同样拒绝。合法后来事实不会被强塞回旧快照。此为内部一致性验证，不是抵抗能同时改写数据库与全部验证元数据的管理员的外部签名。


## 当前开发至定义21（尚待整树冻结）

定义18增加本店会员价规则、适用范围、独立决定、原报价快照、逐行价差和授权；定义19增加本店混合维修套餐的报价快照、购买事件、占额链接、核销链接、内部往来、退款、售后占额和实物原退；定义20增加部分实退原收款更正基准和原退款切片。详见对应reconciliation_v18/19/20，新增表的本地关联摘要不作为第二份现金、收入或库存；集团中央合同和跨店附件不纳入本店来源。

定义20使用现金定义6：正确总实收扣除原真实退款后才等于剩余业务分配。原误记款与其冲正同时排除，原真实退款只计一次。旧1—19及其现金口径仍可核验，不因当前新增功能扩写已封存批次。重算生成新版本，旧批次保留；恢复还核对原不可变字段、附属摘要和真实账本，不能只重算摘要冒充来源正确。

定义21追加续会费原款更正申请、不可变执行链和真实退款依据三项本店来源；申请状态变化不改冻结业务字段。三项摘要只计记录数，不另加收入。现金定义7在定义6基础上排除被续会费纠错替代的旧现金及记账冲正，正确登记仍按原实际收款日计一次；后继真实退款按实际退款日计一次。会费本身及会期不追加第二笔，旧1—20定义保持。专项和恢复验证完成前不宣称通过。
