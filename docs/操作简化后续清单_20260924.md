# 操作简化后续清单 · 2026-09-24

本清单在原定位记录上更新完成状态，不新增业务范围，不把准备、审批、实物和现金合并。第一轮入口简化见 [员工操作简化](员工操作简化_20260924.md)，本轮操作与专项结果见 [员工操作与文件填表](员工操作与文件填表_20260924.md)。已实现不代表公司验收通过或正式启用。

## 1. 原表库位准备：常见三类已做，采购退库等仍待优化

定位：`web/warehouseprep.js`、`web/procurement.js`、`web/repair.js`；原独立入口为 `web/warehouse.js` 的 `warehouseAllocationPage/whAllocate`，规则为 `app/warehouse_service.py` 的 `allocation_options/prepare_external`。

**本轮已做：**采购分批到货、维修领料、维修原领料退回，在原表打开“分配库位”，带入已选物资和数量。只有一个可用物资库位时预填；多库位显示尚差或超分配，名称包含仓库。保存后保留原表数量与凭据；修改数量会使本表已准备的计划失效。过期版本或保存结果不明时要求刷新核对，不静默重做。

**仍待优化，优先处理：**采购退库涉及同一物资多个原到货批次时，仍需独立“准备物资库位”页面。后续应从每个原退货批次带入实际方向、物资和数量，分开显示原批次及本次库位。当前同物资多个原批次不得在同次准备中混合，应逐批办理；其他尚未接入的收发场景保留独立库位入口。

必须保留：库位准备仅保存计划，不占数量、不入出库；保存更新原单版本，实物确认才按精确数量、可用量、盘点和原业务占用检查并过账。不能将多个原批次的成本、可退量或凭据合并，也不能拿新版本盲目重试原实物动作。

## 2. 常见维修承担：本轮已做

定位：`web/repair.js` 的 `repairAllocate`；原规则为 `app/repair_api.py` 的 `Allocation` 和 `app/repair_service.py` 的 `_allocate`。

**本轮已做：**员工明确点击“客户全额承担”才带入当前授权总额；保险、厂家和内部承担按需展开，相关目录按需读取。留空或填 0 均不生成承担行，显示已分配和尚差/超出金额，支持表内上传。核赔工单展示当前对应单位与结果，不默认把第三方承担转给客户。

专项已经验证普通自付、保险分担、零值其他方、核赔防绕过、原返修分支和失效上下文；公司仍需用实际增项、套餐、返修等业务组合试用。不要把这次简化理解为取消原质检、授权或结算规则。

必须保留：当前授权和质检版本、总额相等、每类一行、实际人工成本、内部责任和核赔一致性。已结算分配不能覆盖，预收、实际到账和退款仍分别办理。

## 3. 仓储原收发行退回：本轮已做

定位：`web/warehouse.js`、`web/warehousereturns.js`；`app/warehouse_service.py` 的原批次候选和原 `create/_act` 规则。

**本轮已做：**其他入库、耗材发出、礼品发出的可退原收发行旁提供“退回这批”；全局退回入口按物资、编码或原单号实时查原批次。选中后显示原日期、数量、已退和尚可退，不再要求员工手填数字流水编号。三种退回各查自己的原批次，不混采购或维修。

实际库位和本次实退数量仍由员工确认，不默认回原位。申请与实际退回分开检查累计余量；原批次剩余价值及尾差继续按原规则处理，不让员工重填成本，不自动退款。已通过的真实浏览器链为合成礼品原退，其他类型的公司岗位操作仍待试用反馈。

## 4. 理赔缺原款：本轮已做

定位：`web/claims.js` 的 `claimOptions/claimMissing/claimAction/claimSelectionDialog`；`app/claims_service.py` 的按动作原款候选及原返还规则。

**本轮已做：**缺报销款到店、缺客户退回款等情况，说明应先补哪一步，能办理时提供同单按钮，其他岗位则说明交接人。无需退款的方案指向责任调整生效步骤，仍需要本次凭据。

原款候选显示凭证、日期、账户和该动作真实可办金额。混合返还中，客户退回只选择已转付客户款，未转付原款退回只选择到店且尚未转付的原款；扣除已退、已转付和其他批准方案占额。

必须保留：原维修版本、独立批准、原方案和原账户绑定。外部核准不等于现金，权益不折现，直接付客户不记本店现金，经店路径仍先入后出。实账不由候选查询改写。

## 5. 文件资料填表：已接入，待最终文件链和全量结果

定位：`web/businessassistantfiles.js`、`app/business_assistant_files.py` 及业务助手固定操作接口。

员工主动选择支持的文件后先预览，再勾行或文字、填写目标、核对发送内容，DeepSeek 补问并生成待确认表单。资料和填写内容可下载成新 CSV，原文件不覆盖。原文件解析不调用模型、不写业务、不自动作为凭据；模型只使用已有业务表单，不运行代码。

本轮文件浏览器、实际模型填表及最终冻结源码全量结果以最终验收记录为准。后续根据员工反馈整理不支持或无法识别的实际文档样例；PDF/OCR、宏和复杂 Word 表格暂不在本轮支持范围。不要为了减少步骤取消“选择资料”和“确认办理”。

## 6. 保留的后续体验事项

| 待办 | 下一步 | 必须保留 |
|---|---|---|
| 跨店协同原单选择仍有查找按钮 | 输入后实时提供可选原单，保留必要的最少关键词 | 原岗位和门店范围、附件授权、撤销、旧会话隔离，查询不到不能扩大访问 |
| 主档维护页仍有重复入口 | 将常见创建集中到业务表，管理员保留完整维护入口 | 历史修订、停用、公司规则和各自账本，不把不同身份或经营关系混为一项 |
| 尚未接入原表的库位收发步骤 | 先处理采购同物资多原批次退库，再按员工频率推进 | 原批次、实际数量、原成本、过期版本拒绝及实物不重复过账 |

后续每项仍需要拒绝、重复请求、过期版本、切店及账本/实物守恒验证。公司试用发现的具体卡点可以在“业务助手 → 问题清单”记录，按实际频率调整顺序。
