# P1 写入按风险分类 + P2 向上级评审 验证报告

2026-09-24。按 `docs/助手权限与评审设计_20260924.md` 的四个决定继续：P1（写入按风险分类放开）与 P2（权限不足时向相关上级提交评审）。

## 一、P1：写入按风险分类

**结论先说清楚**：把"评审名单之外的写入"逐条量过一遍——**16 条**。其中 14 条本来就属于你定下的禁区（员工账号与密码、门店设置、经营主体申请、数据复核结论、日报生成、原有单据的任意修改），另有 1 条是**多部分文件上传**（整车请款/批量交接的 CSV 原件），也不可能由助手代传。真正可以放开的只有 1 条：整车请款批次的**办理动作**（试办理、改派），而且它的确认/复核/取消动作按你的规则仍然只指路。

| 改动 | 说明 |
|---|---|
| `app/business_assistant_gateway.py` 新增 `DECISION_TOKENS` 与 `assert_not_decision_action` | 通配路由 `/actions/{action}` 上，动作名含批准/驳回/作废/取消/确认/同意/重开/封存/复核/结算/挂账/改价/整批确认/退款/付款/收款/开票/质检/检查/处置/核销/终止 等语义时**拒绝准备**，返回「只能由有权限的岗位在原业务页面本人办理；权限不够时请在“评审申请”里向上级提交」。此前这类动作是可以被准备成确认卡的 |
| `validate_operation` 调用该检查 | 直连准备与"工单动作"（`prepare_case_action`）两条路径都经过它，因此一个口子就够了 |
| `app/business_assistant_capabilities.json` | 加入 `POST /api/vehicle-imports/batches/{batch_id}/actions/{action}`（清单 286 项） |
| `CLASSIFIED_BLOCKED_WRITES` | 14 条禁区写入 + 多部分上传那条，写成代码里可评审的清单；新增测试要求**每一条已注册写入都必须被分类**（清单内或明确 blocked），新加路由而忘记分类时测试直接失败（fail-closed） |

实测：`approve/reject/cancel_request/confirm/quality/inspect/refund/pay/receive/invoice_issue/reopen/seal/settle/credit/revise/commit/consent/void/terminate/dispose/write_off/internal_settle/reinspect/cancel_approve` 共 24 个动作全部拒绝；`follow/start/finish/deliver/material/quote/remind/rework/rectify` 等日常步骤仍可准备；整车请款批次的 `trial/reassign` 可准备，`review/confirm/cancel` 拒绝。

**可调**：这份禁用词表是一个常量。如果你试用后觉得某类动作（例如登记收款）希望让助手准备，改一个词即可——但按你 2026-09-24 的决定，默认保持"判断类只指路"。

## 二、P2：向上级提交评审

新功能，四件东西：数据表、接口、页面、规则。

**规则（都由服务端判定，模型与前端不能指定）**

| 规则 | 实现 |
|---|---|
| 收件人 | 本店店长；申请人本人是店长或管理员时转**集团管理员** |
| 不改变权限、不执行业务 | 评审只写"请求 + 处理轨迹"两张表；没有改角色、没有写入 Case/CashEntry/StockMove；上级在原业务页面本人办理后回这里登记结果 |
| 不能自己批准自己 | `to_review` 队列排除自己提交的申请；对自提申请做动作一律 403 |
| 只解决权限/额度不足 | 原因选"业务规则不允许"时**创建即被拒绝**：422「业务规则明确不允许的事项不能通过评审绕过」 |
| 要凭据事实 | 必须填系统提示原文（≥8 字）与要办的事（≥5 字）；同一件事重复提交 409 |
| 门店范围 | 表按门店隔离；查询用带条件的 select（不是 identity-map get），跨店经理看不到、也动不了 |
| 版本与轨迹 | 处理动作带版本号，过期返回 409；提交/接手/办理/驳回/撤回全部追加到 `escalation_events`，不修改不删除 |

**接口**：`GET /api/escalations?scope=mine|to_review`、`POST /api/escalations`、`POST /api/escalations/{id}/actions/{claim|done|reject|cancel}`。

**页面**：左侧"评审申请"（`#escalations`）。店长/管理员多一个"待我评审"页签；按钮按身份与状态给出（接手 / 已办理 / 驳回 / 查看 / 撤回），办理与驳回必须写说明；详情弹窗显示系统提示原文与完整处理轨迹。

**迁移**：`h47e_escalations`（`down_revision = g35t_assistant_thinking`），新建 `escalations` 与 `escalation_events` 两张表（含状态/原因/收件人的 CHECK 约束与门店状态索引）。迁移只追加，不回改历史。

## 五、边界与不做的事

- 助手**没有**新增"准备评审申请"的工具：员工自己在页面提交（表单很轻）。`find_workflows` 与提示词已经把"需要更高权限时用评审申请"告诉模型。若以后要在对话里一键准备申请，按现有"待确认卡片"机制加一个工具即可，仍需员工确认。
- 评审不产生任何审批结论、不代签、不改权限；上级驳回时申请人只是看到原因，原业务规则不受影响。
- 公司实际业务验收、生产部署、真实 PostgreSQL 仍待进行；本轮未跑全量回归（230 项目标回归，下轮合并前补跑并更新）。
