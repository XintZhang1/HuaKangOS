# P1 写入按风险分类 + P2 向上级评审 验证报告

2026-09-24。按 `docs/助手权限与评审设计_20260924.md` 的四个决定继续：P1（写入按风险分类放开）与 P2（权限不足时向相关上级提交评审）。

## 一、P1：写入按风险分类

**结论先说清楚**：把"评审名单之外的写入"逐条量过一遍——**16 条**。其中 14 条本来就属于你定下的禁区（员工账号与密码、门店设置、经营主体申请、数据复核结论、日报生成、原有单据的任意修改），另有 1 条是**多部分文件上传**（整车请款/批量交接的 CSV 原件），也不可能由助手代传。真正可以放开的只有 1 条：整车请款批次的**办理动作**（试办理、改派），而且它的确认/复核/取消动作按你的规则仍然只指路。

| 改动 | 说明 |
|---|---|
| `app/business_assistant_gateway.py` 新增 `DECISION_TOKENS` 与 `assert_not_decision_action` | 通配路由 `/actions/{action}` 上，动作名含批准/驳回/作废/取消/确认/同意/重开/封存/复核/结算/挂账/改价/整批确认/退款/付款/收款/开票/质检/检查/处置/核销/终止 等语义时**拒绝准备**，返回「只能由有权限的岗位在原业务页面本人办理；权限不够时请在“评审申请”里向上级提交」。此前这类动作是可以被准备成确认卡的 |
| `validate_operation` 调用该检查 | 直连准备与"工单动作"（`prepare_case_action`）两条路径都经过它，因此一个口子就够了 |
| `app/business_assistant_capabilities.json` | 加入 `POST /api/vehicle-imports/batches/{batch_id}/actions/{action}`（清单 286 项） |
| `CLASSIFIED_BLOCKED_WRITES` | 14 条禁区写入 + 多部分上传那条，写成代码里可评审的清单；新增测试要求**每一条已注册写入都必须被分类**（清单内或明确 blocked），新加路由而忘记分类时测试直接失败（fail-closed） |

实测：`approve/reject/cancel_request/confirm/quality/inspect/refund/pay/receive/invoice_issue/reopen/seal/settle/credit/revise/commit/consent/void/terminate/dispose/write_off/internal_settle/reinspect/cancel_approve` 共 24 个动作全部拒绝；`follow/start/finish/deliver/material/quote/remind/rework/rectify` 等日常步骤仍可准备；整车请款批次的 `trial/reassign` 可准备，`review/confirm/cancel` 拒绝。

**可调**：这份禁用词表是一个常量。如果你试用后觉得某类动作（例如登记收款）希望让助手准备，改一个词即可——但按你 2026-09-24 的决定，默认保持"判断类只指路"。

## 二、P2：向上级提交评审

新功能，四件东西：数据表、接口、页面、规则。

**规则（都由服务端判定，模型与前端不能指定）**

| 规则 | 实现 |
|---|---|
| 收件人 | 本店店长；申请人本人是店长或管理员时转**集团管理员** |
| 不改变权限、不执行业务 | 评审只写"请求 + 处理轨迹"两张表；没有改角色、没有写入 Case/CashEntry/StockMove；上级在原业务页面本人办理后回这里登记结果 |
| 不能自己批准自己 | `to_review` 队列排除自己提交的申请；对自提申请做动作一律 403 |
| 只解决权限/额度不足 | 原因选"业务规则不允许"时**创建即被拒绝**：422「业务规则明确不允许的事项不能通过评审绕过」 |
| 要凭据事实 | 必须填系统提示原文（≥8 字）与要办的事（≥5 字）；同一件事重复提交 409 |
| 门店范围 | 表按门店隔离；查询用带条件的 select（不是 identity-map get），跨店经理看不到、也动不了 |
| 版本与轨迹 | 处理动作带版本号，过期返回 409；提交/接手/办理/驳回/撤回全部追加到 `escalation_events`，不修改不删除 |

**接口**：`GET /api/escalations?scope=mine|to_review`、`POST /api/escalations`、`POST /api/escalations/{id}/actions/{claim|done|reject|cancel}`。

**页面**：左侧"评审申请"（`#escalations`）。店长/管理员多一个"待我评审"页签；按钮按身份与状态给出（接手 / 已办理 / 驳回 / 查看 / 撤回），办理与驳回必须写说明；详情弹窗显示系统提示原文与完整处理轨迹。

**迁移**：`h47e_escalations`（`down_revision = g35t_assistant_thinking`），新建 `escalations` 与 `escalation_events` 两张表（含状态/原因/收件人的 CHECK 约束与门店状态索引）。迁移只追加，不回改历史。

## 五、按 Codex 评审加固（2026-09-25，PR #8 的 5 条意见全部采纳）

| 评审意见 | 结论与改法 |
|---|---|
| P1 `business_assistant_gateway.py`：禁用词表漏了 `collect` / `execute`，财务记账动作还能被准备 | **采纳**。通配 `{action}` 路由改为**白名单 + 默认拒绝**：已评审的 42 条通配路由中只有 `POST /api/flow/cases/{case_id}/actions/{action}`（动作取自该业务自己的动作目录且非判断类）与 `POST /api/vehicle-imports/batches/{batch_id}/actions/{action}` 的 `trial`/`reassign` 可准备；其余一律 403 并指路原页面。`DECISION_TOKENS` 另补 `collect`/`execute`/`receipt`。新增测试按名单逐条验证“未在白名单 = 不能准备”，并断言白名单里的每条都是已评审的 POST 路由 |
| P1 `escalation_service.py`：用账号级岗位（`account_role`）判定评审人，忽略了当前门店岗位 | **采纳**。新增 `store_role(user)`（请求主体已按门店投影），收件人、评审人、队列范围、处理动作一律按**当前门店岗位**判定；账号级岗位只保留“管理员可撤回他人申请”这一处兼容行为。新增用例：账号是销售、门店岗位是店长的人**可以**评审；账号是店长、门店岗位是销售的人**看不到**队列 |
| P1 `escalation_service.py`：规则型拒绝被信任为申请人自填的类别，可以改成“权限不足”绕过 | **采纳**。新增 `escalation_refusals`（迁移 `h48f_escalation_refusals`）：接口返回 403（以及带权限/额度语义的 422）时由服务端记录操作、状态码、系统原话与类别。提交评审**必须引用**一条记录，类别由服务端从原话判定（`rule` 一律 422 拒绝），记录只能用一次、只能本人用、只在本店、24 小时有效。页面不再让员工选类别，改为在“系统刚挡住的这一步”里选记录提交 |

| P2 `escalation_api.py`：提交接口没进助手网关，对话里只能“让员工自己去页面” | **采纳**。`POST /api/escalations`、`GET /api/escalations`、`GET /api/escalations/refusals` 进入已评审清单与 `DOMAINS`（289 项），助手可以先读被挡记录、再准备“评审申请”确认卡；**办理**评审申请的 `POST /api/escalations/{id}/actions/{action}` 明确列入 `CLASSIFIED_BLOCKED_WRITES`，上级的动作永远只在自己页面办。系统提示同步说明这条流程 |

## 六、按业主裁定重做（2026-09-25 晚）：只保留两条限制

业主原话：“你就让它以当前员工身份去调用 api，如果调用到了被权限拒绝的 api，你就让它提示用户哪些是需要向上申请的，问他要不要申请……再就是创建一个中间流程（比如创建订单），那它的前序流程都需要 ai 询问完成……只有这两个限制，其他的限制都应该去掉吧。”

| 改动 | 说明 |
|---|---|
| 去掉动作闸门 | `PREPARABLE_ACTIONS` / `MONEY_OR_APPROVAL_ROUTES` / `DECISION_TOKENS` 与 `assert_preparable_action` 全部删除；`validate_operation` 不再按动作名拒绝。已评审接口 + 员工本人身份 + 确认卡就是这条链路的全部约束，能不能办由原接口判定 |
| 限制一：被拒 → 提示并可申请 | `permission_hint()`：接口返回 403 时给模型一句“这一步需要更高岗位权限，可读 `GET /api/escalations/refusals` 生成评审申请确认卡”。409/422（业务规则、表单）不给这条提示 |
| 限制二：中间单据先补前序 | 新增 `prerequisite_notes()`：新建流程中间单据时，从该业务自己的 flow spec 里取出前序字段（相关业务/客户/车辆/原单），随准备结果返回 `prerequisites`，要求助手逐项问过员工；对已有单据的动作返回“先读当前可办事项与不可办事项，前置没完成先补” |
| 多步连做 | 系统提示里“每个响应最多两个工具”的限制去掉，改成“为了这一个目标可以连续读原单→读目录→准备→再准备，把需要的几步一次准备好”，每步仍各自一张确认卡；`list_operations` 的工具描述同步放宽 |
| 下一步推荐 | `get_case` 的 `assistant_guidance` 从“只对接待单写死”改成通用：现在能办什么（启用的动作）、哪一项还不能办及原因、本单待办、该状态下无事可办时明确说不要凭空建议；接待单的原有提示保持 |

仍然关闭（非业务面，不属于流程步骤）：凭据与登录、部署与品牌设置、原始附件与下载导出、期初导入、任意旧单据 CRUD、多部分文件上传、以及**办理评审申请本身**。

验证：`tests/test_business_assistant_scope.py` 35 项（含“网关不再按动作名拒绝”“403 带评审提示、409/422 不带”“中间单据带前序事实”“写入分类完整性”“非业务面仍关闭”）；`tests/test_escalations.py` 14 项、助手相关模块共 100 项通过；真实 Chrome 流程不变。全量回归数字见 `CHECKPOINT_STATUS.json`。

## 七、边界与不做的事

- 助手**可以**准备“评审申请”确认卡，但**不能**办理评审申请本身；上级的查看、接手、办结、驳回只在自己的页面完成。
- 评审不产生任何审批结论、不代签、不改权限；上级驳回时申请人只是看到原因，原业务规则不受影响。
- 助手不再按动作名预先拦截：能不能办由原接口用员工本人的岗位判定。被接口拒绝时，助手只会说明“需要更高权限（可提交评审申请）”或“业务规则不允许”，不会改权限、不会绕流程。
- 公司实际业务验收、生产部署、真实 PostgreSQL 仍待进行。
